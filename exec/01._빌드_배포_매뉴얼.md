## 빌드 - 로컬

### A. 로컬에서 실행

준비물은 Docker(Compose 포함)와 Node.js 22.18 이상이다.

```bash
# 1) 클론
git clone https://lab.ssafy.com/s15-bigdata-dist-sub1/S15P21E205.git
cd S15P21E205 && git checkout dev

# 2) 환경 변수 (로컬 기본 계정 thorp/thorp가 들어 있다)
cp .env.example .env

# 3) DB·RabbitMQ·Backend·Worker 빌드와 기동
docker compose -f docker-compose.dev.yml --profile app up -d --build

# 4) Frontend 개발 서버
cd frontend && npm ci && npm run dev
```

종료할 때는 `docker compose -f docker-compose.dev.yml --profile app down`을 실행한다. 데이터 볼륨은 남는다.

| 확인할 곳 | 주소 |
|---|---|
| 화면 | `http://localhost:5173` |
| Backend 상태 | `http://localhost:8080/actuator/health` |
| RabbitMQ 관리 화면 | `http://localhost:15672` (`thorp` / `thorp`) |

localhost인 이유는 ssh 터널링으로 구성했기 때문이다. 서버1의 DB(5432), RabbitMQ 관리 UI(15672), Jenkins(9090)는 모두 127.0.0.1에만 바인딩되어있다. 
서버 자기 자신에서만 접근 가능하고 외부에서는 어떤 방법으로도 닿을 수 없다. (의도적인 보안 설정)

config설정 前 터널링 접근 (명령프롬프트)
- `ssh -i "C:\Users\SSAFY\.ssh\J15E205T.pem" ubuntu@j15e205.p.ssafy.io` 
config설정 後 터널링 접근 (명령프롬프트)
- 일반 : `ssh thorp1`
- 터널링 백그라운드 : `ssh -fN thorp1` 

아래와 같이 config설정 권장
```

HostName j15e205.p.ssafy.io

IdentityFile C:\Users\SSAFY\.ssh\J15E205T.pem
LocalForward 15432 localhost:5432
LocalForward 15672 localhost:15672
LocalForward 9090  localhost:9090
ServerAliveInterval 60
ServerAliveCountMax 3
```

### B. 운영 서버(EC2)에 배포

서버가 이미 구성되어 있다면 **`dev`에 머지하는 것만으로 자동 배포된다**(4.3절). 수동으로 배포할 때는
다음과 같이 실행한다.

```bash
ssh -i J15E205T.pem ubuntu@j15e205.p.ssafy.io
cd /home/ubuntu/S15P21E205 && git pull origin dev
cd infra && ./scripts/deploy.sh
curl -sf https://j15e205.p.ssafy.io/api/actuator/health
```

새 서버를 처음 구성할 때는 4.2절의 순서를 따른다. 요약하면 클론 → `infra/.env.prod` 작성(3.2절) →
인증서 발급(`init-letsencrypt.sh`) → `deploy.sh` → Jenkins 기동 → cron 등록이다.

## 0. 전체 구성

```
                 ┌──────────── EC2 (Ubuntu 24.04, 4 vCPU, 16GB) ────────────┐
 브라우저 ─HTTPS→│ nginx ──/────────→ 정적 파일(React 빌드 결과)             │
                 │   │                                                       │
                 │   ├─/api/──→ backend (Spring Boot, 내장 Tomcat :8080)     │
                 │   │              │  JDBC            │ AMQP               │
                 │   │              ▼                  ▼                    │
                 │   │          PostgreSQL ◀──── RabbitMQ ◀──▶ worker ×N    │
                 │   │                                        (Python)       │
                 │   └─/jenkins/project/ → Jenkins (GitLab 웹훅만 공개)      │
                 └───────────────────────────────────────────────────────────┘
```

- 모든 서비스는 Docker Compose로 뜬다. 앱 스택은 `infra/docker-compose.prod.yml`(프로젝트 이름 `thorp`),
  Jenkins는 `infra/jenkins/docker-compose.ci.yml`(프로젝트 이름 `thorp-ci`)로 따로 띄운다.
- 백엔드는 계산하지 않는다. 백테스트는 RabbitMQ 큐에 작업으로 넣고 워커가 처리한다.
- 네트워크는 둘로 나뉜다. `thorp-edge`에는 nginx·backend·Jenkins가, `thorp-internal`에는
  backend·DB·브로커·워커가 붙는다. DB와 브로커는 외부 노출 경로(`thorp-edge`)에 닿지 않는다.

### 2.2 파트별 빌드 명령

운영 배포는 모두 Docker 이미지로 빌드하므로, 로컬에 JDK나 Python을 설치하지 않아도 배포할 수 있다.
아래는 각 파트를 따로 빌드하거나 검증할 때 쓰는 명령이다.

| 파트 | 로컬 준비물 | 빌드·검증 명령 | 산출물 |
|---|---|---|---|
| backend | JDK 21, Docker (테스트가 Testcontainers로 PostgreSQL·RabbitMQ를 띄운다) | `cd backend && ./gradlew spotlessCheck test bootJar` | `backend/build/libs/*.jar` |
| frontend | Node.js 22.18 이상 (테스트 기준, 팀은 24.x 사용) | `cd frontend && npm ci && npm run lint && npm run test && npm run build` | `frontend/dist/` |
| worker | Python 3.11, uv | `cd worker && uv sync --locked && uv run ruff check src tests && uv run pytest` | 이미지로만 배포 |
| data | Python 3.11 | `cd data && pip install -r requirements.txt -r requirements-dev.txt && pytest` | 이미지로만 배포 |

- 백엔드 포맷이 어긋나면 `spotlessCheck`가 실패한다. `./gradlew spotlessApply`로 고친다.
- Docker가 꺼져 있으면 백엔드 DB 테스트가 실패 없이 건너뛰어진다. CI는 `THORP_REQUIRE_DOCKER=true`로
  이 상태를 실패로 만든다. 로컬에서도 결과의 `skipped` 수를 확인한다.

### 2.3 이미지 빌드 방식

| 이미지 | Dockerfile | 빌드 컨텍스트 | 방식 |
|---|---|---|---|
| `thorp-backend:latest` | `infra/docker/backend.Dockerfile` | `backend/` | JDK 21에서 `./gradlew bootJar` → JRE 21 이미지에 `app.jar`만 복사, `java -jar app.jar` |
| `thorp-worker:latest` | `infra/docker/worker.Dockerfile` | `worker/` | `uv sync --frozen --no-dev`로 `uv.lock` 그대로 설치 → 가상환경과 `src/`만 복사, `python -m worker.main` |
| `thorp-data:latest` | `infra/docker/data.Dockerfile` | `data/` | `requirements.txt`로 설치. 실행할 스크립트는 매번 지정한다 |
| 프론트 정적 파일 | 없음 (`node:20-alpine` 컨테이너) | `frontend/` | `npm ci && npm run build` → `infra/nginx/html/`로 복사 |

### 4.3 평상시 배포 (자동)

`dev`에 머지되면 GitLab 웹훅 → 배포 Job이 다음을 순서대로 한다.

1. **Sync**: `$DEPLOY_DIR`에서 `git fetch` → `git checkout dev` → `git reset --hard origin/dev`.
   `.env.prod`, `certbot/`, `nginx/html/`은 gitignore 대상이라 지워지지 않는다.
2. **Deploy** (`infra/scripts/deploy.sh`)
   - `[0/4]` `backtest.jobs`가 classic 큐면 멈춘다(4.5절 참고).
   - `[1/4]` `node:20-alpine` 컨테이너(메모리 2g, CPU 2)에서 `npm ci && npm run build`.
   - `[2/4]` `infra/nginx/html/`을 비우고 `frontend/dist/`를 복사.
   - `[3/4]` `docker compose build backend worker` → `docker compose up -d`.
   - `[4/4]` nginx 템플릿을 다시 생성하고 `nginx -t`가 통과하면 `nginx -s reload`. 이어서 `docker image prune -f`.
3. **Smoke test**: `nginx -t`, 내부망에서 `http://backend:8080/actuator/health`(최대 30회 재시도),
   외부 경로 `https://${DOMAIN}/api/actuator/health`를 인증서 검증을 켠 채 확인한다.
4. 실패하면 backend 최근 로그 200줄을 콘솔에 남기고 Mattermost로 알린다.

### 4.5 배포 시 특이사항

- **`deploy.sh`는 반드시 `$DEPLOY_DIR/infra`에서 실행한다.** Jenkins 컨테이너는 호스트의 docker.sock으로
  컨테이너를 띄우므로 bind mount 경로가 호스트 기준으로 해석된다. Jenkins 워크스페이스에서 실행하면 빈
  디렉토리가 마운트된다. 같은 이유로 Jenkins 컨테이너에는 `DEPLOY_DIR`을 호스트와 같은 경로로 마운트한다.
- **서버 클론에서 추적 파일을 고치지 않는다.** 배포 때마다 `git reset --hard`로 덮어쓴다.
  폐기된 내용은 빌드 로그에 경고로 남는다.
- **Jenkins는 앱 스택과 다른 compose 프로젝트(`thorp-ci`)다.** 같은 파일에 넣으면 배포 중에 Jenkins가
  자기 자신을 재시작해 파이프라인이 끊긴다.
- **DB 스키마는 Flyway가 백엔드 기동 시 적용한다.** 마이그레이션 파일은
  `backend/src/main/resources/db/migration/`에 있다. 이미 적용된 파일은 고치지 않고 새 버전 파일을 더한다
  (`validate-on-migrate`가 체크섬 변경을 막는다). CI의 `Migration version` 단계가 버전 번호 중복과, dev에 이미 있는
  버전보다 낮은 번호를 새로 넣었는지(운영에서 기동이 막힌다)를 검사한다. 기존 DB를 처음 Flyway로 옮길 때의 절차는 `docs/guides/prod-db-flyway-migration.md`다.
- **큐 타입 전환.** `backtest.jobs`가 옛 classic 큐로 남아 있으면 `deploy.sh`가 멈춘다.
  `./scripts/migrate-jobs-queue.sh`로 한 번 전환한 뒤 다시 배포한다(`docs/guides/backtest-queue-migration.md`).
  현재 운영 서버는 이미 quorum으로 전환되어 있다.
- **nginx 템플릿 변경은 재시작 없이 반영되지 않는다.** `deploy.sh`의 `[4/4]`가 다시 생성하고 reload한다.
  `nginx -t`가 실패하면 reload하지 않는다.
- **`/api/` 프록시 설정의 두 가지를 지우지 않는다.** `proxy_pass http://backend_was/`의 끝 `/`가 없으면
  백엔드가 `/api/...` 경로를 받지 못한다. `proxy_buffering off`가 없으면 진행 그래프가 실행이 끝날 때까지 멈춰 보인다.
- **한도 변수가 빠지면 백엔드가 뜨지 않는다.** `.env.prod.example`에 새 변수가 생긴 MR이 머지되면
  서버의 `.env.prod`에도 먼저 넣어야 한다. 빠진 채 배포하면 스모크 테스트에서 실패한다.
- **데이터 배치는 배포 파이프라인이 만들지 않는다.** 경제지표 적재와 경제환경 사전 계산은
  `data-batch` 서비스(`batch` 프로필)를 필요할 때 `run --rm`으로 띄운다. 절차는 `docs/guides/regime-batch-operation.md`다.
  ```bash
  docker compose -f docker-compose.prod.yml --env-file .env.prod --profile batch build data-batch
  docker compose -f docker-compose.prod.yml --env-file .env.prod --profile batch run --rm data-batch python scripts/precompute_regime.py --source macro
  ```
- **워커 엔진 버전.** `worker/uv.lock`이나 계산 규칙을 바꾸면 `application.yml`의 `thorp.backtest.engine-version`도
  바꿔야 한다. 어긋나면 백엔드·워커 테스트가 올바른 값을 알려 주며 실패한다.
- **프론트 빌드 Node 버전이 CI와 다르다.** 배포는 `node:20-alpine`으로 빌드하고 CI는 Node 24로 검사한다.
  테스트는 Node 22.18 이상이 필요하지만 배포에서는 빌드만 하므로 현재는 문제가 없다.
- **사례 연결 워커(`worker-regime-link`)는 로컬 `docker-compose.dev.yml`에만 있고 운영 compose에는 없다.**
  운영 서버에서도 이 컨테이너는 돌고 있지 않다(2026-09-28 확인).
- **백업.** `backup-db.sh`가 매일 04:30에 `/data/backup/thorp-YYYYMMDD-HHMMSS.sql.gz`를 만들고 14일 지난 파일을 지운다.
  복원: `gunzip -c <파일> | docker exec -i thorp-postgres psql -U thorp -d thorp`.
- **자원.** 호스트는 4 vCPU·16GB를 앱과 Jenkins가 함께 쓴다. CI 빌드 두 개와 배포가 겹치면 느려진다.
  Jenkins 실행 슬롯은 CI 최대 2개, 배포 1개다(`infra/jenkins/init.groovy.d/`).

| Jenkins → GitLab | 소스 fetch (`gitlab-deploy-token`), MR 상태 보고 (`ssafy-gitlab`) | Jenkins 자격 증명 저장소 | `Jenkinsfile` |
| Let's Encrypt | 인증서 만료 알림 수신 | `infra/.env.prod`의 `CERTBOT_EMAIL` | `infra/scripts/init-letsencrypt.sh` |
| EC2 SSH | `ubuntu` 사용자, 키 파일 `J15E205T.pem` | 팀원 개인 보관 | — |

로컬 개발용 계정은 `thorp` / `thorp`(DB·RabbitMQ 공통)이며 `.env.example`과 `application.yml`의 기본값에
적혀 있다. 운영에서는 쓰지 않는다.

### 5.2 프로퍼티·설정 파일 목록

**환경 변수**

| 파일                        | 내용                                                   |

**백엔드 (Spring Boot)**

| 파일 | 내용 |
|---|---|
| `backend/src/main/resources/application.yml` | 공통 설정. DB·RabbitMQ 접속(로컬 기본값 포함), 세션, 메일, 실행 한도·결과·탐색 기본값, 엔진 버전 |

| `backend/src/main/java/com/ssafy/thorp/market/infrastructure/config/MarketConfig.java` | 외부 API 키와 시장 조회 정책을 환경 변수에서 직접 읽는다 |
