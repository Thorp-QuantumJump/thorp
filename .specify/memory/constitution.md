# Thorp Constitution

Team Quantum Jump의 퀀트 전략 분석 플랫폼 **Thorp**가 프로젝트 내내 지키는 원칙이다. 사람과
AI(Claude 등) 모두에게 적용된다.

- 근거는 기획서(Notion)의 "확정한 방향"과 본문 실행 기준, 동결된 Git Convention·Jira Convention,
  그리고 Constitution 작성 가이드만이다. 기획서 결정은 D01~D27, 미확인 검증 항목은 U01~U06 번호로
  인용한다.
- 규칙은 **위반 여부를 판정할 수 있는 문장**으로만 쓴다. "~한다", "~하지 않는다", "~금지"는 모두
  MUST 수준이다. 규칙마다 가능하면 **왜**를 붙인다.
- 스프린트마다 바뀌는 것(이번 범위, 기능 우선순위, 수치 기본값, 담당·일정)은 여기 쓰지 않고
  spec에 쓴다. 팀이 합의하지 않은 영역은 규칙을 만들지 않고 "넣지 않은 영역"에 이름만 남긴다.

## Core Principles

### I. 중심 약속은 전략 진단이다

- 제품의 중심 기능은 전략 진단이다. 시장 흐름의 경제환경 탐색과 뉴스는 결과를 해석하는 맥락이고,
  배우기는 입문자가 진단을 시작하도록 돕는 보조다. 우선순위가 충돌하면 진단 흐름을 먼저 지킨다.
  (§2, D01)
- 시장 흐름에서는 전략을 정하지 않아도 분야별 경제환경과 과거 사례를 탐색할 수 있고, 선택한 구간을
  '이 기간으로 전략 비교'로 진단에 연결한다. 검색은 전략을 고르는 신호가 아니라 규칙의 행동을
  이해하는 분석 맥락이다. (§4.3, D25)
- 기능의 **구현 완료**와 **실제 효과 입증**은 구분해 말한다. "구현했다"를 "효과가 입증됐다"로, "모델
  명세를 마쳤다"를 "코드로 구현했다"로 쓰지 않는다. (§2, §9, D17)
- 효과 검증 완료를 개발 착수 조건으로 두지 않는다. 검증이 부족하면 결과 옆에 표시하고 기능 자체를
  되돌리지 않는다. (§7.3, D08, D11)
- 시작 절차로 고객군 선택 설문이나 숙련도 분류를 요구하지 않는다. 진단 전에 학습 수강을 요구하지
  않는다. (§3.2, §4.5, D02)

왜: 중심 약속이 없으면 첫 화면·개발 우선순위·검증 기준이 서로 다른 방향으로 설계되고, 실패한
목표를 다른 목표의 성과로 덮을 수 있다. (D01)

### II. 첫 화면은 단순하게, 복잡한 계산은 시스템이 맡는다

- 계산식·자료 공급원 선택·거리 함수·실험 식별자·서버/인프라 설정을 사용자 기본 입력으로 요구하지
  않는다. (§4.1, §6.5)
- 화면마다 가장 중요한 행동 버튼을 하나만 정한다. **다만 설정 조합을 일괄 비교하는 보조 경로가
  주된 사용 경로로 확인된 화면은 예외로 같은 크기의 버튼 두 개를 둘 수 있다.** 이 예외는 팀이
  spec 단계에서 근거(그 보조 경로를 대체 UI로 숨겼을 때 실제로 쓰임이 줄어드는지, 또는 그 경로가
  없으면 같은 결과를 얻기 위해 반복 조작이 필요한지)를 spec에 적고 constitution 개정 절차로
  확인받은 경우에만 적용되며, 화면 설계자가 임의로 늘릴 수 없다. (§4.1, spec 003 FR-002,
  S15P21E205-253)
- 결과 첫 화면은 **핵심 숫자 3개(비용 차감 후 전체 수익률·가장 크게 줄었던 폭·거래비용), 비교
  그래프 1개, 해석 요약 1문장**으로 구성한다. (§4.1, §4.2.3, D10, D25)
- 분석 기간·비교 대상·비용 적용 여부는 요약 한 줄에 항상 보인다. 결과 의미를 바꾸는 자료 부족·근거
  부족·미판정 상태는 해당 결과 옆에 한 문장으로 표시하고 상세 안에만 숨기지 않는다. 내부 검증 미완료를
  모든 화면의 경고 목록으로 늘리지도 않는다. (§4.1, §7.2, §7.4)
- '자세히 보기'는 결과 근처에 둔다. 상세 정보를 보기 위해 설정 화면으로 되돌려 보내지 않는다. (§4.1)
- 정보는 세 층으로 배치한다: 처음에 바로 보이는 정보 / 요청하면 펼쳐 보는 정보 / 시스템이 처리하는
  정보. 내부 계산 항목이 많아도 화면에 동시에 나열하지 않는다. (§4.1)
- 전략 카드에는 쉬운 이름과 한 줄 설명만 둔다. 상세 설정은 선택한 전략에 해당하는 항목만 열고
  의미·허용 범위·기본값 복원을 함께 제공한다. (§4.2.2)
- 경제환경은 **분야별 비교가 기본**이고 종합 비교는 사용자가 선택해서 연다. 현재 경제를 하나의 좋고
  나쁜 점수로 평가하지 않으며, 분야 안에서도 개별 지표의 실제 값·단위·최근 경로를 유지한다.
  (§4.3, §4.4, D08, D21)
- 첫 결과에서 여러 상세 패널을 반드시 열어야 핵심을 이해할 수 있다면 요약 화면을 수정한다. (§7.2)

왜: 기획서가 "가장 중요한 설계 원칙"으로 못 박았다. 많은 금융지표·설정·주의문을 읽어야만 결과를
볼 수 있는 구조는 복잡도를 사용자에게 그대로 넘기는 것이다. (§2) 버튼 두 개 예외는 이 원칙을
느슨하게 하는 것이 아니라, "가장 중요한 행동"이 화면마다 하나가 아니라 둘로 확인된 드문 경우를
숨기지 않고 명시해 임의 확산을 막기 위한 것이다. 근거 없이 버튼을 늘리면 이 원칙 자체가 무력화된다.

### III. 진단이지 추천이 아니다

- '추천 비중', 주문 버튼, 자동 단일 승자, 일·주·월간 우승 전략, 사용자 간 성과 랭킹을 만들지 않는다.
  자신의 실험 간 비교는 제공한다. (§4.2.3, D13, D16)
- 자동 전략의 출력 비중은 선택한 규칙의 계산 결과로 명시하고, 사용자가 직접 입력한 비중과 구분한다.
  (§4.2.1, D13)
- 초깃값·기본값은 입력 편의를 위한 예시이자 출발점이며, 최적값이나 투자 권고로 표기하지 않는다.
  (§4.2.1, §4.2.2)
- 유사도를 '87% 유사' 같은 확률로 오해할 숫자나 '지금도 잘될 전략' 같은 표현으로 나타내지 않는다.
  거리·순위·유지율을 투자 성공 확률이나 확률적 신뢰도로 변환하지 않는다. (§4.3, §6.4.4, §7.3, D09)
- 거리순 상위라는 이유로 '대표 유사국면' 같은 배지를 붙이지 않는다. (D24)
- 유리했던 기간만 골라 전략을 평가하거나 과거 최고 수익 조합을 현재의 정답으로 표시하지 않는다.
  이후 결과가 좋았다는 이유로 사례를 선택하지 않는다. (§3.1, §4.3)
- 뉴스나 경제환경의 유사성이 그 전략 수익의 원인이었다고 단정하지 않는다. 추가 표본 없이 특정
  경제지표를 수익의 원인으로 설명하지 않는다. (§4.4, §6.4.4, D25)
- 미사용 검증이 없거나 기준보다 개선되지 않은 결과를 '자동 우월성'이나 개인별 투자 추천으로 제시하지
  않는다. (§7.3)

왜: 같은 데이터라도 과거를 설명하는 출력과 개인에게 판단을 제안하는 출력은 사용자 행동을 다르게
유도하며, 기능 이름이나 면책 문구만으로 그 차이가 사라지지 않는다. (D13)

### IV. 비교는 같은 조건에서만 한다

- 후보 비교는 같은 섹터 후보 집합·같은 평가 기간·같은 금액·같은 비용·같은 정보 이용 기준으로 한다.
  (§4.2.3, D10)
- 후보마다 유리한 과거 기간을 달리 선택하지 않는다. 긴 관측 기간 때문에 공통 평가 구간이 줄면
  실행 전에 사용자에게 알린다. (§6.4.1, §6.4.3, D06)
- 수수료·세금·평가 기간은 수익을 높이는 방향으로 자동 최적화하는 변수가 아니다. (§4.2.2, §6.4.3)
- 비교 기준은 사용자 고정 비중·동일 비중을 기본으로 유지한다. 자동 탐색의 전략 비교 효과와 경제환경
  검색의 안정성·설명력은 각각 따로 구분한다. (§4.2.3, §7.3, D10)
- **경제환경 후보는 선택 전략과 독립적으로 결정한다.** 같은 기준월·분야·자료/모델 버전·가용 후보
  집합에서는 전략을 바꿔도 순위가 바뀌지 않는다. 전략의 성과·수익·손실을 검색 입력이나 후보 선정에
  쓰지 않으며, 필터는 자료 가용성에만 의존한다. (§4.3, §6.4.4, D07, D26)
- 경제환경 사례에서 전략을 비교할 때 후보 전략 모두 같은 평가 날짜·비용을 쓰고, 기간이 다른 거래량은
  월당 거래횟수·회전율 등 같은 척도로 비교한다. (§4.3, D25)
- 실제 보유 섹터가 달라졌다면 상세에서 선정 효과와 배분 효과를 함께 설명한다. (§4.2.3)
- 종료 시 시가평가 결과와 청산 비용을 포함한 결과를 구분한다. (§6.4.1)

왜: 기간·위험·비용 가정이 다른 결과를 같은 우열로 나열하면 전략이 아니라 가정의 차이를 측정하게
된다. 전략을 바꿀 때 유리한 과거 구간도 함께 바뀌면 규칙 비교가 되지 않는다. (D07, D10)

### V. 당시에 알 수 있던 정보만 쓴다

- 신호와 리밸런싱 판단은 판단 시점까지 이용 가능한 자료로만 하고, 가상 체결은 그 다음 거래일에 한다.
  (§6.4.1, §6.4.2)
- 상장 전 합성 이력이나 미래 자료로 빈 값을 채우지 않는다. 상장 전 지수 성과를 본 결과에 혼합하지
  않는다. (§6.1, D03)
- 거시 통계는 **최신 개정자료로 과거 경제환경을 비교하는 역사 탐색**과 **당시 공개 정보로 의사결정을
  재현하는 분석**을 구분한다. 역사 탐색에는 최신 개정자료를 쓸 수 있으며 화면에 그 기준을 명시한다.
  (§6.1, §4.4, D12)
- 발표 시차만 적용한 최신 개정값은 당시 자료로 간주하지 않는다. 실제 발표일과 당시 발표·수정값을
  확보하기 전에는 거시 검색을 과거 매매·비중 결정 신호로 쓴 실시간 전략 검증을 주장하지 않는다.
  (§6.1, §6.4.4, D06)
- 경제환경 사례 이후의 63거래일 주 평가·21거래일 보조 평가는 역사 설명용 기준이며, 실제 거시자료
  발표 직후 매매를 재현한 것이 아니다. 당시 의사결정 재현은 발표일·빈티지 이용 가능 시각 이후로 별도
  정렬한다. (§6.4.4, D06)
- 공통 척도(중앙값·산포)는 현재 질의 구간 직전의 과거 자료로만 추정하고, 그 척도를 질의와 모든 과거
  후보에 동일하게 적용한다. 미래 값 추정이나 임의 보간으로 최신월을 늘리지 않는다. (§6.4.4, D21, D22)
- 과거 가상 오늘에서 사후 성과를 참고할 때는 그 시점까지 평가가 완료된 사례만 쓰고, 워밍업 구간은
  성과에서 제외한다. (§6.4.4, D06)
- 과거 진단 화면과 과거 사건에는 당시 발행된 뉴스만 연결한다. 현재 뉴스와 과거 사건 설명을 구분한다.
  GDELT 기록 시각을 기사 발행 시각으로 단정하지 않는다. (§4.4, §6.3)

왜: 당시 공개되지 않은 값으로 판단하거나 신호를 알기 전 가격에 체결하면 전략이 아니라 데이터·실행
가정의 이득을 측정하게 된다. 역사 검색이 안정적이라는 사실과 당시 실행 가능한 투자 성과가
개선된다는 주장은 다르다. (D05, D11)

### VI. 없는 결과를 만들어내지 않고, 사용자 입력을 몰래 바꾸지 않는다

- 결과를 만들 수 없을 때 0이나 확신 있는 요약으로 대체하지 않는다. 자료 부족·빈 뉴스·수집 지연·계산
  실패·ETF 미상장·사후 자료 미완성도 정상 화면 흐름으로 처리한다. (§7.1, §4.3)
- 질의 기준 자료나 관측값의 결측을 임의 보간하지 않는다. 척도가 0이거나 공표 정밀도에 비해 지나치게
  작으면 임의 epsilon을 넣거나 묵시적으로 클리핑해 순위를 만들지 않고, 해당 지표·분야·종합 결과를
  제한한다. 확인된 비정상 척도의 지표를 몰래 빼고 계산하지 않는다. (§6.4.4, D27, U06)
- 처음 3개·최대 10개 사례를 억지로 채우지 않는다. 후보가 부족하면 부족한 대로 보인다. (§6.4.4, D09)
- 전략 진입 경로의 가용성 필터 결과로 전체 경제환경 순위를 조용히 대체하지 않는다. 가장 가까운
  사례를 상품 자료 부족 때문에 다른 사례로 바꾸지 않고, 해당 전략 결과만 '자료 부족'으로 표시한다.
  (§4.3, D09, D26)
- 제약 위반·자료 부족·계산 실패를 낮은 수익과 구분해 기록하고 표시한다. (§6.4.3)
- 확인할 수 없는 내용(기사 제목·요약 등)을 생성하지 않는다. 제목·요약은 확보한 정보에만 근거한다.
  (§6.3)
- 데이터 제공 지연이 있는 항목을 실시간 정보라고 표시하지 않는다. 자료가 오래됐거나 수집이 실패했으면
  마지막 갱신 시각을 보인다. (§4.4)
- 사용자 비중을 임의로 바꾼 뒤 알리지 않는 처리를 하지 않는다. 합계가 맞지 않으면 그 위치에 남은
  비중을 표시하고 '동일하게 나누기'로 되돌릴 수 있게 한다. (§4.2.1)
- 기준월이나 검색 모드가 바뀌어 후보가 달라지면 한 문장으로 알리고 유지율과 변경 내용을 보이며, 별도
  검색으로 기록한다. (§4.3, §4.4, D22)
- 한도 초과·부분 완료·제약 위반은 이유를 짧게 알리고 완료한 범위를 명시한다. (§4.2.2, §6.5)
- 미확인 상태를 검증 완료로 표현하지 않는다. 확인한 범위와 확인하지 못한 범위를 함께 적는다.
  (§6.4.4, §10.1)

왜: 서비스가 항상 답을 내도록 설계되면 근거가 부족할 때도 확신을 만들어 낸다. (D09)

### VII. 탐색과 검증을 구분하고, 기준은 결과를 보기 전에 고정한다

- 선정 절차는 **내부 개발 구간 → 시간 순서 외부 평가 → 최종 잠금 평가** 순으로 검증한다. 가상 오늘을
  옮겨 반복하며 과거·미래를 무작위로 섞지 않는다. (§7.3, D11)
- 후보 탐색·정규화 추정·선정 기준·지표·거리·문턱의 튜닝은 내부 개발 구간에서만 하고, 외부 평가
  구간에서는 절차를 고정한다. (§6.4.3, §7.3)
- 선정 지표·허용 오차·분할 날짜·통계 보정 방식·동률 처리·표시 후보 수·유사성 임계값·경제적 설명력
  판정 기준은 시험 전에 고정한다. 결과를 확인한 뒤 기준을 바꾸면 새 실험이다. (§6.4.3, §7.3, D10, D11)
- 잠금 구간을 보고 수정한 실험은 그 구간을 더 이상 미사용 검증이라 부르지 않는다. (§7.3, D11)
- 경제환경 검색의 가중치·후보·지표를 KOSPI나 전략의 이후 수익률이 높아지는 방향으로 고르지 않는다.
  KDI 보고서 문장은 외부 대조에만 쓰고 검색 입력으로 쓰지 않는다. (§7.3, D11, U02)
- 경제환경 검색의 계산 정확성·후보 안정성·경제적 설명력은 전략 성과 개선과 분리해 검증한다. 최신
  개정자료만 쓴 실험은 역사 검색 평가로 명시한다. (§7.3, D11)
- 검색 상태는 **'계산 불가/후보 없음' / '가까운 순서만 제공·유사성 미판정' / '교정된 기준 충족
  여부'** 세 가지로 구분한다. 문턱을 교정하기 전에는 '충분히 유사' 배지를 붙이지 않고, 미교정이라는
  이유로 '충분한 사례가 없다'고 단정하지도 않는다. 교정 뒤 충족 사례가 없으면 분야별 탐색으로 연결한다.
  (§4.3, D24, U04)
- 사용자에게 보이는 결과 옆에 '탐색 결과 / 미사용 검증 결과 / 미검증'을 구분해 표시한다. 연구 로그와
  세부 통계는 내부·상세에 둔다. (§4.2.3, §7.3, D11)
- 같은 사건의 반복 날짜나 연속된 유사 날짜를 여러 독립 사례처럼 세지 않는다. 날짜 간격만으로 독립
  사건이라고 간주하지 않는다. (§4.3, §6.4.4, D09)
- 검증 대상은 최종 전략 하나가 아니라 전략군·파라미터·검색 지표·가중치·사례 선택을 포함한 전체
  절차다. (§7.3, D11)
- 실제 자료나 사용자 관찰 없이 확인할 수 없는 항목(U01~U06)은 기능 구현과 병행하며, 미확인을 실패로
  취급하거나 관측하지 않은 효과를 확정하지 않는다. 각 항목은 "검증 전 동작"대로 움직인다. (§7.4)

왜: 결과를 보며 전략·지표·거리·사례 수를 바꾸면 선택 과정 전체가 과거에 맞춰지고, 통과 기준이
움직이면 어떤 결과도 성공으로 설명할 수 있다. (D11)

### VIII. 재현할 수 있게 기록한다

- 완료한 분석마다 전략·파라미터 범위·선정 기준·시드·평가 분할·섹터/ETF 대응·당시 대상·데이터
  마감/버전·비용·엔진·검색 설정·사례 선정·원본 ID를 저장한다. (§5, D14)
- 경제환경 탐색 기록에는 선택 분야 또는 종합 모드, 실제 질의 기준월, 전체 후보와 표시 후보, 제외 이유,
  지표 원값과 표준화 값, 분야별 거리, 자료 개정 기준, 모델 버전, 연결한 섹터·ETF·전략·사후 평가 구간,
  당시 정보 재현 여부를 저장한다. 두 검색 경로의 순위·필터·연결 결과는 별도 보존한다. (§5, D14, D26)
- 자동 탐색은 탐색 공간·실행한 전체 후보·미실행 후보 수·제외 사유·평가 분리·정렬 및 선정 규칙을
  기록한다. 유효하지 않아 계산하지 않은 후보도 제외 사유를 남긴다. (§5)
- 설정을 바꾸면 새 분석(새 버전)으로 보존하고 기존 결과를 덮어쓰지 않는다. 나중의 결과에 맞춰 과거
  기준을 덮어쓰지 않는다. (§5, D14, D15)
- 사용자에게 버전이나 실험 ID 입력을 요구하지 않는다. (§5, D14)
- 전략 규칙의 선택(유형·산식·관측 길이·선정/배분·예외 처리)과 수수료·호가 차이·슬리피지·세금·비용
  상승 조건은 결정한 뒤 버전으로 남긴다. (§6.4.2, D05)
- 지표 등록·분야 매핑·계산 가중은 화면 분류와 **별도 버전**으로 관리한다. 화면 이름이나 배치를
  바꿨다는 이유로 계산 가중이 자동으로 바뀌지 않게 한다. 질의 기준월이 바뀌면 척도와 순위도 달라질 수
  있으므로 버전을 기록한다. (§6.4.4, D23)
- 시도·실패·최종 평가 열람 등 감사 정보는 내부에서 관리한다. 개인 식별정보는 계산 기록과 분리한다.
  (§5)

왜: 한 번 시험한 결과와 수많은 실패 중 골라 남긴 결과는 같은 증거가 아니며, 데이터·비용·엔진·선정
규칙 버전이 빠지면 같은 조건을 재현할 수 없다. (D14)

### IX. 실행 한도는 실측으로 정하고, 과금과 구분한다

- 실행 구조는 단일 서버 작업 큐·독립 실험 프로세스 병렬화·특징 사전 집계·캐시로 시작한다. 분산
  Worker·Spark·별도 빠른 탐색 엔진은 병목을 실측한 뒤 판단하며, 기능 확대가 곧 분산 도입 확정을
  뜻하지 않는다. (§6.5, D18)
- 별도 엔진은 Nautilus와 계산 의미·후보 선정 차이를 대조한 뒤 채택한다. 미측정 처리량을 제시하지
  않는다. (§6.5, D18)
- 전략 단일 실행·자동 탐색 묶음·분야별 및 종합 경제환경 검색을 구분해 대기 포함 p50/p95 지연·
  동시성·메모리·실패·건당 비용을 측정한다. (§6.5)
- 후보 수·실행시간·대기열·메모리 상한은 실측 후 고정한다. 상한을 정하기 전에 무제한 탐색을 열지
  않는다. (§6.4.3, §6.5, D18)
- 경제환경 검색은 기준월·자료 버전·모델·분야별로 사전 집계하고 전략과 독립된 검색 캐시를 둔다.
  검색 결과와 전략 실행은 사례 식별자·평가 날짜로 연결하며 ETF 가용성 필터는 별도 키로 보존한다.
  (§6.5)
- 자동 탐색에는 기술적 사용량 상한과 원가 기록을 적용한다. 진단 화면에 포인트·상품 선택·결제 단계를
  넣지 않는다. 가격·무료 범위·유료 제공량은 출시 검토 시 정한다. (D19)
- 계산·데이터·저장 원가와 동일 결과 재조회를 구분해 기록한다. (§6.5, D19)

왜: 실제 병목이 아닌 곳을 최적화하면 운영 복잡도와 비용만 늘고(D18), 기술적 실행 한도와 유료
과금은 다른 결정이므로 혼동하면 안 된다(D19).

### X. 자료는 이용 조건 안에서만 쓴다

- KRX OPEN API와 DATA_GO_KR 증권상품시세는 **개발·검증 단계의 원천**으로만 쓴다. 두 원천은 비상업
  이용과 제3자 제공·재배포 금지를 조건으로 하므로, 실제 서비스 제공용 시세는 KRX 데이터상품 구매 여부와
  비용을 사업 결정에서 다룬 뒤 별도 확보한다. (§6.2, §8.2, D19)
- KRX 자료를 쓰는 화면에는 '한국거래소 통계정보' 출처를 표시한다. ECOS·KOSIS 통계는 출처 표시를 전제로
  쓰고, 지표 등록표에 작성기관을 함께 기록한다. 한국은행 이외 기관이 작성한 ECOS 통계는 해당 기관의
  조건을 따른다. (§6.2)
- KOSIS·ECOS 제공 정보를 플랫폼 없이 그대로 제3자에게 유료 제공하지 않는다. (§6.2)
- 뉴스는 기사 본문을 저장·재배포하지 않고 제목·매체·발행 시각·원문 링크만 다룬다. 이 표시 방식이 매체의
  사전 허가 대상인지는 시장 흐름 뉴스 묶음 공개 전에 매체에 확인한다. (§6.3, §10.1)
- KDI 월간 경제동향은 지표 후보 선정과 해석의 참고 근거다. Thorp의 분야 분류·가중치·거리·사례 선택은
  Thorp 자체 설계이며 KDI 공식 모델로 표현하지 않는다. 원천 차이가 해소되지 않은 지표를 KDI 보고서와
  완전히 같은 값이라고 표현하지 않는다. (§6.2, §6.4.4)
- API 인증키는 서버에서 관리하고 서비스 이용자에게 요구하지 않는다. 자료를 이용할 수 없으면 범위를
  줄이거나 허용된 대체 자료·명시된 예시 자료로 개발한다. (§6.2)
- 이 조건 확인은 입력 자료를 정하는 개발 작업이며, 향후로 미룬 투자자문·제품 출시 관련 법률 검토를 이번
  범위에 다시 추가하는 것은 아니다. (§6.2, D13)

왜: 데이터 이용 권한이 불명확하면 서비스 제공 범위를 확정할 수 없고, 허용 범위를 넘긴 자료로 만든
결과는 출시 시점에 통째로 무효가 된다. (D05, §8.2)

## 프로젝트 범위와 용어

### 해결하는 문제 (§2, §3.1, D20)

- Thorp는 **국내 섹터 ETF의 배분 전략과 설정 조합이 과거 수익·손실·비용에 어떤 차이를 만드는지 쉽게
  비교**하는 서비스다. 사용자는 생산·소비·고용·물가 등의 상태를 여러 지표로 확인하고, 경제환경이
  가까운 과거 구간 이후 자신의 전략이 어떻게 움직였는지 살펴볼 수 있다.
- 사용자 흐름은 **섹터 선택 → 전략과 설정 확인 → 같은 조건으로 비교 → 차이와 취약 조건 이해**다.
  직접 지정한 설정뿐 아니라 사전 정의한 범위의 조합도 자동 비교한다. 경제환경 탐색은 '지금과 비슷했던
  때는 언제인가'와 '그 구간 이후 같은 전략은 어떻게 움직였는가'를 연결하되, 후보를 먼저 확정한 뒤 같은
  후보에서 전략을 비교한다. 전체 기간 분석은 항상 함께 유지한다.
- 차별화 방향은 국내 섹터 ETF의 비중 비교, 한국어 설명, 국내 뉴스·경제자료를 한 흐름으로 연결하는
  것이다. '국내 전용 경쟁자가 없다'를 확인된 사실처럼 쓰지 않는다.

### 핵심 사용자 (§3.2, D02)

- 전략을 검증하려는 개인, 거시경제·뉴스 관심 사용자(전략 없이 분야별 경제환경·과거 사례·뉴스를
  탐색하고 원하면 선택 구간으로 전략 비교를 시작), 완전 입문자. 세 이용 목적을 모두 지원한다.
- 숙련 퀀트 전용 기능은 만들지 않는다. 고객군별 전환율·재방문율 측정과 별도 운영 성과 실험은 운영
  요구에서 제외한다.

### 대상 시장과 자산 (§3.3, D03)

- 분석 단위는 섹터/테마(반도체·2차전지 등)의 비중이다. 계산과 가상 체결은 국내 주식에 투자하는 국내
  상장 **비레버리지·비인버스 ETF**에 연결한다. 원화·일봉·매수 보유 중심이며 공매도·레버리지는 사용하지
  않는다.
- 대표 ETF는 서비스가 미리 관리한다. 사용자는 섹터 이름과 연결된 ETF 이름만 확인하면 시작할 수
  있다. 업종과 테마를 구분하고, 대표 ETF의 실제 상장 이후 기간으로 비교한다.
- 현재 생존 상품만 고른 결과의 한계, 유동성·추적 차이·구성종목 중복은 상세('대표 상품 정보')에서
  관리·표시한다.

### 화면 구조 (§4.1, §4.3, §4.4, §4.5)

- 주요 메뉴는 **전략 진단 / 시장 흐름 / 배우기**이고, 저장한 분석은 보조 메뉴 **내 기록**이다. 처음
  진입하면 전략 진단을 바로 시작할 수 있다.
- 전략 진단은 세 단계로 완료한다: 섹터와 비중 정하기 → 전략과 설정 확인·분석 → 결과 이해·비교.
- '경제환경이 비슷했던 과거 보기'는 시장 흐름과 전략 진단 결과에서 공통으로 접근한다. 시장 흐름에서 온
  사용자는 '이 기간으로 전략 비교'로 섹터와 전략을 정하고, 진단 결과에서 온 사용자는 기존 섹터·전략·설정을
  유지해 같은 구간을 확인한다.
- 시장 흐름은 전략을 만들지 않아도 볼 수 있는 진입 화면이며 생산·소비/투자·대외거래·노동·물가/원자재·
  금융/주택·해외 경기의 7개 분야를 구분한다. 거시경제 API와 뉴스의 이름을 사용자가 고르게 하지 않는다.
  경제환경 검색은 섹터 선택에 따라 바뀌지 않으며, 선택 섹터는 연결할 전략·상품·뉴스의 범위를 정한다.
- 배우기는 주제별 커리큘럼(블로그 글 형식)이며, 각 주제는 질문 하나·예시 하나·'이 예시로 비중
  비교하기' 연결로 구성한다. 진단 화면의 용어 도움말은 같은 설명을 재사용한다.

- 경제환경 지표의 범위는 KDI에서 다루는 자료를 기준으로 하고 실제 값은 ECOS·KOSIS·OECD 등 공식

  개별 통계표·상품의 응답과 과거 범위를 확정된 것으로 쓰지 않는다.
- 장기 원천 전체 적재와 매 사용자 요청마다 전체 데이터 재처리는 하지 않는다.

  동작할 것, (2) 실행은 격리된 환경에서 원칙 IX의 한도 안에서만 할 것, (3) 순위·추천·인기 목록으로
  표시하지 않을 것(원칙 III). 세부는 spec에서 정한다.

- Nautilus를 기준 엔진으로 사용한다.
- 리밸런싱은 정보 확인 후 다음 거래일에 가상 체결한다.
- 공매도·레버리지 없이 정수 수량·잔여 현금·거래 불가·비용을 처리한다.
- 원시 가격은 체결에, 기업행위를 일관되게 반영한 자료는 신호·성과에 사용한다. 분배금과 ETF 내부
  보수를 중복 반영하지 않는다.
- 모든 전략에 비중 상한·현금·추정 불가·실행 불가능한 제약의 처리 규칙을 적용한다. 0 변동성·선정
  대상 없음·추정 실패를 처리한다.
- 대표 ETF의 실제 가격·상장일·분배/분할 자료를 우선 확보한다. 가격과 기업행위 처리가 불명확한
  상품·기간은 분석 범위를 줄인다.
- 과거 구성 이력이 없으면 현재 구성으로 당시 중복·집중도를 재현했다고 주장하지 않는다. 현재 구성
  기준 진단과 과거 운용 결과를 구분한다.
- 후보 중 가장 긴 관측 기간과 최근 제외 구간을 감안한 공통 워밍업을 확보한다.

### 파라미터 후보와 자동 탐색 (§4.2.2, §6.4.2, §6.4.3)

- 전략별로 의미가 있는 설정만 허용하고, 후보 값·범위·간격·유효성 제약·기본값을 실행 전에 등록한다.
- 유효성 제약을 위반하는 조합(모멘텀 선정 수가 가용 섹터 수를 넘는 경우, 상한들의 합계로 투자 비중을
  채울 수 없는 조합)은 계산 전에 제외한다.
- 전략 파라미터·시장 검색 설정·평가 시나리오는 별도 축으로 기록한다.
- 후보 선정은 비용 차감 성과·손실 제약·인접 설정 안정성에 대한 사전 기준을 사용한다.
- 실행 전에 대상 전략·탐색 범위 요약·예상 작업량·적용 한도를 사용자에게 간단히 확인시킨다. 모든 후보
  숫자나 검색 지표 조합을 사용자가 직접 입력하게 하지 않으며 상세 변경은 선택 사항이다.
- 분석 기간은 비교 후보가 공통으로 평가 가능한 범위에서 자동 제시한다. 금액·비용은 '기간·금액·조건'에서
  확인·변경한다.

### 경제환경 검색 (§4.3, §4.4, §6.4.4, D21~D27)

- 분야별 검색은 해당 분야의 실제 입력값과 최근 3개월 경로의 차이로 정렬하고, 종합 비교는 7개 분야
  거리를 같은 비중으로 결합하되 분야별 차이도 함께 보인다. '노동과 건설은 가깝지만 수출은 다릅니다'처럼
  확인된 닮은 점과 차이를 함께 설명한다.
- 시대별 평소 대비 위치는 보조 설명으로만 제공하고 기본 순위와 결합하지 않는다. 움직임 항목의 추가
  가중은 내부 비교 실험이며 사용자 기본값이나 실제 영향 비율로 표시하지 않는다. (D21, D27)
- 분야 내부 동일가중·분야 간 동일가중은 명시적인 Thorp 설계 선택이며 경제적 중요성이 같다는 뜻이
  아니다. 검증 전에 "모든 지표의 중요성이 같다"고 표현하지 않는다. 지표·분야별 명목 비중과 실제 거리
  기여를 기록한다. (D23)
- 종합 사례 안의 분야별 설명은 종합 기준월을 유지하고 분야별 최신 질의값을 섞지 않는다. 분야 안에서도
  더 최신인 개별 발표는 별도 정보로 표시한다. (§4.4, D22)
- 각 사례에는 관측 구간·비슷한 점·다른 점을 먼저 제시하고, 사후 시장·전략 결과는 별도 영역에 연결한다.
  거리·기여도·자료 기준은 상세에서 본다. 현재 시장 상태는 지표의 말로 설명한다.
- 전략 연결 시 보유 섹터·비중, 거래와 비용, 손실 기여를 같은 조건으로 확인하고 전체 기간 결과와 함께
  본다. KOSPI는 순위 확정 후 참고 정보로 붙인다. 기본은 전체 기간 연속 운용 결과의 해당 사후 구간이며,
  그날 현금으로 새로 시작하는 것은 별도 시나리오다. (D25)
- 선택 사례에서 ETF 미상장·워밍업 부족·사후 미완성이면 해당 전략 결과만 제한한다. 사례 부족·사후 자료
  미완성·검색 불안정은 결과 옆에 표시하고 전체 기간 전략 비교를 계속 제공한다. (D26)
- 전략 추가로 가용 범위가 달라지면 알린 뒤 새 검색으로 기록한다. 같은 비교 묶음에서는 같은 후보를
  사용한다.

### 뉴스·거시 데이터 (§4.4, §6.3)

- 뉴스는 제목·매체·발행 시각·짧은 사실 요약·원문 링크를 제공하고, 같은 사건의 중복 보도는 한 묶음으로
  정리한다. 기사 본문은 저장·재배포하지 않는다.
- 1차 필터 순서는 **기간 → 기사 관련성 → 중복 제거 → 필요한 필드 저장**이다. 국내 기사는 선택
  섹터·기업·경제 주제와의 연결을 확인하고, 해외 기사는 국내 섹터와 연결되는 국제 주제로 제한한다. 두
  경로를 합친 뒤 URL 정규화와 사건 묶음을 적용한다.
- 기본 저장 항목은 원문 URL·매체·언어·발행 시각(확인 가능할 때)·수집 시각·관련 섹터/주제·중복
  식별자다.
- 가까운 시점 조회는 필터 가능한 API를 쓰고 호출 간격·재시도·결과 캐시를 관리한다. 배포 파일 수집은
  필요한 날짜·시간 파일만 순차 처리한다.
- 시장 흐름 기본 화면은 분야 이름과 짧은 변화 요약을 보이고, 관심 분야를 열면 개별 지표의 실제
  값·단위·최근 3개월 경로와 '비슷했던 때 보기'를 제공한다. 거시 통계의 최신 개정자료 역사 비교 여부는
  별도로 표시한다.

### 실행·캐시 (§4.2.2, §6.5)

- 캐시 키에 전략·파라미터·섹터/ETF 대응·데이터 마감/버전·평가 분할·비용·엔진·검색 설정을 포함한다.
  동일 버전 조회와 새 계산을 구분한다.
- 후보 실행끼리 병렬화한다.
- '분석하기' 이후 진행·취소·재시도와 동일 결과 재사용을 제공한다. 취소·한도 도달 시 부분 결과임을
  알린다.

### 기록·개인정보·보관 (§5, D14)

- 개인 식별정보는 계산 기록과 분리한다.
- 보관 기간·삭제·연결 해제·공유 후 회수 정책은 spec으로 남기고, 무기한 보관을 전제하지 않는다.
- CSV/JSON 내보내기를 제공한다. 원천 시세·기사의 내보내기는 자료별 이용 범위 안에서만 제공한다.
- 내 기록의 기본 동작은 '다시 보기 / 설정 바꿔 비교'이며, 상세 설정·거래 내역·내보내기는 추가
  메뉴에서 접근한다.

## 검증과 완료 기준

### 기능·계산 확인 (§7.1)

- 탐색·섹터 선택부터 결과 재조회까지의 흐름을 확인한다.
- 대표 거래·현금·비용·분배금·공통 기간을 수기 또는 독립 계산으로 대조한다.
- 경계 사례를 검증한다: 모멘텀의 선정·동점·대상 없음, 최소분산의 제약·추정 불안정·해 없음, 탐색의
  후보 수·제외·취소, 검색의 정규화·시간 정렬.
- 경제환경 검색은 중앙값·산포·대체 척도·지표/분야/종합 거리·기여도 합을 수기 또는 독립 계산으로
  대조한다. 같은 기준월·자료/모델 버전·가용 후보 집합에서 전략을 바꿔도 후보가 같은지, 분야 전환 시
  해당 분야 거리로 정렬되는지, 모드별 기준월·기준월 전환·날짜 중복 제거·자료 부족·ETF 미상장·사후
  미완성·0 척도가 규칙대로 처리되는지 확인한다.
- 동일 버전 재실행이 같은 결과를 내는지 확인한다.
- 평가 경계를 넘는 이후 결과가 개발 자료에서 제거됐는지, 원시 가격·분배금·비용과 거래 내역이
  일치하는지 확인한다.
- 자료 부족·빈 뉴스·수집 지연·계산 실패가 정상 화면 흐름으로 처리되는지 확인한다.

### 사용성 확인 (§7.2, D20)

- 전략을 검증하려는 개인 6~8명에게 섹터 비중 비교 과제를 주어 관찰한다. 필요하면 입문자의 학습 →
  진단 이동도 관찰한다. 이 인원은 오류 발견을 위한 시작 규모이며 수요를 입증하는 표본이 아니다.
- 경제환경 탐색 과제('현재와 고용환경이 가까운 과거를 찾고, 물가에서 다른 점을 설명한 뒤 같은 전략의
  이후 행동을 비교하기')를 추가한다. 종합 비교를 열지 않아도 분야 탐색 과제가 끝나야 한다.
- 확인 질문: 설명 없이 첫 분석을 마칠 수 있는가 / 큰 손실·비용·탐색 성과와 미사용 검증의 차이를
  구분하는가 / 상세 근거를 스스로 찾을 수 있는가 / 분야 유사성을 경제 전체의 일치로 오해하지 않는가 /
  관측 구간과 사후 평가 구간을 구분하는가 / 전체 기간 결과를 함께 보는가.
- 막히는 단계와 불필요한 입력을 관찰한다. 필요하면 개인의 기존 방식과 같은 과제로 비교하고 순서를
  교차해 학습 영향을 살핀다.
- 설문 긍정 응답만으로 출시나 유료 수요를 확정하지 않는다.

### 미확인 항목 처리 (§7.4, §10.1)

- 실제 자료·사용자 관찰 없이 확인할 수 없는 항목(U01~U06)과 자료 가용성·이용 조건의 미확인 항목은
  개발 진행을 막는 조건이 아니다. 확인 전에는 허용된 대체 자료·명시된 예시 자료로 개발하고, 자료
  부족은 해당 결과에만 표시한다.
- 미확인 항목은 실제 결과가 나오면 판정·근거·모델 버전·후속 조치를 기록하고, 확인되면 해당 절로 옮긴다.
  미확인을 실패로 취급하거나 관측하지 않은 효과를 확정하지 않는다.
- 제공받은 외부 PoC 기록은 스크립트를 재실행해 재검증하기 전에는 독립 검증 결과로 승격하지 않는다.

### 완료의 정의 (§2, §9, D01, D17, Jira Convention §5)

**작업(Task) 단위**의 완료는 Jira Convention이 정한 아래 다섯 조건을 모두 충족할 때다. 하나라도 빠지면
완료로 바꾸지 않는다.

1. 기능 구현 완료
2. 테스트 또는 동작 확인 완료
3. 코드 리뷰 완료
4. Merge Request 병합 완료
5. 필요한 문서 수정 완료

**기능 단위**의 완료는 아래 세 가지를 구분해 보고하며, 하나를 다른 것의 증거로 쓰지 않는다.

1. **구현 완료**: 기능·계산 확인(위 §7.1 항목)을 통과했다.
2. **사용성 확인**: 사용성 관찰을 수행하고 발견한 막힘을 요약 화면·입력에 반영했다.
3. **효과 입증(선택 성과 검증)**: 원칙 VII의 절차를 통과했다. 통과하지 못해도 기능을 되돌리지 않고
   결과에 '미검증·개선 근거 없음·판단 보류'를 표시한다.

- 고정 파라미터의 계산 성공을 자동 탐색·추천 효과의 증거로 확대하지 않는다. 모델 v1 명세 완료를 코드
  구현이나 효과 입증으로 표현하지 않는다. (D17)
- 조건 2의 "테스트"가 어떤 명령·범위를 뜻하는지(lint·build·테스트 스위트)는 아직 합의되지 않았다.
  아래 "넣지 않은 영역"을 본다.

## Git·Jira 규칙

### Git (Git Convention, 문서상태 동결)

- 매주 금요일 버전 릴리즈를 진행한다.
- 브랜치 이름은 `{type}({position})/{JIRA_NUMBER}-{description}`이다. type은 `feat` `fix` `refactor`
  `chore` `docs` 중 하나, position은 `fe` `be` `infra` `ai` `de` 중 하나다. 예: `feat(be)/12-kakao-oauth`.
  JIRA_NUMBER는 팀 이름을 제외한 이슈 번호만 쓴다. 여기서 `de` 는 데이터엔지니어링이다.
- 커밋 메시지는 `feat(be): 작업 내역 요약` 형식이며 커밋 설명은 선택이다. 커밋으로 Jira 상태를 바꾸려면
  공백 등 사소한 변경을 한 뒤 `feat(be): 작업 내역 요약/ {지라티켓}` 형식으로 한 번 더 커밋한다.
- MR 제목은 커밋 메시지와 같은 `type(position): 작업 내역 요약` 형식이다. 예: `feat(be): 배우기 글과 용어
  설명을 보관하고 공개 조회한다`. Jira Task 요약의 `[BE]` 같은 분야 표기를 MR 제목에 쓰지 않는다. (초안, 3.5.0)
- MR 본문은 아래 다섯 절을 이 순서로 채운다: **작업 내용 요약 / 관련 티켓(`ticket #`, `link`) /
  주요 변경 사항 / 테스트(체크박스) / 리뷰 포인트**.
- **MR 본문은 핵심부터 짧게 쓴다.** (초안, 3.5.0)
  - 작업 내용 요약은 세 문장 이내로 이 MR이 병합되면 무엇이 달라지는지를 쓴다.
  - 주요 변경 사항은 동작·계약·스키마 단위로 쓴다. 파일·클래스 목록은 옮기지 않는다(diff가 보여준다).
  - 테스트는 실행한 명령과 결과(실패·건너뛴 수), 그리고 자동 테스트로 확인되지 않는 확인만 쓴다.
    테스트 이름과 건수를 나열하지 않는다.
  - 리뷰 포인트는 리뷰어가 판단하거나 팀이 합의해야 할 것만 쓴다.
  - 작업 과정(다시 한 시도, 검사를 돌린 횟수, 바로잡은 이력)은 쓰지 않는다. 필요하면 커밋 메시지에 남긴다.

  왜: 본문이 길면 판단할 거리가 나열에 묻혀 리뷰가 형식으로 끝난다.
- **티켓과 MR은 담는 것이 다르다.** 티켓에는 무엇을 왜 하는지와 완료 기준만 둔다. 어떻게 했는지,
  왜 그렇게 판단했는지, 다른 선택지를 왜 버렸는지, 리뷰어가 주의할 점은 MR 본문에 쓴다.
  티켓 하나를 읽고 그 MR을 읽으면 맥락이 이어져야 한다.

왜: 사람과 AI가 만든 브랜치·커밋·MR이 같은 모양이어야 이슈 추적과 리뷰가 끊기지 않는다.

### Jira 연계 (Jira Convention, 문서상태 동결)

이 문서에는 작업의 정의·연결·완료에 직접 영향을 주는 규칙만 담는다. 스토리 포인트 산정, 스프린트
배치, 담당자 지정 세부는 Jira Convention 문서를 따른다.

이슈 추적은 Jira에서만 한다. GitLab 이슈는 쓰지 않으므로 MR 본문의 `ticket #`은 Jira Task 번호다.

- 이슈 구조는 Epic → Story → Task의 3단계다. Sub-task는 사용하지 않는다. Task는 Epic에 연결하고
  구현 대상 Story와 `relates to`로 연결한다.
- Story 요약은 `[대상]은 (목적)하기 위하여 (활동/작업/기능)할 수 있다` 형식이며 구현 방법이나 기술
  내용은 쓰지 않는다. 하나의 Story에는 가능한 한 하나의 유스케이스만 담는다.
- Task 요약은 `[분야] 작업 내용` 형식이며 분야 표기는 BE / FE / AI / DE / INFRA / DOCS 중 하나를 대괄호로
  감싼다. 범위가 불명확하거나 큰 제목(예: "화면 개발")은 쓰지 않고 여러 Task로 나눈다.

  ```plain text
  [BE] 백테스트 요청 API 구현
  ```

- **1 Plan = 1 Spec**이다. plan은 spec 하나를 구현하는 전체 범위를 다루며, 그 안에 여러 Jira Task·
  Branch·MR이 포함될 수 있다.
- **작업 묶음(work batch) = 1 Branch = 1 MR**이다. plan 하나에서 생성된 tasks가 많을 때, 개발자는
  서로 연관된 여러 task를 하나의 묶음으로 모아 브랜치 하나와 MR 하나로 처리한다. task 하나를 반드시
  브랜치 하나로 나눌 필요는 없고, 반대로 서로 무관한 task를 편의로 한 묶음에 넣지도 않는다.
- 묶음은 아래 세 조건을 모두 만족하는 크기로 정한다. 하나라도 어기면 묶음을 더 쪼갠다.
  1. 묶음 안의 task들이 하나의 목적(같은 계층·같은 기능 흐름·같은 배포 단위)을 공유한다.
  2. 묶음 전체를 독립적으로 구현·검증·리뷰할 수 있고, 되돌릴 때 다른 묶음을 건드리지 않는다.
  3. 리뷰어가 한 번에 읽을 수 있는 변경 범위이며, 묶음 안에 미완성 상태로 남는 task가 없다.
- 각 묶음은 Jira Task 하나에 대응시킨다. 묶음에 연결할 Jira Task가 없으면 **그 묶음의 Branch·MR을
  만들기 전에** Jira Convention의 제목·연결 규칙을 따른 Task를 먼저 생성하고, 그 Ticket 번호로
  브랜치를 만든다. tasks.md의 개별 task 번호는 MR 본문의 "주요 변경 사항"에 나열해 추적한다.
- 묶음 구성은 plan을 시작할 때 정하고, 구현 도중 범위가 달라지면 그 사유와 새 묶음 구성을 plan 또는
  MR 본문에 남긴다.
- Task를 진행 중으로 바꾸기 전에 담당자·스프린트·Epic 연결·Story 연결·스토리 포인트·브랜치를
  확인한다. Task의 완료 조건은 위 "완료의 정의"의 다섯 조건이다.

왜: spec은 사용자 가치와 범위를 정하고, plan은 그 spec을 구현하는 전체 계획을 정한다. speckit이 만드는
task는 실행 지시의 최소 단위라서 그 하나하나를 브랜치와 MR로 나누면 리뷰가 잘게 부서지고 이슈 관리
비용만 늘어난다. 그래서 추적 단위는 task가 아니라 독립적으로 검증·롤백할 수 있는 작업 묶음으로 둔다.

## 스키마 변경 규칙

데이터베이스 스키마를 바꾸는 모든 작업에 적용한다. 도구·파일명 형식·명령은 기술 스택에 속하므로 여기서
정하지 않고 파트 문서에 둔다.

- **운영에 이미 적용된 스키마 변경은 수정하지 않는다.** 고칠 일이 생기면 새 변경을 덧붙인다. 어떤 운영
  환경에도 아직 적용되지 않은 변경은 병합 전후를 가리지 않고 수정·정리할 수 있다.

  왜: 적용 기록과 변경 내용이 어긋나면 그 다음 배포가 모두 막힌다. 반대로 아직 적용되지 않은 변경까지
  동결하면, 되돌릴 수 있는 실수 하나가 영구 기록으로 남는다.

- **스키마 변경·코드 매핑·검증은 같은 MR에 담는다.** 셋 중 일부만 병합하지 않는다.

  왜: 운영은 코드와 스키마가 일치할 때만 기동한다. 한쪽만 먼저 병합되면 그 시점부터 배포가 실패하는데,
  실패를 만든 변경이 방금 병합한 MR이 아니라 이전 MR에 있어 원인을 찾기 어렵다.

- **되돌릴 수 없는 변경은 배포 전에 백업과 팀 승인을 받는다.** 데이터를 지우거나 기존 값을 무효로 만드는
  변경(테이블·컬럼 삭제, 전체 삭제, 타입 변경, 기존 행이 위반하게 되는 제약 추가)은 MR 본문에 그 사실과
  영향 범위를 적는다. 운영 데이터베이스를 초기화하는 명령은 쓰지 않는다.

  왜: 배포를 되돌려도 지워진 데이터는 돌아오지 않는다. 비어 있는 데이터베이스에서는 이런 변경이 모두
  통과하므로 자동 검증만으로는 걸러지지 않는다.

- **적용 기록을 사람이 직접 고치는 복구 수단은 원인을 확인한 뒤에만 쓴다.** 쓸 수 있는 사람을 미리 정해
  두고, 사용한 경우 원인과 조치를 MR 또는 이슈에 남긴다.

  왜: 기록만 맞춰 증상을 없애면, 스키마와 기록이 어긋난 상태 그대로 다음 배포가 진행된다.

- **병합해도 되는지는 사람의 확인이 아니라 자동 검증으로 판정한다.** 검증은 병합될 결과를 대상으로
  실행하고, 실행되지 않은 상태(환경이 없어 건너뛴 경우를 포함한다)를 통과로 보지 않는다.

  왜: 각 변경이 자기 브랜치에서 따로 통과해도, 합쳐진 결과는 아무도 실행해 보지 않은 채 배포될 수 있다.
  건너뛴 검증을 통과로 세면 검증이 비어 있다는 사실 자체가 드러나지 않는다.

## 문서 역할과 AI 작업 방식

### 문서 역할 (가이드 1·5, §9)

- **기획서(Notion)**: 제품 방향, 결정 D01~D27, 검증 항목 U01~U06, 실행 전 결정 항목의 근거 문서다.
  개발 명세이지 구현 완료나 효과 입증 보고가 아니다.
- **Git Convention·Jira Convention(Notion, 동결)**: 브랜치·커밋·MR·이슈 규칙의 원본이다. 이 문서는 그중
  작업 정의·완료에 필요한 부분만 옮겨 적었다.
- **constitution(이 문서)**: 프로젝트 내내 유지되는 원칙. `.specify/memory/constitution.md`에 둔다.
- **spec**: 이번 범위·우선순위와 "실행 전 결정 항목"의 확정값. 사용자 스토리는 Jira Story 문장 형식으로
  쓰고, 기획 근거를 인용할 때 D번호·U번호를 쓴다.
- **plan / tasks**: plan은 **spec 하나의 구현 계획**이고, tasks는 개발자가 그 plan 안에서 적절한 크기로
  나눈 실행 단위다. 작업 단위는 독립 구현·검증·리뷰가 가능하고 변경 범위·의존성·롤백 위험이 관리되는
  크기여야 한다. 여러 task는 위 "작업 묶음" 규칙에 따라 묶음으로 모으고, 묶음마다 Jira Task 제목
  형식을 지킨 Task 하나와 브랜치 하나, MR 하나를 대응시킨다. plan의 Constitution Check는 이 문서를
  기준으로 판정한다.

### AI 작업 방식 (§6.3, §6.4.2, §7.4, §9, §10.1에서 도출)

- 기획서가 "실행 전 결정"으로 남긴 수치·규칙을 임의로 확정하지 않는다. spec에 결정 항목으로 표시하고
  팀 확정을 기다린다. 모델 v1 기본값은 기획서가 확정한 값을 그대로 쓰고, 바꾸려면 새 모델 버전으로
  제안한다.
- "하지 않는 것" 목록의 기능을 제안하거나 구현하지 않는다.
- 확인할 수 없는 사실(데이터 포괄성, 경쟁 우위, 성과 향상률, 미확인 API 응답)을 확인된 것처럼
  문서·화면에 쓰지 않는다. 확인한 범위와 확인하지 못한 범위를 함께 적는다.
- 구현 완료를 효과 입증으로, 명세 완료를 구현 완료로 보고하지 않는다.
- 브랜치·커밋·MR·Task·plan을 만들 때 위 Git·Jira 규칙의 형식을 따른다. plan은 시작 전에 대상 spec과
  구현 범위를 정하고, 개발자는 plan 안의 task들을 작업 묶음으로 모은다. 각 묶음의 Ticket이 없으면
  Task를 먼저 만들고, 그 Ticket·브랜치·MR로 해당 묶음을 추적한다.

### 합의되지 않아 이 판에 넣지 않은 영역 (가이드 2·4)

아래 영역은 기획서·Git Convention·Jira Convention에 합의 내용이 없어 규칙을 두지 않았다. "규칙이
없다"는 뜻이지 "무엇이든 된다"는 뜻이 아니다. 이 영역에서 내린 선택은 plan·MR에 근거를 남기고,
반복되는 선택은 팀 합의를 거쳐 MINOR 개정으로 이 문서에 추가한다.

- 기술 스택의 언어·프레임워크·DB·브로커와 버전, 신규 라이브러리 추가 절차
- 모듈·계층·폴더 구조와 복잡도 한도
- 네이밍, DTO/Entity 구분, 예외 처리, 로깅 형식
- API의 URI·Method·status code·응답 포맷·하위 호환 정책
- DB 명명·PK/FK·nullable, 적용된 스키마 변경을 되돌리는 절차, 배포 중 이전 버전 코드와 새 스키마가
  함께 도는 구간의 호환 규칙 (스키마 변경 자체의 협업 규칙은 "스키마 변경 규칙" 절로 옮겼다)
- 입력 검증 방식, 인증/인가, 시크릿 관리 도구
- 테스트 범위, lint/build 통과 기준 (Task 완료 조건 2 "테스트 또는 동작 확인"의 구체 명령)
- MR merge 방식(squash 여부)과 승인 인원
- AI가 수정할 수 있는 파일과 금지 영역, plan 승인 게이트, clarify 사용 규칙
- ADR·README·API 문서 갱신 기준
- spec 변경 시 plan/tasks/code 갱신 절차

## Governance

- 이 문서는 `.specify/memory/constitution.md`에 두고 `/speckit-constitution`으로 작성·갱신한다.
  (가이드 1)
- **개정 절차**: `/speckit-constitution` 재실행으로 초안 작성 → 팀 MR → 전체 회의 승인 → merge.
  개정마다 버전(SemVer)과 Last Amended를 갱신하고 상단 Sync Impact Report를 갱신한다. 승인 없이
  merge된 개정은 무효다. (가이드 6)
- **버전**: MAJOR = 원칙 삭제·재정의(하위 비호환), MINOR = 원칙·섹션 추가 또는 실질적 확대,
  PATCH = 문구·오타·명확화.
- **규칙 자격**: 팀이 합의했고, 위반 여부를 판정할 수 있는 문장이며, 가능하면 '왜'가 있다. 템플릿
  빈칸을 채우기 위해 규칙을 만들지 않는다. 스프린트마다 바뀌는 것은 spec에 쓴다. (가이드 2·3·5·7)
- **반복 위반**: plan·implement 단계에서 같은 규칙이 반복 위반되면 강제하지 않고 개정을 검토한다.
  비현실적이거나 합의되지 않은 규칙은 두지 않는다. (가이드 4)
- **우선순위**: 이 문서와 spec·plan·코드가 충돌하면 이 문서를 따르거나, 이 문서를 먼저 개정한다.
  모든 MR 리뷰와 plan의 Constitution Check에서 이 문서 위반을 점검한다.
- **근거 자료 변경**: 기획서의 "확정한 방향"이나 Git·Jira Convention이 바뀌면 이 문서를 같은 절차로
  개정한다. 근거 문서끼리 어긋나면(예: 브랜치 형식) 더 최신인 동결 문서를 따르고 팀에 알린다.
