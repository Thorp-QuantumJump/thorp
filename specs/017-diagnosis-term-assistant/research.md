# Research: 진단 화면 용어 도우미

spec 017의 설계 판단 기록이다. 각 항목은 결정 / 근거 / 버린 대안 순서다. 015에서 이미 정한 것(모델·게이트웨이·응답 스키마·데드라인)은 다시 다루지 않는다.

## R1. 근거를 싣는 방식 — 처음 팩 + 닫힌 목록의 읽기 도구

- **결정**: 015와 같은 "처음 팩 + 모델이 요청하면 서버가 읽어 더함" 구조를 쓴다.
  - 처음 팩: 게시된 용어 설명 전부(용어마다 근거 1개)와 화면 종류별 짧은 설명. '전략 선택'은 활성 전략마다 이름·설명 1개씩, '투자 대상 고르기'는 섹터 목록 1개를 싣는다.
  - 도구 셋: `readArticle(articleId)`, `readStrategy(strategyId)`, `readSectorList()`. 두 화면 모두 셋을 다 받는다(Clarifications Q2).
- **근거**: 지금 콘텐츠 크기에서 처음 팩은 용어 14개와 전략 5개라 60개 상한 안에 든다. 글 본문(한 글 최대 60블록)과 설정 항목 설명(전략당 3~8개 축)은 질문에 따라 필요한 부분이 달라 도구로 읽는 것이 맞다. 015의 `ToolLoop`·`FactPack`·라운드 상한을 그대로 쓴다.
- **버린 대안**:
  - 모든 콘텐츠를 처음 팩에 넣는다: 글 9개를 다 실으면 60개를 넘고, 콘텐츠가 늘 때마다 깨진다.
  - 벡터 검색으로 관련 문단을 고른다: 015·017 Out of Scope다. ADR-0008 D1에 따라 벡터 DB를 두지 않는다.
  - 서버가 질문에서 용어를 뽑아 미리 읽는다: 015 plan에서 버린 "두 번째 분류기"와 같은 문제다.

## R2. 도구 인자 — 날짜 대신 닫힌 열거값

- **결정**: `ToolSpec`의 인자를 "날짜" 하나에서 **날짜 또는 열거값**으로 넓힌다.
  - 열거값은 요청 시점에 서버가 만든 닫힌 집합이다. 게시된 글의 `articleId`, 활성 전략의 `strategyId`가 해당한다.
  - 모델에는 strict JSON Schema `enum`으로 보인다.
  - `ToolLoop.checkArguments`는 값이 그 집합 안에 있는지 검사한다.
  - 015의 결과 도구 다섯 개는 날짜 인자 그대로라 동작이 바뀌지 않는다.
- **근거**:
  - 015가 식별자 인자를 막은 이유는 공개 토큰·`backtestId`로 **다른 사람의 결과**를 읽는 경로를 없애는 것이었다.
  - `articleId`·`strategyId`는 공개 콘텐츠의 고정 키이고 이미 공개 URL·API에 나온다. 그래서 그 위험이 없다(spec FR-005).
  - 닫힌 집합이라 프롬프트 인젝션으로 초안이나 다른 경로를 읽을 수 없다. 초안 글은 집합에 없다.
- **버린 대안**:
  - 자유 문자열 인자 + 서버 검색: 검증 경계가 흐려진다.
  - 이름(한국어 표시 이름)을 인자로 쓰기: 운영자가 제목을 고치면 깨진다(013 Clarifications와 같은 이유).

## R3. 숫자 규칙 — 인용 근거 원문에 같은 표기로 있는 숫자만

- **결정**: 화면 종류에 따라 검증 정책을 둘로 나눈다.
  - `RESULT`: 015 그대로다. 자리표시자 밖의 숫자를 모두 거절한다.
  - 용어 종류(`SECTOR_SELECTION`·`STRATEGY_SETTINGS`): 자리표시자를 뺀 나머지에서 **숫자 토큰**을 뽑는다. 숫자 토큰은 정규식 `[0-9０-９][0-9０-９.,]*\s*(%|％|원|일|개월|년|거래일|개)?`에 맞는 덩어리다. 각 토큰이 그 part의 `factIds` 근거 `value` 가운데 하나에 **부분 문자열로** 들어 있어야 한다. 비교 전에 전각 숫자를 반각으로 바꾼다.
  - URL·경로·통화 기호(`₩`·`$`)는 두 정책 모두 거절한다.
- **근거**: Clarifications Q1. 설정 항목 설명의 허용 범위·기본값("20거래일", "최대 40%")과 ETF 이름의 숫자("KODEX 200")를 풀어 쓸 수 있어야 한다. 단위를 토큰에 붙여 비교하므로 "20일"을 "20%"로 바꿔 쓰는 오류도 걸린다.
- **버린 대안**:
  - 숫자만 비교(단위 무시): "20거래일"과 "20%"를 구분하지 못한다.
  - 모든 근거 원문 대상: part가 가리키지 않는 근거의 숫자를 빌려 쓰는 것을 막지 못한다.

## R4. 자리표시자와 `factIds`의 관계

- **결정**: 용어 종류에서는 "자리표시자 집합 ⊆ `factIds`, `factIds` 비어 있지 않음"으로 완화한다. 015는 두 집합이 같아야 한다.
- **근거**:
  - 용어 답은 근거 문장을 풀어 쓰므로, 자리표시자 없이 근거를 가리키기만 하는 part가 정상이다.
  - 근거 문장을 통째로 인용하고 싶으면 `{{Fn}}`도 쓸 수 있다.
  - `factIds`가 없는 `ANSWERED` part는 여전히 거절한다. 근거 없는 문장을 막는 마지막 기계 검사가 이것이기 때문이다.
- **버린 대안**:
  - 015 규칙을 그대로 쓰기: 모든 문장에 자리표시자를 넣어야 해서, 근거 문장을 통째로 붙이는 어색한 답이 된다.

## R5. 한도 키

- **결정**:
  - `admit(ip, scopeKey)`로 바꾼다. `RESULT`는 `token:{publicToken}`을 그대로 쓰고, 용어 종류는 `page:{kind}:{ip}`를 쓴다.
  - 새 설정 `thorp.assistant.limits.per-page-per-ip-per-minute`(초안 5)를 둔다.
  - IP 분당(8)과 하루 전체(1000)는 모든 종류가 함께 쓴다(spec FR-011).
- **근거**:
  - 토큰이 없는 화면에서 IP 한 키만 쓰면, 한 사용자가 결과 화면과 진단 화면에서 같은 몫을 나눠 쓴다.
  - 화면 종류 키를 두면 015와 같은 두 겹 구조가 유지된다.
  - 하루 전체를 하나로 두는 것은 외부 호출 총량을 한 값으로 통제하기 위해서다.
- 인스턴스 메모리 한계(`// ponytail:`)는 015와 같다.

## R6. 프롬프트 — 화면 종류별 파일

- **결정**:
  - `assistant/prompts/term-ko.txt`를 새로 둔다. 015 `answer-ko.txt`는 바꾸지 않는다.
  - 모델 어댑터는 `Conversation`에 실린 `PageKind`로 프롬프트를 고른다. 진단 두 종류는 같은 파일을 쓴다.
  - 프롬프트에 넣는 규칙:
    - 근거 밖 지식 금지
    - 근거 문장 풀어 쓰기 허용
    - 숫자는 근거 표기 그대로
    - 고르기·성과·최적값·미래 판단 금지
    - 결과 값 질문은 `OUT_OF_SCOPE`
    - 동의어 맞추기("MDD" ↔ "가장 크게 줄었던 폭")는 근거가 있을 때만
- **근거**: 결과 프롬프트는 결과 도구·부분 결과 규칙이 대부분이라, 한 파일에 분기를 넣으면 두 화면 모두 품질 관문을 다시 봐야 한다. 파일을 나누면 015 관문 결과(평가 문서)가 그대로 유효하다.
- **버린 대안**:
  - 한 프롬프트에 화면 종류를 변수로 넣기: 015 평가가 무효가 된다.

## R7. 글 연결 — 응답에 `relatedArticles`

- **결정**:
  - `Evidence`에 선택 필드 `source{type, articleId, articleTitle}`를 더한다.
  - 응답에 `relatedArticles[{articleId, title}]`를 더한다. 쓰인 근거 가운데 `articleId`가 있는 것을 중복 없이, 처음 쓰인 순서로 담는다.
  - `RESULT`와 용어 종류의 `ANSWERED` 아닌 답은 빈 배열이다.
- **근거**:
  - spec FR-010이다. 화면이 근거 목록을 해석해 링크를 만들면, 근거 카드를 그리지 않는 015 결정과 섞인다.
  - 필드를 더하기만 하므로 015 응답을 쓰는 화면은 영향받지 않는다.
- **버린 대안**:
  - 답 문장 안에 링크 넣기: 검증기가 URL을 거절하고, 화면에서 라우터 이동이 아니라 전체 새로고침이 된다.

## R8. 게시된 용어 전체 조회

- **결정**:
  - 013 `PublishedTermRepository`에 `findAllPublished()`를 더하고, `LearningQueryService`에 `listPublishedTerms()`를 더한다.
  - 조건은 `findPublished`와 같다. 글이 `PUBLISHED`이고 색인 행의 판이 글의 게시 판과 같아야 한다. 정렬은 글 읽는 순서 다음 용어 키다.
  - 공개 HTTP 경로는 더하지 않는다. 화면이 목록을 쓸 일이 없다.
- **근거**:
  - spec Dependencies다. 용어 하나씩 14번 조회하면 요청마다 쿼리가 늘고, 무엇이 게시돼 있는지 알 길도 없다.
  - 013 색인이 "진단 화면 도움말이 읽는 유일한 원천"이라는 규칙을 지킨다. 초안 저장소 `LearningTermRepository`는 읽지 않는다.
- 글 본문은 기존 `getPublished(articleId)`를 쓴다. 요청마다 읽고 캐시하지 않는다(spec FR-004).

## R9. 근거에서 빼는 것

- **결정**: 다음은 근거로 옮기지 않는다.
  - 글의 `hypothetical` 블록, `example`(예시 섹터·비중), `sources`
  - 001 상품 상세(`indexMethodologySummary` 등)
  - 등록표의 숫자 범위 필드(`range`·`unit`)
  - 화면 하드코딩 문구
- **근거**:
  - 가상 숫자와 예시 비중이 실제 값처럼 읽힐 위험을 1차에서 지지 않는다(spec Edge Cases).
  - 범위 필드는 원문 문자열이 아니라 구조값이다. 그래서 설명 문장(`description`)에 들어 있는 범위만 인용할 수 있다. 이렇게 해야 R3의 "원문에 있는 숫자" 규칙이 명확해진다.
- **결과**: 등록표 설명에 범위가 없는 항목은 범위 질문에 근거 부족으로 답한다. 평가에서 이런 경우가 많으면 등록표 설명을 보강하는 것이 처방이다(003 소유).

## R10. 크기 추정

- 처음 팩 크기는 다음과 같다. 근거 상한 60개 안이다.
  - 게시 용어 설명: 최대 14개(문장 300자 이하)
  - 전략 설명: 5개
  - 섹터 목록: 1개
  - 합계: 약 20개
- 용어가 늘어 40개를 넘으면 그 화면에 가까운 것부터 싣는다(`STRATEGY_SETTINGS`는 등록표 `termId`에 걸린 용어 우선). 나머지는 "일부 용어 설명은 싣지 않음" 근거로 표시하고 `readArticle`로 닿게 한다.
- 프롬프트 토큰은 015 결과 팩과 같은 수준(수천 토큰)으로 추정한다. 실측은 평가 문서(SC-005)에 남긴다.

## R11. 화면 배치 확인 항목

- 플로팅 버튼은 015 `App` 마운트를 그대로 쓴다. 두 화면의 CSS에는 `position: sticky/fixed` 하단 막대가 없다.
- 다만 '전략 선택'의 주 행동 버튼과 좁은 화면 우측 하단 고정 버튼이 겹치는지는 구현 묶음에서 화면으로 확인한다(quickstart §3). 겹치면 015 FR-002의 세로 위치 규칙 안에서 기본 위치만 바꾼다.
