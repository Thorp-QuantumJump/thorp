# Phase 0 Research: 설정 조합 자동 비교

**Date**: 2026-09-10 | **Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md)

Technical Context의 NEEDS CLARIFICATION 5건을 해소한다. 기획서가 "실행 전 결정"으로 남긴 수치는
여기서 확정하지 않는다(constitution "AI 작업 방식"). 확정이 필요한 항목은 팀 확정 대기로 남기고,
그 값 없이도 구현·검증이 진행되는 경로를 정한다.

## R1. 파라미터 등록표의 원천 (PD-02, spec 003 미구현)

**Decision**: `ParameterRegistryPort`를 007 안에 정의하고, 003이 완성되기 전까지 임시 구현체
(`FixedParameterRegistry`)를 둔다. 등록표는 `축 이름 → 후보 값 목록 + 유효성 제약`이며 007은
포트만 의존한다. 임시 구현임은 API 응답(`registryVersion: "PROVISIONAL-*"`)과 화면에 표시한다.

**Rationale**: 탐색 공간의 원천은 003이 소유한다(FR-002). 003을 기다리면 007의 오케스트레이션
전체가 멈추는데, 그 오케스트레이션(그리드 전개·유효성 제외·창 방식 발행·집계·선정·기록)은 등록표의
실제 값과 무관하다. 포트로 끊으면 003 완성 시 구현체 교체 한 번으로 붙는다. 임시값 표시는
FR-005a가 이미 요구한다.

**Alternatives considered**:
- 003 완성까지 007 착수 보류 — 병렬 개발을 막는다(specs/README "우선순위는 병렬 개발을 막지 않는다").
- 등록표를 007이 소유 — spec 003과 소유권이 충돌하고 같은 규칙이 두 곳에 생긴다.

### R1 개정 (2026-09-11, spec FR-025·FR-027)

**무엇이 바뀌었나**: 초판의 임시 구현체 `FixedParameterRegistry`는 축과 후보값을 **Java 코드 상수**로
뒀다. spec이 "007 운영 코드에 전략 목록 상수·전략별 파라미터값을 두지 않는다"(FR-025)를 요구하게
되었으므로 그 구현은 규칙 위반이다.

**Decision**: 임시 구현체를 `ProvisionalFileParameterRegistry`로 바꾼다. 등록표 데이터는
`backend/src/main/resources/registry/parameter-registry-provisional.yml` 한 파일에 두고, 로더는
전략별 해석 없이 파일 구조만 읽는다. 포트 반환형도 spec이 요구하는 항목을 모두 담도록 넓힌다 —
활성 전략 목록, 전략명·표시 정보, 축별 **입력 허용 범위**와 **기본 시작값**, **자동 탐색 후보값**,
단위, 전략별 유효성 규칙 호출(계약은
[contracts/param-search-internal.md](contracts/param-search-internal.md) §1).

**Rationale**: 값이 자원 파일에 있으면 003이 완성될 때 로더 대신 003 구현체로 바꾸기만 하면 되고,
그 전까지도 007 운영 코드에는 전략 이름이 한 번도 나타나지 않는다. 자원 파일은 003 등록표의
대역(stand-in)이며 007이 소유권을 주장하는 값이 아니다 — `version()`이 `PROVISIONAL-*`를 돌려주는
것으로 그 사실을 계속 표시한다.

**Alternatives considered**:
- 코드 상수 유지 + "예외적 허용" 문구 — FR-025를 문서로 무력화한다. 거부.
- 임시 등록표를 DB 테이블로 — 003이 소유할 스키마를 007이 먼저 만들어 소유권이 뒤집힌다. 거부.
- 등록표 없이 007 착수 보류 — R1 초판과 같은 이유로 거부.

## R8. 실행 지원 전략의 원천 (2026-09-11, spec FR-026)

**Decision**: `StrategyExecutionSupportPort`를 007 안에 정의하고 `backtest`(004) 모듈의 구현체가
지원 전략 목록을 돌려준다. 탐색 대상은 **003 등록표의 활성 전략 ∩ 004 지원 전략**이며, 어느 한쪽에
없으면 조합 생성 전에 거부한다(`STRATEGY_NOT_REGISTERED` / `STRATEGY_NOT_EXECUTABLE`).

**Rationale**: 전략 목록은 003의 사실이고 실행 가능 여부는 004의 사실이다. 한쪽이 다른 쪽을 대신
선언하면 같은 사실이 두 문서에 갈라진다. 007이 자체 목록으로 판정하면 FR-025 위반이다. 004가 워커에
전략을 추가할 때 지원 목록만 늘어나면 007은 코드 변경 없이 그 전략을 얻는다.

**거부를 조합 생성 앞에 두는 이유**: 미지원 전략을 그대로 발행하면 후보 전량이 `FAILED`로 끝나
"제약 위반·실행 불가"와 "낮은 수익"의 구분이 흐려진다(원칙 VI, FR-011). 실행 자원도 버린다.

**Alternatives considered**:
- 003 등록표에 실행 지원 표시를 넣는다 — 003이 004의 능력을 선언하게 되어 소유권이 섞인다. 거부
  (2026-09-11 spec Clarifications에서 같은 이유로 기각).
- 004 발행 결과의 오류 코드로 사후 판정 — 위 "거부를 앞에 두는 이유"와 충돌. 거부.

## R9. 등록표 버전 드리프트와 조회 실패 (2026-09-11, spec FR-028)

**Decision**: 등록표 버전은 **실행 접수 시점**에 고정한다. 미리보기 응답의 `registryVersion`을
실행 요청이 되돌려 보내고, 접수 시점 버전과 다르면 `409 REGISTRY_VERSION_CHANGED`로 거부하며 다시
조회한 요약을 화면이 보여 확인을 받는다. 등록 정보·지원 목록 조회가 실패하면
`503 REGISTRY_UNAVAILABLE`로 거부하고 캐시·내부 기본값으로 대체하지 않는다.

**Rationale**: 미리보기에서 본 조합 수·유효 후보 수와 실제 실행된 후보 집합이 다르면 재현 기록이
거짓이 된다(원칙 VIII). 버전을 요청에 담으면 낙관적 검사 한 번으로 그 불일치를 접수 단계에서
드러낼 수 있다. 대체값 실행을 막는 이유는 원칙 VI다 — 없는 등록 정보를 추정해 채우면 그 묶음의
참조 버전이 뜻을 잃는다.

**저장 여부의 구분**: 미등록·실행 미지원·상한 초과·유효 조합 0건은 사용자의 선택이 남긴 결과이므로
묶음을 `REJECTED`로 **저장**한다(FR-020). 조회 실패는 일시적 인프라 장애이므로 저장하지 않고 503만
돌려준다 — `BROKER_UNAVAILABLE`을 묶음으로 남기지 않는 것과 같은 기준이다.

**Alternatives considered**:
- 접수 시점에 조용히 최신 버전으로 다시 계산 — 사용자가 확인한 작업량과 다른 것을 실행한다. 거부.
- 미리보기 결과를 서버가 캐시해 토큰으로 재사용 — 상태를 늘리고, 캐시가 낡으면 같은 문제가 다시
  생긴다. 버전 비교로 충분하다. 거부.

## R2. 실행시간 상한·동시성 상한·중단 규칙 (PD-05 잔여, 팀 확정 대기)

**Decision**: 값을 확정하지 않는다. 대신 **값과 무관하게 동작하는 구조**를 만든다.

- 동시성은 "묶음이 한 번에 큐에 올려둔 미완료 후보 수"(발행 창)로 구현한다. 창 크기를 설정값으로
  두고 기본값은 워커 수와 무관하게 동작한다.
- 실행시간 상한은 묶음 시작 시각 기준 경과 시간으로 판정하고, 값은 설정으로 뺀다.
- 중단 규칙은 "한도 도달 시 발행을 멈추고 실행 중 후보는 완주시킨다"로 고정한다. 이는 값이 아니라
  구조 선택이며, prefetch 1 + manual ACK 구조에서 이미 큐에 든 메시지를 회수할 수 없다는 제약에서
  나온다.

**Rationale**: 원칙 IX는 "상한을 정하기 전에 무제한 탐색을 열지 않는다"를 요구하는데 후보 수 상한
(120, 임시)이 이미 그 조건을 만족한다. 실행시간·동시성은 실측(PD-06) 전에는 근거 있는 값을 낼 수
없고, 구조가 설정값을 받게 만들면 실측 후 코드 변경 없이 고정할 수 있다.

**발행 창이 핵심 설계 선택인 이유**: 접수 시점에 후보 전량(상한 120건)을 모두 큐에 넣으면 (1) 한 묶음이
`backtest.jobs`를 독점해 다른 사용자의 단일 실행이 뒤에 밀리고, (2) 취소가 의미를 잃는다 — 이미
큐에 든 메시지는 회수할 수 없어 취소 후에도 계속 계산된다. 창 방식은 두 문제를 동시에 없애고,
취소·한도 도달을 "다음 후보를 발행하지 않는다"는 단순한 동작으로 만든다(FR-009).

**Alternatives considered**:
- 접수 시 전량 발행 + 워커가 취소 여부 조회 — 워커에 상태 조회 의존을 추가하고 계약을 바꾼다.
- 묶음 전용 큐 분리 — 큐 독점은 막지만 워커 설정이 큐마다 갈라지고 competing consumers의 이점이 준다.

**팀 확정 필요**: 발행 창 크기, 실행시간 상한, 연속 실패 중단 임계값. 확정 전에는 설정 기본값을
쓰고 임시값임을 표시한다.

## R3. 동률 처리 (PD-05 잔여)

**Decision**: spec이 이미 정한 대체 규칙을 그대로 구현한다 — 동률 후보를 모두 표시하고 순서를
임의로 정하지 않는다. 표시 후보 5개 경계에서 동률이면 5개를 넘겨 함께 보이고 동률임을 표시한다.

**Rationale**: spec Edge Cases가 "규칙이 없으면 동률 후보를 모두 표시하고 순서를 임의로 정하지
않는다"고 명시한다. 임의 순서를 넣지 않는 것이 원칙 VI·VIII와 맞고, 추가 결정 없이 테스트 가능하다.

## R4. 묶음의 소유자와 사용자 식별 (인증 미구현)

**Decision**: `search_batch.owner_user_id`를 nullable로 두고, 인증이 없는 현재는 NULL로 저장한다.
저장·재조회는 `searchId`로 하고 목록 조회는 인증 도입 후 소유자 필터를 켠다.

**Rationale**: specs/README 공통 가정이 "인증·인가 방식은 constitution 합의되지 않은 영역이므로
plan에서 근거를 남기고 정한다"고 위임했다. 현재 backend에 `SecurityFilterChain`·JWT가 전혀 없고
(`account`는 signup·이메일 인증만) 007이 인증을 도입하면 006·전 파트에 걸친 결정을 007이 대신
내리는 셈이다. nullable 컬럼은 인증 도입 시 마이그레이션 없이 채워진다.

**Alternatives considered**:
- 007에서 인증 도입 — 범위를 크게 벗어나고 소유 spec이 아니다.
- 소유자 컬럼 생략 — 006(내 기록)이 붙을 때 테이블 변경이 필요하다.

## R5. 평가 분할과 검증 상태 (PD-12 미확정)

**Decision**: 평가 분할을 등록하지 않은 상태로 구현하고, 그 경우 모든 후보를 `UNVALIDATED`
('미검증')로 표시한다. 분할이 등록되면 후보별로 구간별 성과를 분리 저장할 자리(`period_performance`
JSONB)를 미리 둔다.

**Rationale**: FR-014의 마지막 항목이 "평가 분할이 등록되지 않았거나 잠금 구간이 확보되지 않은
탐색이면 모든 후보가 '미검증'으로 표시되고 '충분한 검증이 없다'는 이유로 기능이 막히지는 않는다"고
직접 허용한다(원칙 I). PD-12는 시험 전에 고정하면 되고 구현 착수의 선행 조건이 아니다.

**주의**: 이 경로에서 SC-005("잠금 구간 성과가 후보 선정에 쓰인 사례 0건")는 자동으로 만족한다 —
잠금 구간이 없으므로 쓸 수 없다. 이를 검증 통과로 보고하지 않는다(완료의 구분).

## R6. 후보 1건의 계산 경로 (설계 확인)

**Decision**: 후보 1건은 새 계산 경로를 만들지 않고 **기존 `backtest_job` 1행 + `backtest.jobs`
메시지 1건**으로 실행한다. `search_candidate`가 `backtest_job.id`를 FK로 참조한다. Worker는
변경하지 않는다.

**Rationale**: FR-007이 "후보 하나의 계산은 004의 공통 거래·평가 규칙을 따른다"고 요구한다. 같은
규칙을 두 번 구현하면 004와 007의 결과가 갈릴 수 있고, CLAUDE.md 아키텍처 원칙 1(Backend는 계산하지
않는다)·2(같은 워커 코드 수평 확장)에 맞는다. 004가 배분 전략을 워커에 추가하고 지원 목록에 넣으면
007은 코드 변경 없이 그 전략을 탐색 대상으로 얻는다(R8, FR-026).

**결과 이벤트 수신 경로**: `backtest.events` 큐에는 이미 `BacktestEventListener`가 붙어 있다. 같은
큐에 두 번째 컨슈머를 붙이면 competing consumers라 메시지가 분배되어 둘 다 일부만 받는다. 따라서
007은 큐를 다시 소비하지 않고, 결과 저장 후 Spring `ApplicationEventPublisher`로 발행되는 인메모리
이벤트를 듣는다. 이 방향이 모듈 간 결합도도 낮다.

**Alternatives considered**:
- 007 전용 계산 경로 — 계산 규칙 이중화. 거부.
- `backtest.events`에 007 전용 큐를 추가 바인딩(fanout) — 계약(§2 토폴로지)을 바꿔야 하고 워커·인프라
  변경을 부른다. 인메모리 이벤트로 충분하다.

## R7. 인접 설정 안정성의 계산 자료 구조

**Decision**: 후보마다 `grid_coordinates` JSONB(축 이름 → 후보 값 인덱스)를 저장한다. 이웃은 한 축의
인덱스만 ±1 다른 후보이며, 좌표 비교로 O(후보 수 × 축 수)에 찾는다. 계산 대상은 완료 후보뿐이고
제외·실패·미실행 후보는 이웃으로 세지 않는다.

**Rationale**: FR-013a가 이웃을 "파라미터 축 하나만 등록표에서 한 칸 다른 조합"으로 정의했다. 값
자체(예: 관측 기간 60일)를 비교하면 간격이 불균등한 축에서 "한 칸"의 뜻이 흔들리는데, 등록표
인덱스는 그 뜻을 그대로 담는다. 좌표는 재현 기록(FR-020)에도 필요하다.

**계산 시점**: 묶음이 끝난(완료·부분 완료) 뒤 1회. 안정성 필터가 묶음 내 상대 분위(상위 50%)라
전체 완료 후보가 모여야 판정할 수 있다(FR-013).

**2026-09-11 보강 — 축 순서와 전략 경계**: 인덱스의 뜻은 등록표가 돌려준 후보값 목록의 순서에서
