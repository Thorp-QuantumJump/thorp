# Quickstart: 결과 이해·비교

**Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Contracts**: [contracts/result-api.md](contracts/result-api.md) | **Date**: 2026-09-16

이 문서는 기능이 실제로 동작하는지 확인하는 방법을 적는다. 구현 코드는 담지 않는다.

## 전제

- 백엔드·워커·PostgreSQL·RabbitMQ가 떠 있어야 한다(저장소 루트 README의 개발 환경 구성).
- 001의 KRX 자료가 적재되어 있어야 결과가 나온다.
- 004의 백테스트 실행 경로가 동작해야 한다. `POST /backtests`가 `202`를 돌려주고 잠시 뒤 `COMPLETED`가 되는지 먼저 확인한다.
- **공개 열람 경계(plan의 묶음 A)가 병합되기 전에는 결과 화면이 뜨지 않는다.** 현재 `CurrentRequester.requireRequesterId`가 인증 없이는 예외를 던지기 때문이다.

## 검증 시나리오

각 항목은 spec의 성공 기준과 짝을 이룬다. 자동 테스트로 덮은 것과 눈으로 확인할 것을 나눠 적었다.

### 1. 첫 화면이 네 가지만 보인다 (SC-001)

분석 하나를 완료한 뒤 그 결과 주소를 연다. 핵심 숫자 3개·그래프 1개·요약 1문장·조건 한 줄만 보이고 상세는 접혀 있어야 한다. 브라우저 개발자 도구의 네트워크 탭에서 첫 화면이 부른 요청이 `GET /results/{token}`과 `/timeseries` 둘뿐인지 확인한다. `/trades`가 함께 불렸다면 SC-001 위반이다.

### 2. 고점 대비 하락과 시작 금액 대비 손실이 구분된다 (SC-002)

'가장 크게 줄었던 폭' 옆 설명과 그래프의 음영 구간을 함께 본다. 음영이 그려지지 않으면 `summary.maxDrawdown`과 시계열에서 찾은 구간이 어긋난 경우다([research.md](research.md) R-05). 그때는 음영 없이 숫자와 설명만 보이는 것이 정상이다.

사용성 관찰(PD-14)에서 참여자 6~8명에게 상세를 열지 않고 세 숫자의 뜻을 말하게 한다. 두 명 이상이 같은 지점에서 오해하면 요약 화면을 고친다.

### 3. 두 결과가 같은 조건으로 그려진다 (SC-003)

기준 결과에서 다른 전략을 비교 대상으로 고른다. 결과가 없으면 분석이 자동으로 요청되고 완료 전까지 기준만 그려지며 비교 자리에 진행 상태가 보여야 한다. 완료 후 두 곡선의 기간·금액·비용이 같은지 조건 한 줄에서 확인한다.

평가 기간이 어긋나는 조합(워밍업이 더 긴 전략)을 고르면 겹쳐 그리지 않고 공통 구간과 재계산 대상 두 건을 보인 뒤 확인을 받아야 한다.

### 4. 추천으로 읽힐 표현이 없다 (SC-004)

`frontend/src/features/result/summarySentences.ts`의 틀 목록을 전부 읽는다. 금지 어휘 단위 테스트가 이를 자동으로 막지만, 목록 자체를 사람이 한 번 읽는 것이 이 기준의 취지다.

```bash
cd frontend && npm run test
```

### 5. 결과 의미를 바꾸는 상태가 결과 옆에 보인다 (SC-005)

자료가 부족한 섹터를 포함해 분석한 뒤 결과 옆에 한 문장이 있는지 확인한다. 실행 도중 취소한 요청을 열어 숫자 자리가 0으로 채워지지 않고 "계산되지 않았다"로 표시되는지 확인한다.

### 6. '자세히 보기'가 화면을 옮기지 않는다 (SC-006, SC-007)

'자세히 보기'를 눌렀을 때 주소가 바뀌지 않고 결과 근처에서 패널이 열려야 한다. 대표 상품 정보도 그 안에서 펼쳐지고 001의 화면으로 이동하지 않아야 한다.

### 7. 만료된 주소가 결과를 열지 않는다 (SC-008)

비로그인 상태로 분석한 뒤 만료 시각을 지나게 하거나 설정값을 짧게 두고 다시 연다. `410`과 함께 남아 있지 않다는 안내, 그리고 같은 조건으로 다시 분석할 진입점이 보여야 한다. 빈 결과 화면이나 0으로 채운 숫자가 보이면 실패다.

### 8. 식별자를 바꿔 남의 결과에 닿지 못한다 (SC-009)

결과 주소의 토큰에서 마지막 몇 자를 바꿔 열어 본다. `404`가 나와야 한다. 주소 어디에도 `BT-`로 시작하는 값이 보이지 않아야 하고, 개발자 도구의 응답 본문에도 없어야 한다.

### 9. 회색조에서도 두 결과가 구분된다 (SC-010)

두 결과를 비교한 화면을 회색조로 보거나 흑백으로 인쇄한다. 실선과 파선, 곡선 끝 이름표로 어느 쪽이 기준인지 알 수 있어야 한다.

### 10. 좁은 화면에서 읽힌다

브라우저 폭을 휴대폰 크기로 줄인다. 요소가 세로로 쌓이고 핵심 숫자·그래프·요약을 읽을 수 있어야 한다. 데스크톱에서 열라는 안내만 보이면 실패다(FR-019와 부딪힌다).

## B05 구현 검증 (2026-09-18)

[S15P21E205-309](https://ssafy.atlassian.net/browse/S15P21E205-309), 브랜치 `feat(fe)/309-result-comparison`. T045~T054·T057~T061의 구현과 자동 검증을 마쳤다. Jira 작업은 MR 병합 전이므로 진행 중이다. 실제 KRX 데이터로 사용한 화면과 사용성 관찰은 이번 검증에 포함하지 않았다.

- 프런트엔드: `npm run lint` 오류 0건(기존 경고 20건), `npm run build` 성공. `VITEST_MAX_WORKERS=2 npm test`는 Vitest 1,134개와 기존 Node 테스트 13개 통과, 실패·건너뜀 0건이다.
- 백엔드: Java 21에서 `./gradlew spotlessApply build --no-daemon --console=plain` 성공. 1,736개 통과, 실패 0건, 환경을 명시적으로 켜야 하는 4개만 건너뛰었다: `MARKET_LIVE_TEST=true`의 실시간 API 1개, `THORP_RUN_NEWS_PERFORMANCE=true`의 성능 2개, `THORP_REQUIRE_DOCKER=true`의 필수 Docker 확인 1개. 공개 결과 API·서비스와 평가 기간 계산 관련 39개는 모두 실행해 통과했고 PostgreSQL 통합 테스트도 실행했다.
- 비교 선택 전 추가 조회 없음, 조건 보존 요청, 대기·진행·실패·만료·429의 명시적 재시도, 422의 필요값 표시, 공통 기간 확인 후 두 건 재계산과 원래 주소 보존을 자동 테스트로 확인했다. 두 번째 요청 실패 시 첫 접수 중복 방지와 비교 해제 뒤 늦은 응답 무시도 검증했다.
- 같은 조건에서만 비교 곡선·요약·상세를 연결하며, 자동 탐색 후보 표시와 유일한 주 행동 버튼을 화면 테스트로 확인했다. T059·T060의 상태 컴포넌트와 확인창 테스트는 실제 흐름을 함께 검증하는 `useCompareTarget.test.tsx`에 통합했다. 구현 시 확인한 계약 보정은 [plan.md](plan.md)의 B05 절에 기록했다.
- 코드리뷰에서 확인한 두 경로를 보강했다. 기존 결과와 새 대상의 자료·엔진 버전이 다르면 두 결과를 현재 기준으로 다시 요청하며, 기간·버전 확인창을 닫으면 키보드 초점이 '비교 대상 고르기'로 돌아간다.

- PD-23(비로그인 결과 유효 시간)이 미확정이라 만료 값은 설정 파일에만 있다. 문서에 수치를 적지 않는다.

- 응답 시간 목표는 정하지 않았다. 004의 실행 측정(PD-06)이 나온 뒤 같은 기준으로 정한다.
- `analytics`의 상관관계·위험 기여·손실 기여는 워커가 계산해 저장하지만 API로 나오지 않는다([research.md](research.md) R-06). 004가 노출하기 전까지 상세 패널의 해당 항목은 값을 지어내지 않고 제공되지 않음으로 둔다.
