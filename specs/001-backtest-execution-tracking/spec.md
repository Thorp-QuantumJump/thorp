# Feature Specification: 백테스트 실행 및 결과 추적

**Feature Branch**: `001-backtest-execution-tracking`

**Created**: 2026-09-02

**Status**: Draft

**Input**: User description: "F1. 백테스트 실행 및 결과 추적 — Quantum Jump의 백테스트 실행 및 결과 추적 기능을 정의한다. 백테스트는 실행 시간이 요청마다 크게 달라질 수 있다. 사용자가 백테스트를 시작한 뒤 클라이언트 연결이 종료되더라도 실행 자체가 영향을 받아서는 안 되며, 이후 실행 상태와 결과를 확인할 수 있어야 한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 백테스트 실행 요청과 식별 (Priority: P1)

퀀트 전략의 성과를 검증하려는 사용자가 백테스트 실행을 요청한다. 요청이 수락되면 사용자는
그 실행을 가리키는 고유 식별자를 즉시 받는다. 백테스트 계산이 얼마나 오래 걸리든 사용자는
계산이 끝나기를 기다리지 않고 식별자를 손에 쥔 상태로 요청 단계를 마친다.

**Why this priority**: 실행을 식별할 수 없으면 이후의 상태 추적과 결과 조회가 모두 불가능하다.
이 기능 하나만 있어도 "요청이 접수되었다"는 사실을 사용자가 확인할 수 있으므로 가장 작은
가치 단위가 된다.

**Independent Test**: 백테스트 실행을 요청하고, 계산 완료 여부와 무관하게 고유 식별자를 받는지
확인한다. 같은 사용자가 두 번 요청하면 서로 다른 식별자를 받는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 식별된 사용자의 유효한 백테스트 실행 요청, **When** 사용자가 실행을 요청하면,
   **Then** 시스템은 요청을 수락하고 그 실행을 유일하게 가리키는 식별자를 사용자에게 제공하며,
   그 실행을 요청한 사용자와 연결해 기록한다.
2. **Given** 계산에 수 분 이상 걸리는 백테스트, **When** 사용자가 실행을 요청하면, **Then**
   사용자는 계산 완료를 기다리지 않고 식별자를 받는다.
3. **Given** 수락될 수 없는 실행 요청(필수 조건 누락 등), **When** 사용자가 실행을 요청하면,
   **Then** 시스템은 요청을 거부하고 거부 이유를 알리며, 어떤 실행도 생성되지 않는다.

### User Story 2 - 실행 상태 추적 (Priority: P2)

사용자는 식별자를 사용해 실행이 현재 어느 단계에 있는지(시작 대기, 실행 중, 성공 완료, 실패)를
확인한다. 요청 직후 화면을 닫거나 네트워크가 끊겨도 실행은 계속 진행되며, 사용자는 나중에
다시 접속해 같은 식별자로 현재 상태를 확인할 수 있다.

**Why this priority**: 실행 시간이 요청마다 크게 달라지므로 사용자가 "지금 어디까지 왔는가"를
알 수 있어야 한다. 또한 클라이언트 연결과 실행이 독립적이라는 핵심 정책이 사용자에게 드러나는
지점이다.

**Independent Test**: 실행을 요청한 뒤 클라이언트를 완전히 종료하고, 잠시 후 다른 세션에서 같은
식별자로 상태를 조회한다. 실행이 중단되지 않고 상태가 정상적으로 전이되었는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 수락된 실행의 식별자, **When** 사용자가 상태를 조회하면, **Then** 시스템은 그 실행의
   현재 상태를 하나 반환한다.
2. **Given** 실행 중인 백테스트, **When** 사용자의 클라이언트 연결이 종료되면, **Then** 실행은
   중단되지 않고 계속 진행되어 종결 상태에 도달한다.
3. **Given** 연결 종료 후 다시 접속한 사용자, **When** 이전에 받은 식별자로 상태를 조회하면,
   **Then** 시스템은 최신 상태를 반환한다.
4. **Given** 존재하지 않는 식별자, **When** 사용자가 상태를 조회하면, **Then** 시스템은 해당
   실행이 없음을 명확히 알린다.
5. **Given** 다른 사용자가 요청한 실행의 식별자, **When** 사용자가 상태를 조회하면, **Then**
   시스템은 조회를 거부하고 그 실행의 상태나 존재 여부를 노출하지 않는다.

---

### User Story 3 - 완료 결과 조회와 성공·실패 구분 (Priority: P3)

사용자는 실행이 종결된 뒤 식별자로 결과를 조회한다. 성공한 실행에서는 백테스트 결과를 받고,
실패한 실행에서는 실패했다는 사실과 사용자가 이해할 수 있는 실패 사유를 받는다. 사용자는 두
경우를 혼동하지 않고 구분할 수 있다.

**Why this priority**: 결과를 조회하는 것이 백테스트의 최종 목적이다. 그러나 결과 조회는 실행
식별(US1)과 종결 상태 확인(US2) 위에서만 의미가 있으므로 그 다음 순서에 둔다.

**Independent Test**: 성공하도록 구성된 실행과 실패하도록 구성된 실행을 각각 완료시킨 뒤, 식별자로
조회하여 전자는 결과가, 후자는 실패 사유가 반환되고 둘이 명확히 구분되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 성공적으로 완료된 실행, **When** 사용자가 결과를 조회하면, **Then** 시스템은 그
   실행의 백테스트 결과를 반환한다.
2. **Given** 실패로 종결된 실행, **When** 사용자가 결과를 조회하면, **Then** 시스템은 실행이
   실패했음을 알리고 사용자가 이해할 수 있는 실패 사유를 제공한다.
3. **Given** 아직 종결되지 않은 실행, **When** 사용자가 결과를 조회하면, **Then** 시스템은 결과가
   아직 없음을 알리고 현재 상태를 함께 제공한다.
4. **Given** 종결된 실행, **When** 사용자가 시간이 지난 뒤 다시 조회하면, **Then** 시스템은 동일한
   상태와 결과를 반환한다.

---

### User Story 4 - 실시간 결과 차트 확인 (Priority: P4)

사용자는 백테스트가 실행되는 동안 결과 차트를 실시간으로 확인한다. 실행이 진행되며 누적되는
중간 결과가 사용자의 수동 조작 없이 차트에 점진적으로 반영되고, 실행이 종결되면 차트는 최종
결과로 마무리된다. 화면을 닫았다가 다시 열어도 그 시점까지 누적된 중간 결과부터 이어서 본다.

**Why this priority**: 실행 시간이 길어질 수 있는 상황에서 사용자가 기다리는 동안에도 진행 상황을
결과의 형태로 체감할 수 있게 한다. 다만 US1~US3이 없으면 성립하지 않는 기능이므로 마지막 순서에
둔다.

**Independent Test**: 수 분 이상 걸리는 실행을 요청한 뒤 결과 화면을 열어 두고, 사용자의 조작 없이
차트가 진행에 따라 점진적으로 채워지는지, 종결 후 최종 결과와 일치하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 결과 화면을 열어 둔 사용자, **When** 실행이 진행 중이면, **Then** 차트는 그 시점까지
   누적된 중간 결과를 사용자의 수동 조작 없이 점진적으로 반영한다.
2. **Given** 결과 화면을 열어 둔 사용자, **When** 실행이 성공적으로 종결되면, **Then** 차트는
   사용자의 수동 조작 없이 최종 결과로 완성되며, 최종 결과는 US3에서 조회되는 결과와 일치한다.
3. **Given** 실행 중 화면을 닫았다가 다시 연 사용자, **When** 같은 식별자로 결과 화면을 열면,
   **Then** 차트는 그 시점까지 누적된 중간 결과를 먼저 보여 준 뒤 이어서 갱신된다.
4. **Given** 결과 화면을 열어 둔 사용자, **When** 실행이 실패로 종결되면, **Then** 차트 갱신이
   멈추고 실행이 실패했음과 실패 사유가 표시된다.

---

### Edge Cases

- 존재하지 않거나 형식이 잘못된 식별자로 조회하면 시스템은 "해당 실행 없음"을 명확히 구분해
  알린다. 다른 실행의 정보가 노출되어서는 안 된다.
- 실행을 처리하던 주체가 실행 도중 비정상 종료되면, 그 실행은 무기한 비종결 상태에 머무르지 않고
  사용자가 실패로 확인할 수 있는 상태에 도달한다.
- 동일 실행 작업이 재시도되거나 중복 전달되어도 사용자는 하나의 식별자에 대해 하나의 결과만 본다.
  종결된 실행의 상태와 결과는 이후의 중복 전달로 바뀌지 않는다.
- 사용자가 동일한 조건으로 백테스트를 다시 요청하면 별도의 실행으로 취급되어 새 식별자를 받는다.
  (이는 실행 작업의 중복 전달과 구별된다.)
- 종결되지 않은 실행의 최종 결과를 조회하면 최종 결과 대신 현재 상태와 그 시점까지 누적된 중간
  결과가 제공된다.
- 동일 실행 작업의 중복 전달로 같은 구간의 중간 결과가 다시 도착해도 차트에 그 구간이 중복해서
  그려지지 않는다.
- 실행이 실패로 종결되면 그때까지 누적된 중간 결과는 최종 결과로 승격되지 않는다. 사용자는
  실패 사실과 사유를 확인하며, 중간 결과는 참고용으로만 남는다.
- 다른 사용자가 요청한 실행의 식별자로 조회하면 시스템은 조회를 거부하며, 그 실행의 상태·결과·
  존재 여부를 노출하지 않는다.
- 실행이 시작 대기 상태에서 오랫동안 시작되지 않더라도 사용자는 그 상태를 그대로 확인할 수 있어야
  하며, 시스템이 상태를 임의로 종결 처리해서는 안 된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 유효한 백테스트 실행 요청을 수락하면 그 실행을 유일하게 가리키는 식별자를
  생성하고 사용자에게 제공해야 한다.
- **FR-002**: 실행 요청에 대한 응답은 백테스트 계산의 완료를 기다리지 않아야 한다. 사용자는 계산
  시간과 무관하게 식별자를 받는다.
- **FR-003**: 백테스트 실행은 그것을 시작한 요청의 생명주기와 독립적이어야 한다. 요청 처리가
  끝나거나 클라이언트 연결이 종료되어도 이미 시작된 실행은 중단되거나 영향을 받지 않아야 한다.
- **FR-004**: 사용자는 식별자로 실행의 현재 상태를 조회할 수 있어야 한다. 상태는 최소한 다음 네
  가지를 구분해야 한다: 시작 대기, 실행 중, 성공 완료, 실패.
- **FR-005**: 실행 상태는 시작 대기에서 시작해 실행 중을 거쳐 성공 완료 또는 실패 중 하나의 종결
  상태에 도달한다. 종결 상태에 도달한 실행의 상태는 이후 변경되지 않아야 한다.
- **FR-006**: 실행 상태의 집합과 허용되는 전이는 상태를 생산하고 소비하는 모든 파트가 공유하는
  계약으로 `docs/specs/`에 문서화되어야 한다. (헌장 원칙 II)
- **FR-007**: 사용자는 성공 완료된 실행의 결과를 식별자로 조회할 수 있어야 한다.
- **FR-008**: 실패한 실행은 성공한 실행과 명확히 구분되어야 하며, 사용자가 이해할 수 있는 실패
  사유를 함께 제공해야 한다.
- **FR-009**: 동일한 실행 작업의 재시도나 중복 전달은 중복 결과나 중복 상태 변경을 발생시키지
  않아야 한다. 하나의 식별자에는 최대 하나의 결과만 존재한다. (헌장 원칙 V, 멱등성)
- **FR-010**: 실행의 상태와 결과는 실행이 종결된 이후에도 같은 식별자로 다시 추적할 수 있어야 한다.
- **FR-011**: 존재하지 않는 식별자로 조회하면 시스템은 해당 실행이 없음을 명확히 알려야 하며, 다른
  실행의 정보를 노출해서는 안 된다.
- **FR-012**: 실행이 정상적으로 끝날 수 없게 된 경우(처리 주체의 비정상 종료 등) 그 실행은 무기한
  비종결 상태에 머무르지 않고 실패 상태에 도달해야 하며, 사용자는 이를 실패로 확인할 수 있어야 한다.
- **FR-013**: 실행이 진행되는 동안 시스템은 그 시점까지 누적된 중간 결과를 제공해야 하며, 사용자는
  결과 차트에서 이 중간 결과를 수동 새로 고침 없이 점진적으로 확인할 수 있어야 한다.
- **FR-014**: 실행이 성공 완료되면 중간 결과의 누적은 최종 결과와 일치해야 한다. 실행 도중 화면을
  떠났다가 돌아온 사용자는 그 시점까지 누적된 중간 결과부터 이어서 볼 수 있어야 한다.
- **FR-015**: 동일 실행 작업의 재시도나 중복 전달로 같은 구간의 중간 결과가 다시 생산되어도 중간
  결과가 중복되어서는 안 된다. (FR-009의 멱등성은 중간 결과에도 적용된다.)
- **FR-016**: 실행의 상태, 중간 결과, 최종 결과는 그 실행을 요청한 사용자만 조회할 수 있어야 한다.
  다른 사용자의 조회는 거부되어야 하며, 거부 시 해당 실행의 존재 여부와 내용을 노출해서는 안 된다.
- **FR-017**: 실행 요청은 식별된 사용자에 의해서만 수락되어야 하며, 시스템은 각 실행을 요청한
  사용자와 연결하여 기록해야 한다.

### Key Entities *(include if feature involves data)*

- **백테스트 실행(Backtest Run)**: 사용자의 실행 요청 하나에 대응하는 추적 단위. 고유 식별자,
  요청한 사용자, 요청 시각, 현재 상태, 상태가 마지막으로 바뀐 시각, 실패 시 실패 사유를 가진다.
  성공 완료된 경우 최종 결과와 1:1로 연결되며, 실행 중에는 0개 이상의 중간 결과를 가진다.
- **중간 결과(Intermediate Result)**: 실행이 진행되는 동안 누적되는 부분 결과. 어느 실행에 속하는지,
  어느 구간까지의 결과인지를 식별할 수 있어야 하며, 같은 구간의 중간 결과는 한 번만 존재한다.
  구성 항목은 별도 스펙에서 정의한다.
- **실행 상태(Run Status)**: 실행이 생명주기에서 어느 단계에 있는지를 나타내는 값. 최소 집합은 시작
  대기, 실행 중, 성공 완료, 실패이며, 정확한 값과 전이 규칙은 공유 계약 문서(`docs/specs/`)가
  정한다.
- **백테스트 결과(Backtest Result)**: 성공 완료된 실행이 산출한 최종 결과. 이 스펙은 결과가 실행에
  1:1로 귀속되고 식별자로 조회되며 누적된 중간 결과와 일치한다는 사실만 정의하며, 결과의 구성
  항목(지표, 시계열 등)은 별도 스펙에서 정의한다.
- **사용자(User)**: 실행을 요청하고 그 실행의 상태·결과를 조회할 수 있는 식별된 주체. 실행과의
  관계는 요청자로서 1:N이다. 사용자 식별·인증 자체는 이 스펙의 범위 밖이다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 실행 요청의 95%에서 사용자는 백테스트 계산 시간과 무관하게 2초 이내에 식별자를
  받는다.
- **SC-002**: 실행 도중 클라이언트 연결을 종료한 뒤 재접속해 조회하는 시험에서, 실행이 중단된
  사례가 0건이고 상태·결과 조회 성공률이 100%다.
- **SC-003**: 동일 실행 작업을 의도적으로 중복 전달하는 시험에서, 식별자당 결과 개수가 항상 1이고
  종결 상태가 바뀐 사례가 0건이다.
- **SC-004**: 시작된 모든 실행은 정상 완료, 실패, 처리 주체의 비정상 종료 중 어떤 경로를 거치더라도
  종결 상태에 도달한다. 무기한 비종결 상태로 남는 실행은 0건이다.
- **SC-005**: 사용자는 식별자만으로 첫 조회에서 실행이 성공했는지 실패했는지 추가 조작 없이 구분할
  수 있다.
- **SC-006**: 실행 상태가 바뀐 뒤 사용자가 조회하는 상태에 그 변화가 반영되기까지의 지연은 95%에서
  5초 이내다.
- **SC-007**: 종결된 실행은 종결 후 최소 보존 기간 동안 같은 식별자로 100% 조회된다.
- **SC-008**: 실행 중 새 중간 결과가 생산된 뒤 열어 둔 결과 차트에 반영되기까지의 지연은 95%에서
  5초 이내다.
- **SC-009**: 성공 완료된 실행에서 누적된 중간 결과와 최종 결과가 불일치하는 사례는 0건이다.
- **SC-010**: 다른 사용자의 실행 식별자로 상태·중간 결과·최종 결과를 조회하는 시험에서 정보가
  노출된 사례는 0건이다.

## Assumptions

- 진행 상태는 이산적인 단계(시작 대기, 실행 중, 성공 완료, 실패)로 제공한다. 백분율 등 세부 진행률
  표시는 이 스펙의 요구사항이 아니다.
- 사용자가 요청 단계에서 제출하는 입력 조건의 내용과 검증 규칙은 이 스펙의 범위 밖이다. 이 스펙은
  "수락된 요청은 식별자를 받고, 수락되지 않은 요청은 실행을 생성하지 않는다"는 경계만 정의한다.
- 결과의 구성 항목(수익률, MDD, Sharpe 등)과 차트의 구체적 형태는 별도 스펙에서 정의한다. 이 스펙은
  결과가 실행에 귀속되어 조회 가능하다는 사실과 결과 차트가 중간 결과로 점진 갱신된다는 사실만
  다룬다.
- 중간 결과의 단위(예: 거래일 단위, 일정 구간 단위)와 생산 빈도는 별도 스펙 또는 설계 단계에서
  정한다. 이 스펙은 중간 결과가 구간을 식별할 수 있고 누적이 최종 결과와 일치해야 한다는 특성만
  요구한다.
- 사용자를 식별하는 수단(로그인, 인증)은 이 기능의 전제 조건이며 별도 기능에서 제공한다. 이 스펙은
  "식별된 사용자"가 존재한다고 가정하고 요청자 기준의 접근 범위만 정의한다.
- 실행에 대한 접근 권한은 요청자에게만 있으며, 공유·위임·관리자 조회는 요청되지 않았으므로 포함하지
  않는다.
- 사용자가 같은 조건으로 백테스트를 다시 요청하면 별도의 실행으로 취급한다. 중복 방지(FR-009)는
  이미 수락된 동일 실행 작업의 재시도·재전달에 적용되며, 사용자의 새 요청에는 적용되지 않는다.
- 종결된 실행의 상태와 결과는 최소 30일 동안 보존된다. 보존 기간 종료 후의 처리 정책은 이 스펙의
  범위 밖이다.
- 제출한 실행의 목록 조회, 실행 취소, 실행 재시작은 요청되지 않았으므로 이 스펙에 포함하지 않는다.
- 상태를 전달하는 방식(폴링, 서버 푸시 등), 실행을 처리하는 구성 요소와 분배 방식, 저장 형식은 이
  스펙에서 정하지 않으며 설계 단계에서 결정한다.

## Constitution Alignment

- **원칙 I (독립적 실행 경계)**: FR-002·FR-003이 요청 처리와 계산의 분리를 요구한다. 실행 주체의
  형태는 정하지 않는다.
- **원칙 II (요청 생명주기 독립·추적 가능)**: FR-001·FR-003·FR-004·FR-010이 식별자 기반 추적을
  요구하고, FR-006이 상태 계약의 문서화를 요구한다.
- **원칙 IV (파트 경계 계약)**: 상태 집합, 결과 귀속 규칙, 중간 결과의 구간 식별 규칙을 공유
  계약으로 문서화한다(FR-006). 구체적 필드와 전달 형식은 설계 단계에서 정한다.
- **원칙 V (결과 신뢰성 — 멱등성)**: FR-009·FR-015가 최종 결과와 중간 결과 모두에 대해 중복 전달
  멱등성을 요구하고, FR-014가 중간 결과 누적과 최종 결과의 일치를 요구한다. 재현성과 비교 가능성은
  결과 지표 스펙에서 다룬다.
- **보안·데이터 제약**: FR-016이 요청자 외 사용자에게 실행 정보를 노출하지 않도록 요구한다.
- 원칙에서 벗어나는 요구사항은 없다.
