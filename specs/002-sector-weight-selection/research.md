# Phase 0 Research: 섹터·비중 선택

**Date**: 2026-09-15 | **Plan**: [plan.md](./plan.md) | **Spec**: [spec.md](./spec.md)

spec이 plan으로 넘긴 지점과 Technical Context의 미확정 항목을 조사해 결정한다. spec의 요구사항을 바꾸지 않으며, 팀이 확정할 제품 결정(PD)에 해당하는 값은 정하지 않는다. 화면 문구도 확정하지 않는다. 여기서 정하는 것은 문구가 놓일 자리와 나타나는 조건까지다.

## 결정 1: 표시 정밀도와 합계 판정 정밀도를 소수 첫째 자리로 두고, 비중을 0.1%p 단위 정수로 다룬다

**문제**: spec은 표시 정밀도와 합계 판정 정밀도를 같은 값으로 두라고만 정하고 자릿수는 plan에 넘겼다(spec.md의 Edge Cases와 Assumptions). 여기에 더해 백분율을 소수로 더하면 `0.1 + 0.2 !== 0.3`인 부동소수 문제가 합계 판정에 그대로 들어온다. 100%가 아닌데 100%로 판정하거나 그 반대가 되면 FR-006·FR-007이 무너진다.

**Decision**: 정밀도는 **소수 첫째 자리(0.1%p 단위)** 하나로 통일한다. 화면 안에서는 비중을 **0.1%p 단위 정수**로 다루며, 100%는 정수 `1000`이다. 합계 판정은 `합계 === 1000`이라는 정수 비교이고, 표시할 때만 10으로 나누어 소수 첫째 자리 문자열로 만든다. 사용자 입력 문자열은 정수로 바꾸어 보관하며, 저장·인계 값도 정수로 내보낸다.

```
표시값 "33.4%"  ←→  내부값 334
합계 판정        sum(weightTenths) === 1000
동일 비중 n개    q = floor(1000 / n),  r = 1000 - q * n
```

소수 둘째 자리 이하가 들어오면 **입력을 받지 않고 그 자리에 한 문장으로 알린다.** 조용히 반올림하면 원칙 VI가 금지한 "사용자 입력을 임의로 바꾼 뒤 알리지 않는 처리"가 된다. 거부는 변경이 아니므로 SC-002를 어기지 않는다. 입력 칸은 `step`을 0.1로 두고, 붙여넣기처럼 `step`을 우회하는 경로도 같은 검사를 거친다.

**Rationale**:

- FR-005가 "표시 정밀도가 소수 첫째 자리라면 섹터를 3개 고를 때 33.4% / 33.3% / 33.3%"라는 예시를 전제로 적어 두었다. 다른 자릿수를 고르면 spec 본문의 예시가 그 자리에서 틀린 문장이 된다. 예시를 살리는 자릿수가 소수 첫째 자리다.
- 실제로 필요한 해상도도 그 정도다. 섹터 10개를 고르면 동일 비중이 10.0%이고, 20개를 고르면 5.0%다. 100%를 20으로 나눠도 0.1%p 단위로 나누어떨어진다. 소수 둘째 자리는 사용자가 구분해 입력할 이유가 없고, 정수 자리로 올리면 섹터 3개·6개·7개에서 잔여분이 1%p까지 커져 눈에 띄는 불균형이 된다.
- 정수 단위로 다루면 부동소수 문제가 아예 생기지 않는다. `334 + 333 + 333 === 1000`은 어떤 브라우저에서도 같다. 저장소에 실어 보냈다가 되읽는 경로에서도 값이 흔들리지 않는다.
- 새 의존성이 필요 없다. `frontend/package.json`에 decimal.js·big.js 계열이 없고, 정밀 소수 라이브러리를 이 화면 하나 때문에 들이는 것은 014가 인증 상태 하나에 전역 상태 라이브러리를 들이지 않은 판단과 어긋난다.

**Alternatives considered**:

- **정수 퍼센트(소수점 없음)**: 판정이 가장 단순하다. 그러나 spec이 "소수점 비중 입력은 허용하되"라고 명시했고(spec.md의 Edge Cases), 섹터 3개에서 34/33/33이 되어 잔여분이 1%p가 된다. 기각.
- **소수 둘째 자리(0.01%p)**: 잔여분이 더 작아진다. 그러나 FR-005의 예시와 어긋나고, 사용자가 구분해 입력할 필요가 없는 자리이며, 입력 칸의 자릿수만 늘어나 원칙 II의 단순함에 역행한다. 기각.
- **소수를 그대로 쓰되 합계 판정에 허용 오차(epsilon)를 둔다**: 구현이 짧다. 그러나 원칙 VI가 "임의 epsilon을 넣어" 판정을 만드는 처리를 명시적으로 금지한다. 또 허용 오차를 두면 99.9999%를 100%로 판정하게 되어 무엇이 합격인지 설명할 수 없다. 기각.
- **비중을 문자열로 보관하고 판정 때만 파싱**: 부동소수를 피하지만 덧셈마다 파싱이 필요하고, 같은 값의 표기가 여럿("33.4"와 "33.40") 생겨 비교가 어려워진다. 기각.

## 결정 2: 잔여분은 표시 순서상 첫 번째 선택 섹터에 몰아주고, 표시 순서를 화면이 결정론적으로 정한다

**문제**: FR-005는 나머지를 한 섹터에 몰되 "선택 순서가 달라도 같은 자리가 되도록 일관된 규칙"을 요구하고 자리는 plan에 넘겼다.

**Decision**: 잔여분 `r`(0.1%p 단위 정수)은 **표시 순서상 첫 번째 선택 섹터** 하나에 더한다. 표시 순서는 사용자의 클릭 순서가 아니라 화면이 정하는 순서이며, `classification`(업종 `INDUSTRY` 먼저, 테마 `THEME` 다음) → 섹터 이름의 한국어 정렬(`Intl.Collator('ko')`) 순이다. 선택 목록도 같은 순서로 정규화해 보관한다.

```
정렬된 선택 섹터  [A, B, C]      q = 333, r = 1
초깃값            A 334, B 333, C 333
```

**Rationale**:

- "선택 순서와 무관하게 일관되다"를 만족하려면 잔여분 자리를 정하는 키가 사용자 행동과 무관한 값이어야 한다. 클릭 순서·선택 배열의 마지막 항목은 모두 사용자 행동에 따라 달라진다.
- 서버 응답의 배열 순서에 기대지 않는다. [001 계약](../001-etf-market-data/contracts/sector-api.md)이 `sectors` 배열의 정렬을 정하지 않았기 때문에, 응답 순서에 의존하면 백엔드 구현이 바뀔 때 화면 규칙이 조용히 따라 바뀐다. 화면이 스스로 정렬하면 그 위험이 없다.
- 첫 번째 자리를 고른 까닭은 FR-005의 예시가 `33.4% / 33.3% / 33.3%` 순서로 적혀 있어 큰 값이 앞에 오는 읽기를 전제하기 때문이다. 목록의 맨 위는 사용자가 가장 먼저 보는 자리이기도 해서, 왜 한 섹터만 0.1%p 큰지 설명하기 쉽다.
- 업종을 테마보다 먼저 두는 것은 FR-003이 요구한 업종/테마 구분 표시를 목록 자체로 드러내기 위해서다. 한국어 이름 정렬은 섹터 코드(영문) 정렬보다 사용자가 항목을 찾기 쉽다.

**Alternatives considered**:

- **마지막 섹터에 몰기**: 합계 표시가 목록 아래에 있으므로 시선 흐름과 맞는다. 그러나 섹터를 더 고를 때마다 잔여분이 붙은 자리가 아래로 옮겨 다녀, 사용자가 방금 고른 섹터만 값이 다른 것처럼 보인다. 기각.
- **가장 큰 비중을 가진 섹터에 몰기**: 초깃값 단계에서는 모든 값이 같아 동률이 되므로 결국 다른 기준이 필요하다. 기각.
- **잔여분을 0.1%p씩 앞에서부터 여러 섹터에 나눠 주기**: 값 차이가 더 작아진다. 그러나 FR-005가 "한 섹터에 몰아"라고 명시했다. 기각.
- **서버 응답 배열 순서를 그대로 쓰기**: 구현이 가장 짧다. 그러나 계약이 정렬을 보장하지 않는다. 기각하되, `GET /sectors`에 정렬 규칙을 명시하도록 001에 제안한다(범위 밖 보고).

## 결정 3: 상태 유지는 `sessionStorage` 항목 하나로 하고, 014가 쓰는 방식을 그대로 따른다

**문제**: FR-014는 "같은 탭 세션 동안 유지되고 새로고침과 로그인 왕복을 버티며 탭을 닫으면 사라진다"는 행동만 정하고 저장 수단을 plan에 넘겼다.

**Decision**: `sessionStorage` 항목 하나에 JSON으로 저장한다. 키는 `thorp.diagnosis.sectorSelection`이며, 014가 이미 쓰는 `thorp.auth.returnTarget`(`frontend/src/auth/returnTarget.ts`)과 같은 이름 규칙을 따른다. 페이로드 구조와 불변식은 [contracts/selection-handoff.md](./contracts/selection-handoff.md)가 소유한다. 상태가 바뀔 때마다 저장하고 화면 진입 때 읽는다. 저장소 접근이 막힌 환경에서는 014의 `returnTarget`처럼 예외를 삼키고 메모리 상태로만 동작한다.

읽어 온 페이로드는 신뢰하지 않고 검증한다. 섹터 코드는 현재 `GET /sectors` 응답에 있는 코드만 받아들이고, 비중은 0 이상 1000 이하의 정수만 받아들인다. 검증을 통과하지 못한 항목이 있으면 **그 항목을 선택에서 빼되 빠졌다는 사실을 한 문장으로 알린다.** 무엇을 제안할지(기본값 복원·대체 선택)는 [006 FR-008](../006-my-records/spec.md)과 UI-01이 소유하므로 002가 정하지 않는다.

**Rationale**:

- [014 plan](../014-user-auth/plan.md)이 로그인 뒤 복귀 위치에 같은 목적(탭 세션 동안 유지, 탭을 닫으면 소멸)으로 `sessionStorage`를 이미 채택했고, [014 research.md](../014-user-auth/research.md) 결정 7이 `localStorage`를 "다른 탭·이후 브라우저 세션까지 남으므로 범위가 넓다"는 이유로 기각해 두었다. 002의 요구가 같으므로 같은 수단을 쓴다. spec.md의 Clarifications가 이 선례를 근거로 들었다.
- `sessionStorage`는 탭 단위이고 새로고침과 같은 탭 안의 화면 이동을 견딘다. FR-014가 요구한 행동과 그대로 맞는다. 로그인 왕복도 같은 탭 안의 이동이므로 유지된다.
- 서버에 임시 저장하지 않는 것은 spec의 가정 때문이다. 섹터·비중 선택은 사용자 식별 없이 가능해야 하는데(spec.md의 Assumptions), 서버 저장은 식별자를 요구하거나 익명 식별자를 새로 만들게 된다.
- 읽어 온 값을 검증하는 까닭은 `sessionStorage`가 사용자가 편집할 수 있는 저장소이기 때문이다. 검증 없이 상태에 넣으면 목록에 없는 코드나 음수 비중이 그대로 003·004로 흘러간다.

**Alternatives considered**:

- **`localStorage`**: 탭을 닫아도 남아야 한다면 맞지만, SC-006이 "탭을 닫고 새 탭으로 들어왔을 때 값이 남은 사례 0건"을 요구한다. 기각.
- **URL 쿼리 문자열**: 새로고침과 공유를 견딘다. 그러나 선택과 비중이 URL에 드러나 링크가 '추천 비중'처럼 읽힐 여지가 생기고(원칙 III), 외부에서 주입한 값을 화면이 그대로 받게 되어 검증 부담이 커진다. 기각.
- **React Router의 navigation state만 사용**: 새로고침에서 사라져 FR-014를 만족하지 못한다. 기각.
- **서버 임시 저장**: 위 Rationale의 식별 문제와 충돌한다. 기각.

## 결정 4: 상장일 기준 공통 비교 시작일은 화면이 구한다. 002는 백엔드 작업을 만들지 않는다

**문제**: FR-008의 안내에는 "언제부터 비교 가능한가"가 필요하다. 001에는 이미 `GET /sectors/evaluation-window`와 [공통 평가 기간 산식](../001-etf-market-data/contracts/evaluation-window.md)이 있는데, 그 산식은 워밍업 거래일 수를 필수 입력으로 받는다. 이 값을 002가 쓸 수 있는지에 따라 002가 백엔드 작업 없이 끝나는지가 갈린다.

**Decision**: 002는 `GET /sectors/evaluation-window`를 **부르지 않는다.** 화면이 `GET /sectors` 응답만으로 다음 두 값을 구한다.

```
commonStartFromListing = max(선택 섹터의 representativeEtf.listedOn)
bindingSectorCode      = 그 최댓값을 만든 섹터
```

안내 문장은 이 값이 **상장일만 반영한 시작일**이며 전략을 고른 뒤 워밍업 때문에 더 늦어질 수 있다는 사실을 함께 담는다. 워밍업 몫의 안내는 [003 FR-011](../003-strategy-settings/spec.md)이 소유한다. 결과적으로 002는 새 엔드포인트도, 기존 엔드포인트의 변경도 요구하지 않으므로 `backend/`·`worker/`·`data/` 변경이 없다.

**Rationale**:

- `GET /sectors/evaluation-window`의 요청은 `?sectors=...&strategy=...` 형태이고([001 contracts/sector-api.md](../001-etf-market-data/contracts/sector-api.md)), 산식의 첫 줄이 `warmup = max(strategies[].warmupTradingDays)`다. 워밍업 거래일 수는 003이 소유하는 전략 등록표의 값이므로, 전략을 고르기 전인 002에서는 입력을 채울 수 없다. spec.md의 Clarifications가 같은 근거로 002의 안내 범위를 상장일 차이 하나로 좁혔다.
- 재료는 이미 화면에 있다. `GET /sectors`가 섹터마다 `representativeEtf.listedOn`을 주므로 최댓값을 구하는 데 추가 호출이 필요 없다.
- 두 값이 어긋날 위험이 없다. 001 산식에서 `warmupTradingDays = 0`이면 `firstEvaluable = listedOn`이라고 명시되어 있어(evaluation-window.md의 경계 동작), 002가 구하는 값은 그 산식의 특수한 경우와 정확히 같다. 002가 다른 규칙을 새로 만드는 것이 아니다.
- 화면이 거래일 달력을 다루지 않아도 된다. 워밍업이 0이면 거래일 수를 세는 부분이 사라지고 날짜 최댓값만 남는다.

**경계 동작**: 선택 섹터가 두 개 미만이거나 상장일이 모두 같으면 "기간이 줄어든다"는 사실이 없으므로 안내를 내지 않는다. spec.md의 Edge Cases가 적은 "공통으로 비교할 수 있는 기간이 아예 남지 않는" 경우는 `commonStartFromListing`이 오늘(브라우저 기준 날짜) 이후일 때로 판정한다. **이 판정은 근사치다.** 정확한 판정에는 자료 마감일이 필요한데 `GET /sectors` 응답에 `dataDeadline`이 없고, 상장폐지일은 아예 응답에 없어 spec이 Out of Scope로 뺐다. 정확한 판정은 003이 `evaluable: false`로 받는다. 현재 계약에서 이 경로에 도달하려면 아직 상장하지 않은 ETF가 대응표에 실려야 하므로 실제로는 거의 일어나지 않지만, 화면이 음수 기간을 계산해 이상한 문장을 만들지 않도록 방어한다.

**Alternatives considered**:

- **002가 `GET /sectors/evaluation-window`를 워밍업 0으로 부른다**: 산식을 한 곳에 둘 수 있다. 그러나 `strategy` 파라미터가 필수이고, 002가 아무 전략이나 골라 넣으면 그 전략의 워밍업이 반영된 값을 받아 상장일만 반영한 값이 아니게 된다. 계약을 넓히면 001 변경이 필요하다. 기각.
- **001에 워밍업 없는 전용 엔드포인트를 요구한다**: 계산 위치가 하나로 모인다. 그러나 최댓값 하나를 얻으려고 왕복을 하나 더 만들고, 001의 계약과 백엔드·워커 양쪽 구현을 넓혀야 한다. 002가 얻는 값은 이미 손에 있는 필드의 최댓값이다. 기각.
- **안내를 003으로 미룬다**: 백엔드 작업이 확실히 없다. 그러나 SC-003과 User Story 3이 선택 단계의 안내를 요구하고, 결과 화면에서 처음 알게 되는 일을 막는 것이 이 요구사항의 목적이다. 기각.

## 결정 5: 첫 화면은 기존 `/`의 `LandingPage`를 개편하고, 섹터·비중 화면은 새 경로에 만든다

**문제**: `frontend/src/App.tsx`에는 이미 `/`(LandingPage), `/home`, `/dashboard`, `/backtest`, `/param-search`, `/records/*`, `/login`, `/signup`과 나머지를 `/`로 보내는 경로가 있다. FR-001이 요구하는 첫 화면이 이 중 어느 것인지, 002가 기존 화면을 대체하는지가 정해져 있지 않다.

**Decision**: 세 가지로 나눈다.

1. **첫 화면은 `/`의 `LandingPage`를 개편해 만든다.** 새 경로를 만들지 않는다. 개편 내용은 주요 메뉴 '전략 진단 / 시장 흐름 / 배우기'와 보조 메뉴 '내 기록'을 모두 보이게 하고, 가장 중요한 행동 버튼을 '전략 진단하기' 하나로 두는 것이다(FR-001).
2. **섹터·비중 화면은 새 경로 `/diagnosis/sectors`에 만든다.** 002는 한 화면이므로 경로도 하나다. 진단 흐름의 다음 단계가 같은 접두사 아래로 이어질 수 있게 `/diagnosis/` 아래에 둔다.
3. **기존 경로를 지우지 않는다.** `/backtest`·`/param-search`·`/home`·`/dashboard`·`/records`는 각각 003·007·009·006이 소유할 자리이므로 002가 정리하지 않는다. 메뉴의 목적지는 이미 화면이 있으면 그 경로로 연결하고(시장 흐름은 `/home`, 내 기록은 `/records`), 아직 화면이 없는 배우기는 `/learn`에 '준비 중' 화면을 두어 메뉴가 사라지지 않게 한다. 최종 목적지 확정은 각 소유 spec의 몫이다.

**Rationale**:

- `/`를 옮기면 기존 링크와 나머지 경로를 `/`로 보내는 규칙(`App.tsx`의 `path="*"`)이 모두 영향을 받는다. 첫 화면의 자리는 그대로 두고 내용만 FR-001에 맞추는 편이 변경 범위가 작다.
- 002가 기존 `LandingPage`를 통째로 버리지 않는 까닭은 FR-001이 요구하는 것이 메뉴 구성과 행동 버튼 하나이지 소개 문구의 제거가 아니기 때문이다. 다만 행동 버튼은 하나여야 하므로(원칙 II), 지금 화면에 여러 행동 유도가 있으면 '전략 진단하기' 하나만 남긴다.
- 섹터·비중 화면을 `/`에 합치지 않는 까닭은 SC-001이 세는 행동 때문이다. '전략 진단하기'가 한 번의 행동으로 세려면 누르기 전과 뒤의 화면이 달라야 한다.
- 메뉴를 숨기지 않는 것은 spec.md의 Clarifications가 낸 결론이자 FR-001·SC-008의 요구다.

**Alternatives considered**:

- **`/sectors`처럼 짧은 경로**: 입력이 짧다. 그러나 서버의 `GET /sectors`와 이름이 같아 문서에서 혼동되고, 003·005가 이어질 자리를 예고하지 못한다. 기각.
- **첫 화면과 섹터 선택을 `/` 한 화면에 합치기**: 화면 이동이 없어 빠르다. 그러나 첫 화면의 행동 버튼 하나 규칙과 SC-001의 행동 세기가 흐려진다. 기각.
- **`/backtest`를 002의 화면으로 재사용**: 새 경로가 안 생긴다. 그러나 그 화면은 003이 소유할 전략 선택 자리이고 지금은 모의 데이터로 동작한다. 002가 손대면 003의 범위를 미리 잠근다. 기각.

## 결정 6: '준비 중'과 409는 같은 표시 컴포넌트를 쓰되 행동 하나만 다르게 둔다

**문제**: FR-001은 아직 만들지 않은 메뉴를, FR-017은 대응표 미발행(409 `SECTOR_MAP_NOT_READY`)을 각각 "한 문장을 보이는 정상 화면"으로 처리하라고 요구한다. 두 상태가 같은 것인지 다른 것인지가 정해져 있지 않다.

**Decision**: 표시 방식은 공용 컴포넌트 하나(`NotReadyNotice`)로 통일하고, 그 컴포넌트는 **한 문장과 선택적인 행동 하나**만 받는다.

| 상태 | 화면 | 행동 |
|---|---|---|
| 아직 만들지 않은 메뉴 | `/learn` 등 전용 경로의 정상 화면 | 없음 |
| `GET /sectors`가 409 `SECTOR_MAP_NOT_READY` | `/diagnosis/sectors` 안의 목록 자리 | 다시 불러오기 하나 |
| `GET /sectors`가 네트워크 실패·5xx | 같은 자리 | 다시 불러오기 하나 |

409 상태에서는 섹터를 고를 수 없으므로 다음 단계 버튼을 두지 않는다(FR-017). 어느 경우에도 오류 경계(Error Boundary)나 빈 목록으로 떨어지지 않는다. 화면을 렌더링하는 분기는 예외가 아니라 상태 값이다.

**Rationale**:

- 두 상태의 공통점은 "아직 줄 것이 없다"이고, 원칙 VI는 그런 상태도 정상 화면 흐름으로 처리하라고 요구한다. 표시를 한 컴포넌트로 모으면 SC-008이 두 경우를 같은 기준으로 셀 수 있다.
- 차이는 재시도로 해소되는지 여부다. 409는 [001 계약](../001-etf-market-data/contracts/sector-api.md)이 "재시도 가능한 상태로 구분한다"고 적어 둔 상태이므로 다시 불러오기가 뜻이 있다. 아직 만들지 않은 메뉴는 다시 눌러도 바뀌지 않으므로 행동을 두지 않는다. 행동이 없을 때 버튼을 두면 원칙 II가 제한한 행동 버튼 수만 늘어난다.
- 네트워크 실패를 409와 같은 화면으로 처리하되 문장을 나누는 까닭은, 014가 `normalizeApiError`에서 `api | network | unexpected`를 이미 구분해 두었기 때문이다(`frontend/src/api/client.ts`). 같은 구분을 재사용하면 002가 오류 분류를 새로 만들지 않아도 된다.

**Alternatives considered**:

- **메뉴에서 아직 없는 화면을 숨기기**: 화면이 단순해진다. 그러나 FR-001과 SC-008이 명시적으로 금지한다. 기각.
- **409를 오류 화면으로 처리**: 구현이 짧다. 원칙 VI 위반이다. 기각.
- **두 상태에 서로 다른 컴포넌트를 두기**: 문구를 따로 다듬을 수 있다. 그러나 같은 규칙을 두 곳에서 관리하게 되고 한쪽만 고쳐질 위험이 있다. 기각.

## 결정 7: 안내 여섯 가지를 상시 표시와 조건부 표시로 나눈다

**문제**: 이 화면이 요구받은 안내는 초깃값 예시 표시(FR-005), 예시 대응표 표시(FR-015), 상장일 안내(FR-008), 후보 집합 뜻(FR-009), 0%의 뜻(FR-016), 합계 부족·초과(FR-007)로 여섯 가지다. 전부 동시에 보이면 원칙 II가 요구한 첫 화면 단순함이 무너진다. 덮어쓰기 확인(FR-012)도 화면 요소를 늘린다.

**Decision**: 아래처럼 나눈다. **문구 자체는 확정하지 않는다.** 정하는 것은 자리와 나타나는 조건이다.

| 안내 | 나타나는 조건 | 자리 |
|---|---|---|
| 초깃값이 예시이며 투자 권고가 아님 (FR-005) | 비중 입력 칸이 하나 이상 있을 때 항상 | 비중 입력 묶음의 머리 한 문장 |
| 섹터 목록이 예시 대응표에서 옴 (FR-015) | 응답의 `isSample`이 true일 때만 | 섹터 목록의 머리 한 문장 |
| 상장일 차이로 비교 시작일이 늦어짐 (FR-008) | 선택 섹터 두 개 이상이고 상장일이 서로 다를 때만 | 선택 요약 옆 한 문장 |
| 선택 섹터는 자동 전략의 후보 집합이며 사용자 비중은 '내가 정한 비중'에 쓰임 (FR-009) | 섹터를 하나 이상 고른 뒤 항상 | 비중 입력 묶음의 꼬리 한 문장 |
| 0%인 섹터의 뜻 (FR-016) | 비중이 0인 섹터가 하나 이상일 때만 | 같은 꼬리 자리에 한 문장 추가 |
| 합계 부족·초과와 남은 비중 (FR-007) | 합계가 1000이 아닐 때만 | 합계 표시 그 자리 |
| 예시 값 덮어쓰기 확인 (FR-012) | 배우기 예시로 진입했고 이미 입력한 섹터나 비중이 있을 때만 | 확인 대화상자 |

FR-005와 FR-015의 표시는 가리키는 대상이 다르므로(spec.md의 FR-015) 한 문장으로 합치지 않는다. 덮어쓰기 확인은 `radix-ui`의 대화상자 요소를 쓴다. 이미 의존성에 있고(`frontend/package.json`), 014의 인증 화면이 접근성 기준을 적용한 것과 같은 방식으로 초점 관리와 키보드 조작을 얻을 수 있다.

**Rationale**:

- 상시 표시는 둘(FR-005·FR-009)뿐이다. 나머지 넷은 조건이 성립할 때만 나타나므로, 조건을 만들지 않은 사용자는 안내 두 문장만 본다. 처음 방문한 사용자가 섹터 두 개를 동일 비중 그대로 쓰면 이 화면에서 보는 안내는 두 문장이다.
- 남은 비중을 "그 위치에" 표시하는 것은 원칙 VI와 FR-007이 직접 요구한 자리다. 별도 알림 영역으로 빼지 않는다.
- 덮어쓰기 확인을 상시 요소가 아니라 대화상자로 두는 것은 SC-011이 "입력이 하나도 없는 상태에서 진입했는데 확인을 물은 사례 0건"을 요구하기 때문이다. 조건이 성립할 때만 나타나야 한다.

**Alternatives considered**:

- **안내를 접어 두고 '자세히 보기'로 펼치기**: 화면이 가장 조용해진다. 그러나 원칙 II가 "결과 의미를 바꾸는 자료 부족·근거 부족 상태는 해당 결과 옆에 한 문장으로 표시하고 상세 안에만 숨기지 않는다"고 못 박았다. 상장일 안내가 여기 해당한다. 기각.
- **덮어쓰기 확인을 화면 안 배너로 두기**: 대화상자보다 방해가 적다. 그러나 사용자가 무시하고 진행하면 예시 값이 반영되지 않은 채로 남아 배우기에서 온 목적이 사라진다. FR-012는 "먼저 묻고" 답을 받으라고 요구한다. 기각.

## 결정 8: KRX 출처 표시는 화면에 두고, 계약 확장은 001에 남긴다

**문제**: 원칙 X는 "KRX 자료를 쓰는 화면에는 '한국거래소 통계정보' 출처를 표시한다"고 요구한다. 섹터 목록은 대표 ETF 이름과 상장일을 보이므로 여기 해당하는데, `GET /sectors` 응답에는 `sourceAttribution`이 없다. 그 필드는 `GET /sectors/{code}/instrument-profile`에만 있다.

**Decision**: 002는 두 가지를 한다. 첫째, 대표 상품 정보 패널에서는 응답의 `sourceAttribution` 값을 그대로 표시한다. 둘째, 섹터 목록 화면에는 같은 출처 문구를 화면 상수로 두어 표시한다. 상수는 한 곳(`src/diagnosis/` 아래)에만 두고, `GET /sectors`가 나중에 같은 필드를 주면 상수를 지우고 응답 값으로 바꾼다.

**Rationale**:

- 원칙 X는 조건 없이 표시를 요구하므로 미표시를 고를 수 없다. 상품 정보 패널을 펼쳐야만 보이는 구조는 목록만 보는 사용자에게는 미표시와 같다.
- 값을 지어내는 것은 아니다. 001이 이미 같은 문구를 고정 값처럼 내보내고 있고(계약의 예시 응답이 `"sourceAttribution": "한국거래소 통계정보"`다), 002는 같은 문구를 옮겨 적는다. 다만 문구의 소유가 계약이 아니라 화면 코드가 되는 것은 약점이므로 상수를 한 곳에 모으고 후속 조치를 남긴다.

**후속 조치**: `GET /sectors` 응답에 `sourceAttribution`을 더하도록 001에 제안한다. 계약 변경은 001이 소유하므로 002에서 고치지 않는다.

**Alternatives considered**:

- **목록 화면에서 출처를 생략하고 상품 정보 패널에만 두기**: 계약과 화면이 일치한다. 원칙 X 위반이다. 기각.
- **목록을 그릴 때 섹터마다 `instrument-profile`을 호출해 `sourceAttribution`을 얻기**: 값의 출처가 계약이 된다. 그러나 섹터 수만큼 호출이 늘고, 그 응답은 FR-010이 정한 펼쳐 보는 층의 자료다. 기각.

## 결정 9: 배우기 예시는 라우터 navigation state로 받는다

**문제**: FR-012는 배우기의 '이 예시로 전략 진단하기'로 진입하면 예시 섹터·비중이 채워져야 한다고 요구한다. [013 FR-003](../013-learning-pages/spec.md)이 그 연결을 소유하지만 013은 아직 만들지 않았으므로, 002가 받을 입구의 형태를 정해야 한다.

**Decision**: 예시 값은 React Router의 navigation state로 받는다. 002는 그 state를 한 번 읽고 소비한 뒤 `replace`로 지운다. 받은 값은 결정 3의 검증을 똑같이 거친다(현재 목록에 있는 섹터 코드, 0 이상 1000 이하 정수 비중). 페이로드 형태는 [contracts/selection-handoff.md](./contracts/selection-handoff.md)가 정의한다. 예시 내용 자체(어떤 주제가 어떤 섹터·비중을 쓰는가)는 013이 소유하며 002는 정하지 않는다.

**Rationale**:

- 이 값은 한 번의 이동에만 쓰이고 그 뒤에는 사용자의 입력이 된다. 이동에 실려 오는 값을 담는 자리가 navigation state다.
- 새로고침하면 state가 사라진다. 그때 사용자가 이미 덮어쓰기를 결정했다면 값은 세션 저장에 들어가 있어 남고, 아직 결정하지 않았다면 예시만 사라지고 원래 입력이 그대로 남는다. 둘 다 사용자 입력을 지우지 않는 방향이라 원칙 VI와 어긋나지 않는다.
- 쿼리 문자열을 쓰지 않는 까닭은 결정 3의 기각 사유와 같다. 비중이 담긴 링크는 공유되면 '추천 비중'처럼 읽힐 여지가 있고(원칙 III), 외부 주입 경로가 열린다.

**Alternatives considered**:

- **쿼리 문자열로 섹터·비중 전달**: 새로고침과 공유를 견딘다. 위 사유로 기각.
- **`sessionStorage`에 예시를 따로 써 두고 002가 읽기**: 새로고침을 견딘다. 그러나 예시를 쓰는 쪽(013)과 읽는 쪽(002)이 저장소 키를 공유하게 되어, 덮어쓰기 확인 전에 이미 저장소가 오염된다. 기각.
- **배우기가 002의 상태를 직접 세팅**: 화면 사이 경계가 사라진다. 기각.

## 결정 10: '동일하게 나누기'는 사용자 수정 여부를 초깃값 상태로 되돌린다

**문제**: FR-005는 "사용자가 비중을 한 번이라도 고친 뒤"와 아닌 경우를 나누고, 그 분기값이 Key Entities의 '비중 초깃값 표시 상태'다. FR-007의 '동일하게 나누기'를 누른 뒤 이 값이 어느 쪽이 되는지는 spec에 적혀 있지 않다. 이 값이 이후 섹터를 더할 때의 동작을 가르므로 정해야 한다.

**Decision**: '동일하게 나누기'를 누르면 선택 섹터 전체를 동일 비중으로 다시 채우면서 **사용자 수정 여부를 '고치지 않음'으로 되돌린다.** 따라서 그 뒤에 섹터를 더하거나 빼면 다시 전체가 동일 비중으로 채워진다.

**Rationale**:

- FR-007이 '동일하게 나누기'를 "되돌릴 수 있게 한다"로 적었다. 되돌린 결과가 초깃값과 값은 같은데 이후 동작만 다르면 그것은 되돌린 것이 아니다.
- SC-009는 "비중을 한 번 이상 고친 뒤 섹터를 추가한 모든 경우"를 세는데, 여기서 문제 삼는 것은 사용자가 만든 값이 말없이 바뀌는 일이다. 사용자가 스스로 초깃값으로 되돌린 뒤에는 지켜야 할 사용자 값이 없다.
- 반대로 두면 한 번 고친 사용자는 그 탭에서 다시는 자동 채움을 받지 못한다. 섹터를 늘릴 때마다 0%가 붙어 합계가 계속 100% 아래로 내려가고, 사용자는 '동일하게 나누기'를 매번 눌러야 한다. SC-001이 세는 행동 수가 늘어난다.

**Alternatives considered**:

- **수정 여부를 '고침'으로 유지**: 사용자가 한 번이라도 손댄 이력을 보존한다는 해석이다. 그러나 위 세 번째 사유로 기각.
- **'동일하게 나누기'에 두 가지 뜻을 나눠 담기(값만 되돌리기 / 상태까지 되돌리기)**: 버튼이 둘이 된다. 원칙 II와 충돌한다. 기각.
