# Quickstart: 섹터·비중 선택 검증

**Plan**: [plan.md](./plan.md) | **Contracts**: [contracts/](./contracts/README.md)

이 화면이 실제로 동작하는지 확인하는 절차다. 구현 코드는 담지 않는다. 각 시나리오는 spec의 Success Criteria 하나 이상을 검증한다.

## 사전 준비

```bash
cd frontend
npm install
npm run dev            # http://localhost:5173
```

화면이 부르는 서버 자원은 `GET /sectors` 하나와 대표 상품 정보 하나뿐이다. 두 엔드포인트는 백엔드의 `sector` 도메인이 내부 경로 `/sectors`로 이미 제공하고 있고(`backend/src/main/java/com/ssafy/thorp/sector/presentation/controller/SectorController.java:21`), 화면은 `apiClient`의 기본 `baseURL`인 `/api`를 거쳐 부른다. Vite 개발 서버가 `/api` 접두사를 떼어 백엔드로 넘긴다.

```bash
# 백엔드와 저장소를 함께 띄운다
docker compose -f docker-compose.dev.yml up -d postgres backend
curl -s localhost:8080/sectors | jq '{mapVersion, isSample, count: (.sectors | length)}'
```

대응표가 아직 발행되지 않았으면 이 호출이 `409 SECTOR_MAP_NOT_READY`를 낸다. 그 상태 자체가 시나리오 7의 검증 대상이므로 화면 개발을 막지 않는다.

## 시나리오 0: 새로 만든 테스트가 실제로 수집되는지 먼저 확인한다

**검증 대상**: 검증 장치가 조용히 꺼지지 않는 것

`frontend/vite.config.ts`의 `test.include`는 현재 `['src/**/*.test.tsx', 'src/api/auth.test.ts', 'src/auth/**/*.test.ts']`다. `.test.ts`는 열거된 두 경로만 수집하므로, `src/diagnosis/weights.test.ts` 같은 파일을 새로 만들어도 Vitest가 집어 가지 않는다. `npm run test:legacy`의 파일 목록에도 없어서 **실패하지 않고 그냥 실행되지 않는다.**

```bash
cd frontend
npm test 2>&1 | tail -20      # 수집된 파일 수와 통과·실패·skip 수를 본다
```

**기대 결과**

- `src/diagnosis/`의 테스트 파일이 수집 목록에 있다
- 일부러 틀린 단언을 하나 넣으면 실패한다. 실패가 나지 않으면 그 파일은 돌지 않은 것이다. 확인한 뒤 단언을 되돌린다
- `skipped` 수가 0이다

## 시나리오 1: 두 번의 행동으로 다음 단계에 도달한다

**검증 대상**: SC-001, FR-001, FR-002, FR-004

1. 저장된 상태가 없는 새 탭으로 `/`에 들어간다.
2. 주요 메뉴 '전략 진단 / 시장 흐름 / 배우기'와 보조 메뉴 '내 기록'이 모두 보인다. 가장 중요한 행동 버튼은 '전략 진단하기' 하나다.
3. '전략 진단하기'를 누른다. 설문·숙련도 분류·학습 수강 요구 없이 섹터 목록이 열린다.
4. 섹터 두 개를 고른다. 각 섹터에 50.0%가 채워지고 다음 단계 버튼이 활성된다.

**기대 결과**: 사용자가 한 행동은 '전략 진단하기'와 '섹터 선택' 두 가지다. 필수 입력은 섹터 선택 하나다. 섹터를 하나만 골랐을 때는 다음 단계로 넘어가지 않고 두 개 이상 필요하다는 안내가 보인다.

## 시나리오 2: 동일 비중 초깃값의 합계가 정확히 100%다

**검증 대상**: SC-009(초깃값 쪽), FR-005

```bash
cd frontend
npm test -- src/diagnosis/weights.test.ts
```

**기대 결과**: 선택 수 2~20 전부에서 합계가 정확히 `1000`이다. 3개면 `334 / 333 / 333`, 6개면 `170 / 166 × 5`, 7개면 `148 / 142 × 6`이다. 잔여분은 언제나 표시 순서상 첫 번째 섹터에 붙는다. 섹터를 고른 순서를 바꿔 같은 집합을 만들어도 결과가 같다.

화면에서도 확인한다. 섹터 3개를 고르면 `33.4% / 33.3% / 33.3%`가 보이고, 이 값이 예시이며 투자 권고가 아니라는 표시가 함께 보인다.

## 시나리오 3: 사용자가 입력한 비중을 시스템이 바꾸지 않는다

**검증 대상**: SC-002, FR-006, FR-007

1. 동일 비중이 채워진 상태에서 한 섹터의 비중을 올려 합계를 110%로 만든다.
2. 다른 섹터의 비중이 그대로인지 본다.
3. 합계 표시 자리에 초과가 얼마인지 보인다.
4. 다음 단계로 넘어가려 하면 합계를 맞춰야 한다는 한 문장이 보이고 값이 자동으로 조정되지 않는다.
5. 합계를 90%로 만들어 같은 것을 확인한다.
6. '동일하게 나누기'를 누르면 전체가 동일 비중으로 되돌아가고 합계가 정확히 100%가 된다.

**기대 결과**: 어느 단계에서도 사용자가 입력하지 않은 섹터의 값이 바뀌지 않는다. 소수 둘째 자리(`33.45`)를 입력하려 하면 값이 반올림되어 들어가지 않고, 입력 자체가 거부되면서 한 문장 안내가 보인다.

## 시나리오 4: 비중을 고친 뒤 섹터를 더하고 뺀다

**검증 대상**: SC-009, FR-005

| 단계 | 동작 | 기대 결과 |
|---|---|---|
| 1 | 섹터 3개 선택 (아직 안 고침) | 33.4 / 33.3 / 33.3 |
| 2 | 섹터 1개 추가 (아직 안 고침) | 전체가 25.0 × 4로 다시 채워진다 |
| 3 | 한 섹터를 40.0으로 수정 | 나머지는 그대로. 합계 115.0 |
| 4 | 섹터 1개 추가 | 기존 네 개의 값이 그대로이고 새 섹터만 0.0 |
| 5 | 섹터 1개 해제 | 남은 값 그대로. 합계가 100% 아래로 내려가면 부족 안내 |
| 6 | '동일하게 나누기' | 전체가 동일 비중. 이후 섹터를 더하면 다시 전체가 동일 비중으로 채워진다 |

6단계의 마지막 문장이 [research.md](./research.md) 결정 10이 정한 동작이다.

## 시나리오 5: 0%를 입력할 수 있다

**검증 대상**: SC-010, FR-016

1. 섹터 3개를 고른 뒤 한 섹터에 `0`을 입력한다.
2. 값이 거부되지 않고 0.0%로 남는다. 그 섹터가 선택 목록에서 빠지지 않는다.
3. 0%인 섹터의 뜻을 알리는 한 문장이 보인다.
4. 나머지 두 섹터로 합계를 100%로 맞추고 다음 단계로 넘어간다.

**기대 결과**: 003으로 넘어간 선택 섹터 목록에 0%인 섹터가 그대로 들어 있다. `sessionStorage`의 `thorp.diagnosis.sectorSelection`을 열어 `weightTenths: 0`인 항목이 남아 있는지 확인한다.

## 시나리오 6: 상장일 차이를 선택 단계에서 알린다

**검증 대상**: SC-003, FR-008

1. 대표 ETF 상장일이 서로 다른 섹터 두 개 이상을 고른다.
2. 언제부터 비교할 수 있는지와 어느 섹터의 상장일 때문인지 한 문장으로 보인다.
3. 그 안내가 데이터 입력이나 자료 공급원 선택을 요구하지 않는다.
4. 상장일이 같은 섹터들만 고르면 이 안내가 보이지 않는다.

**기대 결과**: 안내가 선택 단계에 있다. `GET /sectors` 외의 호출이 일어나지 않는다(브라우저 개발자 도구의 네트워크 탭으로 확인한다). 이 값은 상장일만 반영한 것이며 전략 워밍업 몫은 003이 알린다는 사실이 문장에 담겨 있다.

## 시나리오 7: 아직 줄 것이 없는 상태가 정상 화면으로 처리된다

**검증 대상**: SC-008, FR-001, FR-017

```bash
# 대응표가 발행되지 않은 상태를 만든다. 발행 상태라면 백엔드를 그 상태로 띄우거나
# 테스트에서 409 응답을 주는 스텁으로 확인한다
curl -s -o /dev/null -w '%{http_code}\n' localhost:8080/sectors    # 409 기대
```

**기대 결과**

- 섹터 화면에 빈 목록이나 처리되지 않은 오류 화면이 아니라 준비 중이라는 한 문장이 보인다
- 그 상태에서는 섹터를 고를 수 없고 다음 단계로 넘어가지 않는다
- 다시 불러오기 행동 하나가 있다
- 아직 만들지 않은 메뉴(배우기)를 열면 같은 형태의 한 문장이 보이고, 그 화면에는 행동 버튼이 없다
- 어느 경우에도 메뉴가 사라지지 않는다

## 시나리오 8: 탭 세션 동안 값이 유지되고 탭을 닫으면 사라진다

**검증 대상**: SC-006, FR-014

1. 섹터와 비중을 입력한다.
2. 새로고침한다. 값이 그대로다.
3. 로그인 화면을 거쳐 돌아온다. 값이 그대로다.
4. 탭을 닫고 새 탭으로 같은 주소에 들어간다. 값이 남아 있지 않다.

**기대 결과**: 2·3단계에서 100% 유지되고 4단계에서 0건 유지된다. 저장소를 막은 프라이빗 창에서도 화면이 오류로 막히지 않고 그 탭 안에서는 동작한다.

## 시나리오 9: 예시 대응표 표시가 조건대로만 보인다

**검증 대상**: SC-007, FR-015

| 응답의 `isSample` | 기대 결과 |
|---|---|
| `true` | 섹터 목록이 예시 대응표에서 왔다는 표시가 보인다 |
| `false` | 그 표시가 보이지 않는다 |

이 표시는 FR-005의 동일 비중 초깃값이 예시라는 표시와 가리키는 대상이 다르므로 서로 다른 자리에 있어야 한다. 둘이 한 문장으로 합쳐져 있으면 SC-007 위반이다.

## 시나리오 10: 배우기 예시로 들어올 때 기존 입력을 지키는지 확인한다

**검증 대상**: SC-011, FR-012

013이 아직 없으므로 테스트에서 navigation state를 직접 실어 확인한다. 페이로드 형태는 [contracts/selection-handoff.md](./contracts/selection-handoff.md)에 있다.

| 들어갈 때 상태 | 기대 결과 |
|---|---|
| 아무것도 입력하지 않음 | 묻지 않고 예시 값이 채워진다 |
| 섹터나 비중이 이미 있음 | 덮어쓸지 먼저 묻는다 |
| 위에서 '덮어쓰지 않음' 선택 | 기존 값이 그대로 남는다 |
| 위에서 '덮어씀' 선택 | 예시 값으로 바뀌고, 뒤로 가기나 새로고침에 확인이 다시 뜨지 않는다 |

## 시나리오 11: 화면에 없어야 할 입력이 없다

**검증 대상**: SC-005, FR-011

**기대 결과**: 이 화면에 계산식·자료 공급원·거리 함수·실험 식별자·서버 설정 입력 항목이 0개다. 처음에 바로 보이는 정보는 선택 섹터·비중·적용 ETF 이름뿐이다. 대표 상품 정보는 같은 화면에서 펼쳐 보며, 보려고 다른 화면으로 이동하지 않는다(FR-010).

## 전체 검증 명령

파트 검증 명령은 `frontend/CLAUDE.md`가 정한 것을 그대로 쓴다.

```bash
cd frontend
npm run lint && npm run build
npm test
```

`npm test`는 Vitest(DOM)와 Node 테스트를 차례로 돌린다. **통과 수만 보지 말고 수집된 파일 수와 `skipped` 수를 함께 본다.** 시나리오 0이 이 확인을 먼저 두는 까닭이다.
