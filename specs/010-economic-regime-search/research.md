## R1. 지표 자료를 어디서 읽는가 — 008 미구현

**결정**: `MacroIndicatorPort`(application/port) + `FixtureMacroIndicatorAdapter`(infrastructure).
008이 완성되면 어댑터만 PostgreSQL 조회 구현체로 교체한다. 010 운영 코드는 포트만 안다.

**근거**: 007이 003(전략 등록표) 없이 완성된 경로와 같다 — `ParameterRegistryPort` +
`ProvisionalFileParameterRegistry`로 만들고 003 완성 시 구현체를 바꾼다. 004도
`MarketMetadataPort` + `FixtureMarketMetadataAdapter`로 001 없이 만들었다. 저장소에 전례가 둘
있고 둘 다 교체 지점이 한 곳으로 모여 있다.

008 자신도 이것을 허용한다 — FR-022 *"인증키 발급 전이거나 자료를 이용할 수 없으면 명시된 예시
자료로 개발하고 예시 자료임을 화면에 표시한다."*

**포트가 돌려주는 것** (008 spec FR-006·FR-013·FR-014에서 그대로 옴):

| 메서드 | 돌려주는 것 | 근거 |
|---|---|---|
| `monthlySeries(indicatorId)` | 지표 하나의 월별 변환값 전 구간 (대상월 → 값) | 008 FR-006 |
| `rawSeries(indicatorId)` | 변환 전 원값 전 구간 | 008 FR-006 "원값과 변환 후 값을 모두 보존" |
| `registry()` | 지표 → 분야 매핑, 등록표 버전 | 008 FR-002·FR-003 |
| `baselineMonths()` | 분야별 T_g와 T_all | 008 FR-013 |
| `dataVersion()` | 현재 자료 버전 | 008 FR-009 |
| `publication(indicatorId, month)` | 그 값의 발표일 | 008 FR-007, 010 FR-031 |

**버린 대안**:
- *008을 먼저 만들고 시작* — 008은 인증키 확인과 통계표 코드 13개 조사가 선행이고 일정이 010 밖에
  있다. 010의 계산 규칙은 자료의 출처와 무관하게 성립하므로 기다릴 이유가 없다.
- *기존 `market` 도메인(지표 11개)을 빌려 쓰기* — 목적이 다르다. 그쪽은 화면 카드용 최신값 하나이고
  시계열이 없으며, 010이 입력으로 쓰면 안 되는 KOSPI·KOSDAQ·V-KOSPI200이 섞여 있다(spec FR-004).

**픽스처가 담는 것**: 17개 지표 × 월별 시계열. 규칙 검증에 필요한 모양을 일부러 심는다 —
① 정상 계열, ② 중간에 결측 구멍이 있는 계열(FR-005 연속 구간 판정), ③ 상수 계열(MAD=0 → IQR),
④ 상수이면서 IQR도 0인 계열('계산 불가'), ⑤ 시작 연도가 늦어 분야 T_g를 뒤로 미는 계열.
값은 지어낸 것이며 화면에 예시 자료임을 표시한다(008 FR-022).

## R2. 사전 계산을 어디서 돌리는가

**결정**: `data/` 파이프라인의 배치로 돌리고 결과를 PostgreSQL에 적재한다. Backend는 적재된 것을
읽어 HTTP로 내주기만 한다.

**근거**:
- 루트 `AGENTS.md` **"Backend는 계산하지 않는다"**. 사전 계산은 사용자 요청과 무관한 오프라인
  계산이라 이 원칙의 정확한 대상이다.
- `data/CLAUDE.md`의 적재 방향이 그대로 맞는다 — *"`raw/ → processed/ → PostgreSQL` 한 방향뿐이고,
  Backend·Worker가 읽는 곳은 PostgreSQL이다."* 008 수집도 `data/`에 두기로 했으므로(008 Assumptions)
  수집 → 사전 계산 → 적재가 한 파이프라인 안에서 이어진다.
- 중앙값·MAD·IQR·분위수는 pandas가 이미 가진 연산이다. 직접 구현하면 R6의 분위수 정의를 스스로
  지켜야 한다.

**버린 대안**:
- *Backend `@Scheduled`* — "Backend는 계산하지 않는다"를 정면으로 어긴다. 기존 Java ECOS 클라이언트를
  재사용할 수 있다는 이점이 있으나, 그 클라이언트는 009용 최신값 조회라 시계열에 쓸 수 없다.
- *`worker/`* — 워커는 `backtest.jobs`의 competing consumer이고 실행 1건 = 메시지 1건 모델이다.
  주기 배치를 얹으면 한 프로세스에 실행 모델 둘이 섞이고, 백테스트 처리량이 배치에 밀린다.

## R3. 사전 계산의 단위와 규모

**결정**: 사전 계산 단위는 **(자료 버전, 등록표 버전, 모델 버전) × 기준월 t × 모드(분야 7 + 종합 1)**
이다. 산출물은 그 조합마다 **검색 상태 + 표시 후보 최대 10개 + 각 사례의 분야별 거리·기여도 +
후보 집계(전체 후보 수·제외 사유별 건수)**다.

**단위가 기준월인 이유**: 척도 m·s가 `t-122 ~ t-3`에서 나온다(FR-005). 같은 후보월이라도 기준월이
다르면 m·s가 달라 z가 달라진다. 즉 **월별 z를 t와 무관하게 미리 계산해 둘 수 없다.** 이것을 놓치면
사전 계산 설계가 통째로 틀린다.

**규모** (자료가 1990-01부터라고 가정, T = 441개월):

```
기준월 후보      T - 63 ≈ 378       (앞 63개월은 척도 60 + 질의 3이 안 나온다)
모드             7 분야 + 1 종합 = 8
사전 계산 항목   378 × 8 ≈ 3,000 건
저장 행          3,000 × 최대 10 사례 ≈ 30,000 행

기준월 하나의 연산
  척도     17 지표 × 최대 120개월 정렬
  z        (질의 3 + 후보 ~190) × 17
  거리     후보 ~190 × 17 지표 × 3 시점 ≈ 9,700 절댓값 차
전체       ≈ 3.7M 기본 연산 — 단일 프로세스로 수 초
```

전량 재계산이 수 초이므로 **증분 갱신을 만들지 않는다.** 자료 버전이 바뀌면 전 구간을 다시 계산한다
(spec FR-030). 증분은 구현과 검증 비용만 늘리고 아끼는 시간이 없다.

**버린 대안**:
- *전체 후보의 거리를 전부 저장* — 378 × 190 × 8 ≈ 574,000행이 되는데 화면에 쓰이지 않는다. 표시
  후보 10개 밖의 거리는 재계산이 수 초라 저장할 값이 없다. FR-032가 기록하라는 "전체 후보"는
  **집계**(전체 후보 수·제외 사유별 건수)로 남긴다.
- *요청 시점 계산* — spec FR-030이 금지한다(SC-002a).

## R4. 소수 연산과 재현성

**결정**: 계산은 IEEE-754 double(pandas/NumPy 기본)로 하고, **저장은 문자열 decimal**로 한다.
거리·z·기여도는 **소수점 아래 12자리에서 반올림한 값을 저장**하고, 순위 결정과 동률 판정은
저장된 값으로 한다.

**근거**: SC-002가 재검색 100% 동일을, SC-003이 독립 계산과 허용 오차 안 일치를 요구한다. 계산을
double로 두면 합산 순서에 따라 마지막 비트가 흔들리고, 그 상태로 정렬하면 **거의 같은 두 후보의
순서가 실행마다 뒤집힌다**. 정렬 전에 한 번 반올림해 고정하면 그 흔들림이 순위에 닿지 않는다.
12자리는 거리 값의 크기(z 차이의 평균, 대개 0~5)에 비해 충분히 아래이고 double의 유효자릿수
(약 15~17자리) 안이다.

FR-012의 *"정확한 동률은 더 오래된 종료월을 우선한다"* 는 이 반올림된 값이 같을 때를 말한다 —
근사 동률을 동률로 보지 않는다.

저장 형식은 저장소 규약을 따른다 — `V2__backtest_result.sql` 규약의 *"decimal은 예외 없이 JSONB"*,
`NUMERIC` 컬럼은 scale을 임의로 정하고 넘는 값을 조용히 반올림하므로 쓰지 않는다.

**버린 대안**:
- *Python `Decimal`로 전 계산* — 중앙값·분위수·평균에 Decimal을 쓰면 pandas 벡터 연산을 버리게 되고,
  MAD의 분위수 보간에서 결국 정의를 직접 써야 한다. 얻는 정밀도는 12자리 반올림이 이미 덮는다.
- *반올림 없이 double 그대로 정렬* — 위의 순서 뒤집힘이 SC-002를 깬다.

## R5. 분위수 정의 — MAD·IQR

**결정**: IQR은 spec FR-006이 정한 대로 **선형 보간**(numpy 기본 `linear`)의 75분위 − 25분위다.
정규분포 보정 상수는 근사값이 아니라 **Φ⁻¹(0.75)를 실제로 계산해** 쓴다 —
s = MAD / Φ⁻¹(0.75), IQR 대체 시 s = IQR / (2·Φ⁻¹(0.75)).

**근거**: FR-005가 *"근사값 1.4826이며 **구현은 정확한 분위수 값을 쓴다**"* 라고 명시한다. 1.4826과
`1/Φ⁻¹(0.75)`는 5자리에서 갈리는데, R4의 12자리 반올림보다 위쪽이라 순위에 닿을 수 있다.
`scipy.stats.norm.ppf(0.75)`로 구한다.

분위수 방법을 spec이 지정한 이유는 방법마다 값이 다르기 때문이다(`linear`·`nearest`·`midpoint` 등).
적는 위치는 모델 버전이다 — 방법을 바꾸면 새 모델 버전이다.

**버린 대안**: *상수 1.4826·1.349를 그대로 쓰기* — spec이 명시적으로 배제했다.

## R6. 문턱 미교정(PD-09) 상태에서의 동작

**결정**: 검색 상태를 `NEAREST_ONLY`("가까운 순서만 제공·유사성 미판정")로 **고정**한다. 문턱
값을 코드에 두지 않고, 사례는 '최근접 참고 사례'로 표시한다.

**근거**: spec FR-020이 확정 전 동작을 이미 적었다. 007이 PD-12 미확정에서 전 후보를
`UNVALIDATED`로 둔 것과 같은 처리다 — 미확정을 실패로 만들지 않고, 그렇다고 통과로 만들지도 않는다.

교정이 끝나면 상태 `THRESHOLD_APPLIED`가 추가되고 FR-021(충족 사례 없음 안내)이 살아난다. 그때
이전에 `NEAREST_ONLY`로 기록된 검색은 표시를 유지한다(spec Edge Cases). 그래서 **검색 상태를 저장
값으로 두고 조회 시점에 다시 판정하지 않는다.**

## R7. 지표별 최소 유효 척도(PD-10) 미확정

**결정**: 010은 `MAD → IQR → 계산 불가` 세 단계만 구현한다. 지표별 임계값을 010 코드에 두지 않는다.

**근거**: PD-10 소유가 008이다(spec FR-007, 008 FR-015). 008 FR-015가 *"확정 전에는 등록표에 공표
정밀도만 기록하고 척도 판정은 010의 규칙에 맡긴다"* 라고 명시한다. 확정되면 `MacroIndicatorPort`의
등록표에 최소 유효 척도가 실려 오고, 010은 "s가 그 값보다 작으면 계산 불가"를 한 줄 더하면 된다.

## R8. 비슷한 점·다른 점 문장 규칙

**결정**: 문장은 **템플릿 조립**이며 자유 생성하지 않는다. 지표별 `|z_질의 − z_후보|`가 큰 순으로
정렬해 위에서 **다른 점 최대 2개**, 작은 순으로 **비슷한 점 최대 2개**를 뽑고, 각각 실제 값과
단위를 넣어 조립한다.

```
비슷한 점:  "{지표명}은 {질의값}{단위}로 당시 {후보값}{단위}와 비슷합니다."
다른 점:    "{지표명}은 지금이 {질의값}{단위}로 당시 {후보값}{단위}보다 {높습니다|낮습니다}."
```

**근거**: spec Assumptions가 *"문장 규칙은 plan에서 정하고 **자유 생성 문장은 쓰지 않는다**"* 로
넘겼다. 자유 생성은 원인 단정("수출 부진으로 …")이나 확률 표현을 만들어 FR-022·US1 시나리오 4를
깬다. 템플릿은 그 두 가지가 구조적으로 들어갈 수 없다.

"높다/낮다"만 쓰고 "좋다/나쁘다"는 쓰지 않는다 — 실업률이 높은 것과 생산이 높은 것의 뜻이 반대이고,
그 해석은 010의 몫이 아니다.

**개수 2개인 이유**: spec이 든 예시가 *"실업률은 비슷하지만 소비자물가 상승률은 지금이 더 높습니다"*
로 양쪽 하나씩이다. 분야 안 지표가 2~3개뿐이라 2개면 대부분을 덮는다. 종합은 분야 단위로 같은
규칙을 적용한다(US3 시나리오 2 *"노동과 건설은 가깝지만 수출은 다릅니다"*).

## R9. 목표 응답 시간

**결정**: 검색 조회 응답 목표를 **p95 300ms**로 둔다. 사전 계산 배치에는 목표를 두지 않고 소요
시간을 기록만 한다.

**근거**: 조회는 사전 계산 항목 1건 + 표시 후보 10행을 읽는 인덱스 조회다. 004·007의 결과 조회와
같은 모양이라 같은 크기의 목표를 쓴다. 이 값은 **측정 목표이지 한도가 아니다** — 넘으면 인덱스를
보고, 값 자체를 성능 주장으로 쓰지 않는다(원칙 IX).

배치에 목표를 두지 않는 이유도 같다. R3의 추정(수 초)은 계산이지 실측이 아니므로, 실측 전에 목표로
제시하면 미측정 수치를 약속하는 셈이 된다. spec FR-033이 요구하는 것도 "기록"이지 "목표 달성"이
아니다.

## R10. 기존 `market` 도메인과의 관계

**결정**: 건드리지 않는다. 010은 backend에 **새 도메인 `regime`**을 만든다. 008이 만들 지표 저장소는
`macro` 자리이며 010은 `MacroIndicatorPort`로만 닿는다.

**근거**: `market`은 009 화면 카드용이고 지표 11개가 `MarketCode` enum·컨트롤러 메서드 11개·
`EcosMarketClient`의 switch 분기 셋에 나뉘어 하드코딩돼 있다. 010이 요구하는 것은 **버전이 붙은
데이터로서의 등록표**(008 FR-002·FR-003)라 구조가 다르고, 고치면 도는 화면 11개가 전부 영향을 받는다.
008 spec Out of Scope가 이 경계를 이미 적었다.
