# Quickstart: 내 기록 검증

**Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Contracts**: [contracts/](contracts/)

구현이 끝났는지 사람이 판정하는 절차다. 자동 테스트가 덮지 못하는 확인을 포함한다.

## 사전 조건

```bash
# 저장소 루트
docker compose -f docker-compose.dev.yml up -d postgres rabbitmq

# backend/.env 가 있어야 기동한다 (없으면 MAIL_USERNAME 플레이스홀더를 풀지 못한다)
./gradlew :backend:bootRun

# 워커 — 결과가 실제로 완료되어야 '다시 보기'를 확인할 수 있다
cd worker && python -m worker

cd frontend && npm run dev
```

**014가 먼저 동작해야 한다.** 006의 선행 조건은 세션 인증·현재 사용자 확인·`/records` 보호 경로이며
2026-09-18 현재 구현·계약 검증이 끝났다. 확인:

```bash
curl -i http://localhost:8080/my-records          # 401 AUTHENTICATION_REQUIRED 여야 한다
curl -i http://localhost:8080/auth/me             # 401
```

## 검증 명령

```bash
./gradlew spotlessApply build                      # backend. ArchUnit 이 myrecord 4계층을 판정한다
cd frontend && npm run lint && npm run build && npm test
```

`npm test` 결과의 **`skipped` 수를 확인한다.** 새 테스트 파일이 `vite.config.ts`의 `test.include`에
걸리지 않으면 실패하지 않고 조용히 수집되지 않는다(frontend/CLAUDE.md).

## 시나리오

### S1. 완료한 분석을 목록에서 찾아 다시 본다 (US1, FR-001·FR-006)

1. 로그인한 뒤 진단을 두 번 서로 다른 조건으로 완료한다.
2. `/records`를 연다.
3. **확인**: 두 항목이 이름·섹터·전략·분석 기간·저장일로 구분되어 보인다. 저장일 최신순이다.
4. **확인**: 항목의 주 모양 버튼은 **'다시 보기' 하나**다. '설정 바꿔 비교'는 보조 모양이다(R7).
   같은 크기 버튼 둘이면 원칙 II 위반이므로 고친다.
5. '다시 보기'를 누른다.
6. **확인**: 저장된 결과가 열리고 '동일 버전 조회'임이 보인다. 워커 대기열에 새 작업이 생기지
   않는다(RabbitMQ 관리 화면에서 확인). 재계산하면 FR-006 위반이다.
7. 상세를 펼친다. **확인**: 자료·대응표·등록표·비용 버전이 보인다.
8. **확인**: 어느 화면에서도 버전이나 실험 식별자를 입력하라고 요구하지 않는다(SC-004).

### S2. 저장 뒤 자료가 갱신돼도 결과가 같다 (SC-002)

1. S1의 결과 화면에서 핵심 숫자 3개를 적어 둔다.
2. 새 `dataset_version`을 적재한다(001 수집 파이프라인 또는 개발용 자료 갱신).
3. 같은 기록을 '다시 보기'로 다시 연다.
4. **확인**: 세 숫자가 1에서 적은 값과 같다. 다르면 저장된 결과가 아니라 다시 계산된 값이다.

### S3. 설정을 바꿔 새 분석으로 비교한다 (US2, FR-007·SC-003)

1. 기록 상세에서 '설정 바꿔 비교'를 누른다.
2. **확인**: `/strategy`가 열리고 저장된 섹터·비중·전략·파라미터·분석 조건이 채워져 있다.
   `sessionStorage`의 두 키를 개발자 도구에서 보고 `mapVersion`·`registryVersion`이
   **저장 당시 버전**인지 확인한다(현재 최신 버전이면 계약 위반, contracts/record-handoff.md).
3. 리밸런싱 주기만 바꿔 '분석하기'를 누른다.
4. **확인**: 완료 후 `/records`에 원본과 새 분석이 **별도 항목**으로 있다.
5. **확인**: 원본을 다시 열면 결과가 3 이전과 같다. 바뀌었으면 SC-003 위반이다.

### S4. 같은 조건을 다시 분석하면 새 기록이 생기지 않는다 (FR-009)

1. S3의 원본과 **완전히 같은 조건**으로 진단을 다시 완료한다.
2. **확인**: `/records`의 항목 수가 늘지 않고 기존 항목이 그대로 있다.
3. **확인**: DB에서 `SELECT count(*) FROM my_record WHERE owner_id = ? AND analysis_run_id = ? AND deleted_at IS NULL AND is_copy = false` 가 1이다.

### S5. 대응표가 바뀐 기록을 다시 연다 (UI-01, FR-008)

세 경우를 각각 확인한다. **판정은 서버가 하고 화면은 문자열을 비교하지 않는다.**

| 준비 | 기대 |
|---|---|
| 다른 섹터만 바뀐 새 대응표 버전을 발행한다 | `mappingDrift.changed: false`. **알림이 뜨지 않는다.** 상세의 참조 버전만 저장 당시 값으로 보인다 |
| 그 기록이 쓴 섹터의 대표 ETF를 다른 종목으로 교체한 버전을 발행한다 | `mappingDrift.changed: true`, `kind: INSTRUMENT_REPLACED`. 다시 보기에서 한 문장이 보인다 |
| 그 기록이 쓴 섹터를 목록에서 뺀 버전을 발행한다 | `kind: SECTOR_REMOVED`. '설정 바꿔 비교'에서 대체 섹터를 고르게 하되 **자동으로 바뀌지 않는다** |

첫 줄이 가장 중요하다. 버전 번호만 올랐을 때 알림이 뜨면 UI-01 결정과 원칙 II를 함께 어긴다.

### S6. 등록표 허용 범위 밖 값 (Story 2 시나리오 4)

1. `strategy_rules`의 어떤 축 허용 범위를 좁힌 새 등록표 버전을 발행한다(기존 기록의 저장값이 범위
   밖이 되도록).
2. 그 기록에서 '설정 바꿔 비교'를 누른다.
3. **확인**: 그 축이 **비어 있고** 이유와 기본값 복원 선택이 보인다. 값이 조용히 잘려 들어가 있으면
   FR-008 위반이다.
4. **확인**: 복원을 누르기 전에는 '분석하기'가 진행되지 않는다.

### S7. 탐색 묶음과 경제환경 기록 (US3)

1. 자동 탐색 한 번을 완료한다.
2. **확인**: `/records`에 묶음이 **한 항목**으로 보인다. 펼치면 후보별 결과·선정 이유·실패/제외 사유·
   후보 실행 상태와 탐색 공간·미실행 후보 수·정렬 및 선정 규칙이 보인다.
3. 부분 완료로 끝난 묶음을 만든다(실행 시간 한도를 낮춰 재현).
   **확인**: 부분 완료임과 완료 범위가 항목에 보인다.
4. 경제환경 검색을 **시장 흐름에서** 한 번, **전략 결과에서** 한 번 수행한다.
5. **확인**: 두 기록이 **별도 항목**으로 남는다. 한쪽이 다른 쪽을 대체하지 않는다(Story 3 시나리오 4).
6. **확인**: 연결 정보(연결한 섹터·전략·사후 평가 구간)는 "아직 연결 정보가 없다"로 보인다.
   **011이 없어 생산자가 없는 것이 정상이다**(R9). 임의의 값이 채워져 있으면 원칙 VI 위반이다.

### S8. 내보내기 (US4, FR-015·FR-016·SC-005)

1. 완료한 분석을 CSV와 JSON으로 각각 내려받는다.
2. **확인**: 설정값·참조 버전·핵심 결과·시계열·거래 내역·예외 처리 기록이 담겨 있다.
3. **확인**: `exclusions`가 **있다**(빠진 것이 없어도 키는 있다). 각 항목에 `item`·`reason`·`message`.
4. **확인**: 원천 일별 시세의 원값과 기사 본문이 **없다.** 필드 자체가 없어야 한다 —
   `grep -i "dailyPriceRaw\|articleBody"` 로 찾아 값이 비어 있는 키가 있으면 계약 위반이다(R10).
5. CSV를 한국어 Windows 표 계산 도구로 연다. **확인**: 한글이 깨지지 않는다(UTF-8 BOM).
6. 탐색 묶음을 내보낸다. **확인**: 탐색 공간·후보별 결과·상태·제외 사유·선정 규칙이 담긴다.

### S9. 이름 변경과 삭제 (US5, FR-017·SC-007)

1. 항목 이름을 바꾼다. **확인**: 목록의 이름만 바뀌고 다시 보기의 결과·참조 버전이 그대로다.
2. 다른 항목을 삭제한다. **확인**: 확인 절차를 거친 뒤 목록에서 사라진다.
3. **확인**: 삭제한 항목이 005의 비교 대상 목록과 경제환경 연결 대상에서도 선택되지 않는다.
4. **공용 결과가 남았는지 확인한다** — 이것이 2026-09-18 명료화의 핵심이다.

```sql
-- 삭제한 기록의 run 이 그대로 있고 결과·거래도 남아 있어야 한다
SELECT deleted_at IS NOT NULL AS record_deleted FROM my_record WHERE record_id = 'MR-…';
SELECT count(*) FROM backtest_result WHERE run_id = :runId;   -- 0 이면 안 된다
SELECT count(*) FROM backtest_trade  WHERE run_id = :runId;   -- 0 이면 안 된다
```

5. **다른 사용자로 같은 조건의 분석을 미리 만들어 두고** 위 삭제를 한 뒤 그 사용자로 로그인해
   '다시 보기'를 누른다. **확인**: 정상적으로 열린다. 열리지 않으면 SC-007 위반이다.
6. **확인**: 복구 경로가 화면에 없다.

### S10. 탐색 묶음 저장 상한 (FR-018, R11)

1. 설정값을 2로 낮춰 기동한다.
2. 탐색을 두 번 완료한 뒤 세 번째를 시작한다.
3. **확인**: 시작 **전에** 현재 개수와 상한이 보이고 거절된다(`409 RECORD_LIMIT_REACHED`).
4. **확인**: 기존 항목이 지워지지 않았다.
5. **확인**: 계산이 시작되지 않았다(RabbitMQ 대기열에 새 작업 없음). 계산 뒤에 막으면 자원이 버려진다.

### S11. 자동 삭제가 없다 (PD-13, 2026-09-18 명료화)

1. 저장소 전체에서 만료·정리 배치를 찾는다.

```bash
grep -rn "my_record" --include=*.java backend/src/main/java | grep -i "schedul\|expire\|cleanup\|purge"
```

2. **확인**: 결과가 없다. `my_record`를 지우는 스케줄러·배치가 있으면 이번 결정 위반이다.
3. **확인**: `saved_at`·`last_viewed_at`은 채워진다(나중에 보관 기간을 도입할 수 있게).
   `last_viewed_at`은 '다시 보기'를 누를 때 갱신된다.

### S12. 비로그인 경계 (FR-020, 014 연계)

1. 로그아웃 상태로 `/records`를 연다. **확인**: 로그인 안내가 보이고 기록이 보이지 않는다.
2. 로그인한다. **확인**: 원래 가려던 `/records` 위치로 돌아온다(014 FR-011).
3. 로그아웃 상태로 진단을 진행하다 저장이 필요한 지점에 이른다.
   **확인**: 식별 안내가 나오고 **진단 중인 입력이 유지된다**(014 FR-017).
4. 세션을 강제로 만료시킨 뒤 `/records`에서 항목을 연다.
   **확인**: 보호 정보가 숨고 재로그인 안내가 나온다. 재로그인 후 만료 전 위치로 돌아온다(014 FR-012).
   **빈 기록으로 표시되면 안 된다.**

### S13. 목록 기본 보기와 필터 (FR-004, R13)

1. 실패한 분석과 취소한 분석을 각각 하나 만든다.
2. **확인**: 기본 보기에 그 둘이 보이지 않는다.
3. 상태 필터로 실패·취소를 켠다. **확인**: 상태와 사유가 함께 보이고 **낮은 수익과 다른 자리**에 있다.
4. **확인**: 정렬 선택지에 수익률·하락 폭·비용이 **없다**(원칙 III, R7).
5. **확인**: 목록 응답 본문에도 성과 수치가 없다(개발자 도구 네트워크 탭).

### S14. 사용성 관찰 (SC-006, PD-14)

구현 검증이 아니라 별도 항목이다. 전략을 검증하려는 개인 6~8명에게 설명 없이 "이전 분석을 다시 열고
조건을 바꿔 비교하기"를 준다. 두 명 이상이 같은 단계에서 막히면 목록·동작 이름을 고친다.

**이 관찰을 통과하지 않은 상태를 "효과가 입증됐다"로 쓰지 않는다**(constitution 완료의 정의).

## 확인하지 않는 것

| 항목 | 이유 |
|---|---|
| 보관 기간 만료 동작 | 자동 삭제를 만들지 않기로 했다(2026-09-18 명료화). 확인할 동작이 없다 |
| 경제환경 기록의 연결 섹터·전략·사후 평가 구간 값 | 생산자([011](../011-regime-strategy-link/spec.md))가 없다. 자리만 있고 비어 있는 것이 기대 상태다(R9) |
| 삭제된 분석을 참조하던 기록의 표시 | 들어오는 참조를 만드는 곳이 `my_record_regime_link.linked_record_id` 하나이고 그 생산자가 011이다. 규칙은 구현하되 **발생 조건이 아직 없다.** 구현했다는 사실을 검증됐다는 뜻으로 쓰지 않는다 |
| 목록·내보내기 응답 시간 목표 | 원칙 IX가 실측 후 고정하도록 정했고 PD-06이 그 항목을 소유한다 |
| 탐색 묶음 상한의 확정값 | PD-13 미확정. 확인하는 것은 장치이고 값이 아니다 |
