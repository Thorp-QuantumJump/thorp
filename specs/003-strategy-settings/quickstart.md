# 확인 절차: 전략 선택·상세 설정

**Spec**: [spec.md](spec.md) | **Contracts**: [strategy-registry-api.md](contracts/strategy-registry-api.md) | **Date**: 2026-09-15

이 기능이 실제로 동작하는지 확인하는 절차다. 구현 방법은 여기에 적지 않는다.

## 준비

```bash
cd backend && ./gradlew spotlessApply build
```

```bash
cd frontend && npm run lint && npm run build
```

등록표는 자원 파일에서 읽으므로 이 확인에 데이터베이스가 필요하지 않다. 분석 요청까지 이어 보려면 [004](../004-backtest-execution/spec.md)의 준비가 함께 필요하다.

## 1. 등록표가 옮겨진 뒤에도 007이 그대로 도는가

**가장 먼저 확인한다.** 등록표는 지금 007이 실제로 쓰고 있어, 옮기다 깨지면 자동 탐색이 먼저 멈춘다.

```bash
cd backend && ./gradlew test --tests '*ParamSearch*'
```

기대: 옮기기 전과 같은 결과. 실패하면 [strategy-registry-internal.md](contracts/strategy-registry-internal.md) §4의 순서를 어긴 것이다.

```bash
cd backend && ./gradlew test --tests '*ArchitectureTest*'
```

기대: 통과.

**규칙을 더하는 것만으로는 확인이 되지 않는다.** 지금 규칙은 계층 사이만 검사하고 도메인 사이의 방향을 보지 않으므로 `strategy → paramsearch` 역방향을 막는 규칙을 이 작업에서 더하는데, 통과만 보면 그 규칙이 아무것도 잡지 않아도 통과한다.

규칙을 더한 뒤 **일부러 어겨 본다**. `strategy` 안의 아무 클래스에 `paramsearch`의 타입을 import하는 한 줄을 넣고 다시 돌린다.

기대: **실패한다.** 통과하면 규칙이 동작하지 않는 것이다. 확인한 뒤 그 한 줄을 지운다.

## 2. 등록표를 조회할 수 있는가

PD-02가 2026-09-15 확정([S15P21E205-254](https://ssafy.atlassian.net/browse/S15P21E205-254), [data-model](data-model.md) §4-2)됐으므로 T017로 실제 제품 등록표를 채운 뒤 이 수동 확인을 수행한다.

서버를 띄우고:

```bash
curl -s 'http://localhost:8080/strategies/registry?universeSize=3' | jq '.registryVersion, .provisional, [.strategies[].strategyId]'
```

기대:
- `registryVersion`이 비어 있지 않고 확정한 제품 등록표 버전과 같다
- `provisional`이 `false`다. `PROVISIONAL-` 응답과 `true` 표시는 기존 007 값 이관·합성 픽스처 경로에서 별도로 검증한다
- 활성 전략 다섯이 실린다

로그인하지 않은 상태에서도 200이 와야 한다. 전략 진단은 비로그인 이용을 허용한다.

## 3. 유효성 제약이 미리 걸러지는가

```bash
curl -s 'http://localhost:8080/strategies/registry?universeSize=2' \
  | jq '.strategies[] | select(.strategyId=="SECTOR_MOMENTUM") | .axes[] | select(.name=="topN") | .choices'
```

기대: 섹터가 둘이므로 등록된 선정 수 후보(`[2, 3, 4]`, PD-02 확정값) 중 2를 넘는 3·4가 `selectable: false`로 실리고 목록에서 사라지지 않는다. 단, `selectionMode`가 `TOP_N`일 때만 `topN` 축이 열린다 — 이 확인은 기본값(`selectionMode=TOP_N`) 기준이다.

```bash
curl -s 'http://localhost:8080/strategies/registry?universeSize=3' \
  | jq '.strategies[] | select(.strategyId=="MINIMUM_VARIANCE") | .validationRules'
```

기대: `MAX_WEIGHT_TOO_LOW_FOR_UNIVERSE` 규칙이 `left`·`operator`·`right`와 함께 실린다.

**이것은 규칙 목록이지 위반 판정이 아니다.** `universeSize`가 몇이든 규칙은 항상 실린다. 위반은 사용자가 상한에 특정 값을 넣었을 때 생기며, 그 확인은 아래 5-1에서 한다. 최소분산의 기본 상한은 40이라 섹터 3개에서도 120이 되어 기본값으로는 위반이 아니다.

## 3-1. 비활성 전략이 목록에서 빠지는가

등록표에서 전략 하나에 `active: false`를 넣고 서버를 다시 띄운다.

```bash
curl -s 'http://localhost:8080/strategies/registry' | jq '[.strategies[].strategyId]'
```

기대: 그 전략이 목록에 **없다.** `selectable: false`로 실리는 것과 다르다 — 비활성은 아예 빠지고, `selectable: false`는 실리되 고를 수 없는 것이다.

확인한 뒤 `active: false`를 되돌린다.

## 4. 화면이 두 번의 행동으로 분석을 시작하는가 (SC-001)

1. 섹터를 셋 고르고 비중을 확정한 뒤 전략 선택 화면으로 넘어간다.
2. 다섯 카드가 이름과 한 줄 설명만으로 보이는지 확인한다. 세부 설정이 보이면 안 된다.
3. 카드 하나를 고른다.
4. '기본 설정'으로 표시되는지, 기간·금액·비용 한 줄이 보이는지 확인한다.
5. '분석하기'를 누른다.

기대: 상세 설정을 한 번도 열지 않고 분석이 시작된다. 기본 화면에 보이는 입력은 전략 선택 하나다(SC-005).

## 5. 목록형과 입력형이 제대로 그려지는가

'변동성에 따라 나누기'를 고르고 상세 설정을 연다.

| 항목 | 기대 |
|---|---|
| 변동성 관측 기간 | 후보 목록에서 고른다. 등록되지 않은 값을 넣을 방법이 없다 |
| 리밸런싱 주기 | 후보 목록. 월말 같은 달력 기준과 21거래일 같은 거래일 수 기준이 함께 보인다 |
| 비중 상한 | 값을 직접 입력한다 |

비중 상한에 허용 범위 밖의 값(예: 5)을 넣는다.

기대: 허용 범위를 안내하고 **값을 저장하지 않는다.** 10으로 잘라 넣지 않는다(FR-006).

## 5-1. 규칙을 어긴 값을 화면이 그 자리에서 막는가 (SC-003)

**범위 안이지만 규칙을 어기는 값**을 확인한다. 5절의 범위 밖 값과는 다른 경로다.

섹터를 **셋** 고른 상태에서 '변동성에 따라 나누기'의 비중 상한에 **30**을 입력한다. 30은 허용 범위(10~100) 안이지만 30 × 3 = 90이라 투자 비중을 채울 수 없다.

기대:
- 경고가 **입력 즉시** 보인다. '분석하기'를 누른 뒤가 아니다
- 문구는 등록표의 `detail`을 그대로 쓴다. 화면이 문장을 지어내지 않는다
- '분석하기'를 누를 수 없다
- **34로 고치면** 경고가 사라지고 '분석하기'가 살아난다(34 × 3 = 102)

서버에 요청이 나가지 않는지도 함께 본다. 값을 만질 때마다 왕복하면 [research](research.md) R7-1에서 기각한 방식이 된 것이다.

**서버도 막는지 확인한다.** 화면을 거치지 않고 같은 설정으로 분석 요청을 직접 보낸다.

기대: 422 `VALIDATION_RULE_VIOLATED`. 화면 검증을 우회해도 분석이 시작되지 않는다(FR-006).

## 6. '기본 설정' 표시가 값과 함께 움직이는가

1. 상세 설정에서 값을 하나 바꾼다 → 표시가 '설정을 바꿈'으로 바뀐다.
2. '기본값 복원'으로 모두 되돌린다 → 표시가 '기본 설정'으로 돌아온다.

이 표시는 사용자가 켜고 끄는 항목이 아니다(FR-002).

## 7. 워밍업 판정이 설정을 따라 다시 도는가

상장이 늦은 섹터를 섞어 공통 평가 가능 범위가 짧아지게 만든 뒤:

1. 카드 목록에서 각 전략의 기본 설정 기준 판정을 확인한다.
2. '변동성에 따라 나누기'를 고르고 관측 기간을 252거래일로 늘린다.

기대: 기본 설정으로는 고를 수 있던 전략이라도 워밍업이 길어져 평가 구간이 사라지면 그 자리에서 다시 판정해 알린다(FR-011).

워밍업을 채우고 구간이 남기만 하면 막지 않고 줄어든 기간만 알린다. 워밍업조차 못 채우면 카드를 고를 수 없다. **두 상황을 구분하는지 확인한다.**

### 7-1. 축이 둘인 워밍업이 제대로 더해지는가

역변동성은 축이 하나(`[lookbackDays]`)라 이것만으로는 `sum` 배열을 검증할 수 없다. **섹터 모멘텀으로 확인한다** — `[lookbackDays, skipRecentDays]` 둘을 더한다.

1. '흐름을 따라 배분하기'를 고르고 관측 기간을 60거래일, 최근 구간 제외를 0으로 둔다.
2. 이 상태의 워밍업이 60인지 확인한다.
3. **관측 기간은 그대로 두고 최근 구간 제외만 21로 바꾼다.**

기대: 워밍업이 **81로 늘어난다.** 카드 판정과 줄어든 기간 안내가 그 값으로 다시 계산된다.

**늘어나지 않으면 `sum`의 둘째 항목을 읽지 않는 것이다.** 첫 설계(`{basis, plus}`)가 이 경우를 담지 못해 바꾼 것이므로([research](research.md) R4), 이 확인을 건너뛰면 같은 결함이 되살아나도 알 수 없다.

### 7-2. 최소 평가 기간을 사용자가 고르면 그 값으로 다시 판정하는가 (FR-011a)

공통 평가 가능 범위가 워밍업을 뺀 뒤 1년보다 조금 더 남게 섹터를 섞은 뒤:

1. '기간·금액·조건'에서 최소 평가 기간을 기본(1년)으로 둔 채 카드가 선택 가능한지 확인한다.
2. 최소 평가 기간을 엄격(3년)으로 바꾼다.

기대: 같은 워밍업·같은 공통 평가 가능 범위인데도 카드가 선택 불가로 바뀌고 이유가 "최소 평가 기간(3년)에 못 미칩니다" 식으로 보인다. 완화(제한 없음)로 바꾸면 다시 선택 가능해진다.

## 8. 설정값이 탭 수명만큼 남는가 (SC-007)

1. 전략과 상세 설정을 정한다.
2. 화면을 새로 고친다 → 값이 그대로 남아 있다.
3. 섹터 선택 단계로 돌아갔다 다시 온다 → 값이 남아 있다.
4. 탭을 닫고 다시 연다 → 기본값 상태로 시작한다.

전략 카드를 옮겼다 돌아오면 그 전략의 값이 살아 있고 다른 전략에 적용되지 않는지도 확인한다.

## 9. 등록표를 받지 못하면 막히는가 (SC-008)

서버를 내리거나 등록표 파일을 읽지 못하게 만든 뒤 화면을 연다.

기대:
- 전략 카드를 하나도 고를 수 없다
- 불러오지 못했다는 안내와 다시 시도할 방법이 보인다
- '분석하기'와 '설정 조합 자동 비교' 어느 쪽도 누를 수 없다
- 임시 값이나 예비 등록표로 대신 동작하지 않는다

## 10. 등록표 버전이 바뀌면 알리는가

1. 화면을 연 채로 등록표 버전을 올려 서버를 다시 띄운다.
2. '분석하기'를 누른다.

기대: 409 `REGISTRY_VERSION_CHANGED`로 거절되고, 화면이 등록표를 다시 조회해 바뀐 사실을 알린다. 조용히 새 버전으로 실행하지 않는다.

## 11. 자동 비교로 전략 하나만 넘어가는가

전략 하나를 고르고 '설정 조합 자동 비교'를 누른다.

기대: 그 전략과 섹터 후보 집합이 고정된 채 [007](../007-auto-parameter-search/spec.md)의 실행 전 확인 화면이 열린다. **다른 전략이 함께 넘어가지 않는다.**
