# Thorp Spec 색인

Thorp 퀀트 전략 분석 플랫폼의 현재 개발 범위(기획서 §8.1)를 기능 단위 spec 13개로 나누고, §8.1 기능이 아니라 그 기능들이 요구하는 기반 spec 1개(014 사용자 인증)를 더한 색인이다. 각 spec은 `specs/NNN-name/spec.md`에 있고, 이 문서는 spec 사이의 관계·우선순위·팀이 확정해야 할 결정 항목·공통 가정·범위 밖 항목을 한 곳에 모은다. 개별 spec의 내용을 여기서 다시 정하지 않는다.

**근거 문서**: Notion 기획서 "Thorp - 퀀트 전략 분석 플랫폼"(2026-09-09 18:03 UTC 편집판, 2026-09-10 조회)과 [constitution v1.0.0](../.specify/memory/constitution.md). 기획 근거는 절 번호(§), 결정 번호(D01~D27), 미확인 검증 항목(U01~U06)으로 인용한다. 최상위 규칙은 constitution이며, spec과 충돌하면 constitution을 따르고 spec을 고친다.

**이력**: 2026-09-10에 기획서 §8.1 전체를 담은 `001-thorp-platform` 하나로 초안을 썼고, 같은 날 spec 단위 재조정 요청에 따라 아래 13개로 분리했다. 원본의 요구사항·엣지 케이스·결정 항목은 모두 개별 spec 또는 이 문서로 옮겼다. 같은 날 006 내 기록이 요구하는 사용자 식별 흐름을 기반 spec `014-user-auth`로 추가했다.

## Spec 단위를 나눈 기준

- 한 spec은 사용자가 한 가지 목적으로 수행하는 기능 하나(예: 회원가입, 상품 검색, 주문 생성 크기)를 다룬다. 여러 기능을 묶은 영역 단위(예: '회원 기능')는 너무 크고, API 하나·화면 요소 하나(예: '이메일 중복 검사')는 task 크기라 spec으로 두지 않는다.
- 기획서가 사용자 흐름을 "섹터와 비중 정하기 → 전략과 설정 확인·분석 → 결과 이해·비교"의 세 단계로 나눈 것(§4.1)을 따라 전략 진단은 입력 두 단계(002·003), 실행(004), 결과(005)로 나눴다. 자료 확보(001·008)와 화면(002·009)은 서로 다른 팀(DATA/FRONT)이 맡는 다른 종류의 일이라 분리했다.
- 004 백테스트 실행은 가장 크지만 '분석하기' 한 번이라는 단일 사용자 행동의 접수·계산·결과 산출을 다루므로 '주문 생성(주문 생성·금액 계산·상태 생성)'과 같은 크기로 보고 나누지 않았다. 계산 규칙만 떼어내면 사용자 스토리가 없는 문서가 된다.
- 경제환경 검색(010)은 분야별 검색과 종합 비교를 한 spec에 두었다. 둘은 같은 모델의 두 모드이며 '상품 검색(키워드·필터·정렬·페이지네이션)'처럼 한 기능이다. 사례를 전략과 연결하는 011은 사용자·진입 경로·규칙이 달라 분리했다.
- 뉴스(012)와 시장 흐름 개요(009)는 같은 화면에 놓이지만 수집 파이프라인·이용 조건·공개 조건이 달라 분리했다.

## 흐름과 의존 관계

- **전략 진단 흐름**: 001 자료 → 002 섹터·비중 → 003 전략·설정 → 004 실행 → 005 결과 → 006 기록. 005의 '다른 조건으로 비교'와 006의 '설정 바꿔 비교'는 003으로 돌아간다.
- **자동 탐색**: 003의 진입점 → 007 탐색 묶음(004의 실행을 여러 개 묶어 쓴다) → 005에서 후보 비교, 006에 한 묶음으로 저장.
- **경제환경**: 008 지표 자료·기준월 → 009 시장 흐름 개요 → 010 검색(분야별·종합) → 011 사례와 전략 연결(004의 결과에서 사후 구간을 잘라 쓴다) → 006 기록. 011은 005의 '경제환경이 비슷했던 과거 보기'에서도 진입한다.
- **뉴스**: 012는 009의 기본 화면에 놓이고, 010·011의 사례 화면에 당시 뉴스를 연결한다.
- **배우기**: 013의 '이 예시로 비중 비교하기'는 002로 진입하고, 003·005의 용어 도움말이 013의 설명을 재사용한다.
- **사용자 인증**: 014는 006 내 기록의 진입 경계다. 비로그인 사용자가 '내 기록'에 접근하면 014의 로그인 흐름으로 보내고 성공 후 원래 위치로 돌려보낸다. 001~005·007~013의 공개 흐름은 014에 의존하지 않는다.
- **공통 축**: 004의 실행 측정 기록(실행 유형별 대기 시간·처리량·원가)은 007과 010의 실행도 함께 기록한다. 001과 008의 자료 버전, 003의 등록표 버전, 004의 비용 조건 버전은 006의 재현 기록이 참조한다.

## 우선순위

constitution 원칙 I(중심 약속은 전략 진단)에 따라 전략 진단 흐름(001~005, P1) → 내 기록과 자동 탐색(006·007, P2) → 경제환경 자료·탐색과 전략 연결(008~011, P3) → 뉴스·배우기(012·013, P4) 순이다. 경제환경 검색은 자동 탐색 완료 뒤에만 착수하는 종속 작업이 아니며(§8.1), 우선순위는 병렬 개발을 막지 않는다. 각 spec 안의 사용자 스토리 우선순위(P1~P3)는 그 spec 안에서의 순서다. 기반 spec 014는 006이 요구하는 사용자 식별을 제공하므로 006보다 늦지 않게 착수한다.

## 공통 화면 원칙

constitution 원칙 II(첫 화면은 단순하게)의 규칙은 모든 화면 spec이 자기 화면에 적용한다. 주요 메뉴 '전략 진단 / 시장 흐름 / 배우기'와 보조 메뉴 '내 기록', 화면마다 행동 버튼 하나, 정보 세 층 배치, 결과 첫 화면 구성, '자세히 보기'의 위치, 결과 옆 한 문장 상태 표시, 계산식·공급원·거리 함수·실험 식별자·서버 설정을 요구하지 않는 규칙이 여기에 속한다. 개별 spec은 이 규칙을 반복하되 여기서 새로 정하지 않는다.

## 공통 가정

- **이용 식별**: 전략 진단·시장 흐름·배우기는 사용자 식별 없이 이용할 수 있고, '내 기록' 저장·재조회는 식별된 사용자 단위로 동작한다. 인증·인가 방식은 constitution "합의되지 않은 영역"이므로 plan에서 근거를 남기고 정한다. 이 규칙의 소유 spec은 [014](014-user-auth/spec.md)이며 결정 근거는 [014 plan](014-user-auth/plan.md)과 [research](014-user-auth/research.md)에 있다. 다른 spec의 plan은 인증 방식을 다시 정하지 않고 014를 따른다.
- **이용 환경**: 한국어 웹 서비스이며 데스크톱 브라우저를 우선한다. 모바일 대응 범위는 plan에서 정한다.
- **계산 위치**: 백테스트·탐색·검색 계산은 서비스가 수행하고 사용자 기기에서 하지 않는다. 기준 백테스트 엔진은 constitution "계산·데이터 규칙"이 정한 엔진을 따르며 spec에서 다시 정하지 않는다.
- **자료 확보 전 개발**: 대표 ETF 목록과 인증키 기반 실제 조회가 확정되기 전에는 허용된 대체 자료·명시된 예시 자료로 개발한다. 예시 자료 사용은 결과 옆에 표시한다.
- **모델 v1 기본값**: 기획서 §6.4.4가 확정한 경제환경 모델 v1 수치는 그대로 적용한다. U01~U06 검증 결과에 따른 변경은 새 모델 버전으로만 제안한다.
- **기존 산출물과의 관계**: 현재 저장소는 단일 KRX 종목 모멘텀 백테스트 DEMO 상태다. 기존 API·메시지 스펙(`docs/specs/`)과 ADR(수수료 모델 등)은 이 spec들에 맞춰 갱신 대상이며, spec은 그 문서를 근거로 삼지 않는다.
- **분산 처리**: 기능 확대가 분산 Worker·Spark 도입을 뜻하지 않는다. 도입은 004의 실측 뒤 판단한다. 데이터 저장은 CLAUDE.md 아키텍처 원칙에 따라 Parquet 친화적으로 한다.
- **뉴스 공개 시점**: 시장 흐름 뉴스 묶음은 매체 허가 확인(PD-15) 회신 전에는 내부 환경에서만 검증하고 공개하지 않는다.
- **당시 재현 분석**: 거시 통계의 당시 발표·수정값(빈티지) 확보와 당시 재현 분석은 이번 범위가 아니다. 모든 경제환경 분석은 최신 개정자료를 이용한 역사 탐색이며 화면에 그렇게 표시한다.
- **법률 검토**: 투자자문·제품 출시 관련 법률 검토는 향후 고려사항이며 이번 개발의 선행 조건이 아니다. 현재 범위가 법적으로 비해당이거나 승인됐다고 단정하지도 않는다. (D13)

## Spec 간 정합 기록

여러 spec이 같은 자원(DB 마이그레이션 번호, 공유 계약 문서)을 건드릴 때 내린 결론을 여기에 남긴다. 개별 spec은 자기 문서에서 이 결론을 따르고, 여기서 다시 정하지 않는다.

### DB 마이그레이션 버전: 연속 번호 → 타임스탬프 (2026-09-11, 001 T002)

`backend/src/main/resources/db/migration/`의 신규 마이그레이션은 `V{YYYYMMDDHHMMSS}__설명.sql` 형식을 쓴다. 규칙의 원본은 [`backend/CLAUDE.md`](../backend/CLAUDE.md)다.

- **왜**: 여러 spec이 병렬로 진행되면서 004(`V3`~`V6`), 007(`V3__param_search`), 014(`V3__spring_session`)가 모두 `V3`을 자기 번호로 적어 두었다. 연속 번호는 브랜치가 병합되는 순서를 미리 알아야 정할 수 있어 충돌이 반복된다. 타임스탬프는 브랜치끼리 겹치지 않는다.
- **기존 이력**: 이미 적용된 `V1__init_schema`·`V2__backtest_result`·`V3__param_search`는 그대로 둔다. Flyway가 버전을 숫자로 정렬하므로 `1 < 3 < 20260911143000` 순서가 유지되고 기존 이력과 충돌하지 않는다. `V3`은 007이 실제로 병합해 선점했다.
- **갱신 대상**: **004·007·014 문서에 적힌 `V{N}` 표기는 갱신 대상이다.** 004의 `V3`~`V6` 계획, 014의 `V3__spring_session`, 그리고 001 tasks.md의 `V7` 표기가 여기 해당한다. 각 표기는 그 spec을 진행하는 작업에서 타임스탬프 형식으로 바꾼다.
- **001은 다른 spec의 문서를 직접 고치지 않는다.** 001 T002가 고친 것은 001 자신의 문서(`spec.md`·`data-model.md`·`contracts/market-dataset.md`)와 `backend/CLAUDE.md`, 그리고 004가 001에 요구한 계약 문서 [`004-backtest-execution/contracts/market-data-input.md`](004-backtest-execution/contracts/market-data-input.md) 하나뿐이다. 그 계약 문서는 001이 만족해야 할 열 이름을 담고 있어 001 T002가 열 이름 정합을 소유한다고 tasks.md가 정했기 때문이며, 고친 범위도 열 이름과 불변 조건에 한정한다. 004·007·014의 나머지 문서는 각 spec이 자기 작업에서 갱신한다.

### 시장 자료 열 이름: 001 기준으로 통일 (2026-09-11, 001 T002)

004가 `trade_date`·`data_version`·`adj_close`·`halted`로 제안한 열 이름을 001의 `date`·`dataset_id`·`adjusted_close`·`trading_suspended`로 통일했다. 004 계약이 "열 이름은 제안이며 의미가 우선한다"고 허용했고 004는 아직 구현 전이라 문서 수정만으로 끝난다. 자료를 실제로 소유·적재하는 001의 이름을 따르면 provider 매핑 계층이 없어진다.

**브로커 메시지 계약(`docs/specs/backtest-messaging/`)과 ADR-0002·ADR-0003은 바뀌지 않는다.** `marketData.datasetId`라는 필드 이름은 그대로이고 값 규칙만 `KRX_DAILY_{YYYYMMDD}`로 정해진다(001 research.md 결정 4).

## 공통 검증·완료 규칙 (§7, 원칙 VII, 완료의 정의)

- **계산 확인**: 대표 거래·현금·비용·분배금·공통 기간(004)과 경제환경 검색의 중앙값·산포·대체 척도·지표/분야/종합 거리·기여도 합(010)을 수기 또는 독립 계산으로 대조한다. 허용 오차는 PD-12에서 시험 전에 고정한다. 평가 경계를 넘는 이후 결과가 개발 자료에서 제거됐는지, 원시 가격·분배금·비용과 거래 내역이 일치하는지 확인한다.
- **사용성 관찰 (PD-14)**: 전략을 검증하려는 개인 6~8명에게 섹터 비중 비교 과제와 경제환경 탐색 과제('현재와 고용환경이 가까운 과거를 찾고, 물가에서 다른 점을 설명한 뒤 같은 전략의 이후 행동을 비교하기')를 주어 관찰한다. 종합 비교를 열지 않아도 분야 탐색 과제가 끝나야 한다. 필요하면 입문자의 학습 → 진단 이동도 관찰한다. 설명 없이 완료한 참여자 수·막힌 단계·오해 유형을 기록하고, 두 명 이상이 같은 단계에서 막히면 해당 화면을 수정한다. 이 인원은 오류 발견을 위한 시작 규모이며 수요를 입증하는 표본이 아니다. 각 spec의 사용성 관련 성공 기준은 이 관찰의 일부다.
- **완료의 구분**: 구현 완료·사용성 확인·효과 입증을 구분해 보고하며 하나를 다른 것의 증거로 쓰지 않는다. 미사용 검증이 없거나 개선 근거가 없어도 기능을 되돌리지 않고 결과에 '미검증·개선 근거 없음·판단 보류'를 표시한다. Task 단위 완료는 constitution "완료의 정의"의 다섯 조건을 따른다.
- **외부 PoC**: 제공받은 외부 PoC 기록은 스크립트를 재실행해 재검증하기 전에는 독립 검증 결과로 승격하지 않는다.
- **공통 성공 기준**: 화면 어디에도 추천 비중·주문 버튼·자동 단일 승자·우승 전략·사용자 간 랭킹·확률 표현·결제 단계가 없다(리뷰 체크리스트 위반 0건). 자료 부족·빈 뉴스·수집 지연·계산 실패·ETF 미상장·후보 없음·0 척도 상황은 100% 오류 화면 없이 정상 흐름과 한 문장 안내로 처리된다. 동일 버전 재실행은 전략 단일 실행·자동 탐색·경제환경 검색 모두에서 100% 같은 결과를 낸다.

## 범위 밖 (전체)

constitution "하지 않는 것"과 기획서 §8.2에 따라 아래 항목은 어느 spec·plan·코드에도 추가하지 않는다. 필요해지면 constitution을 먼저 개정한다.

- 맞춤형 투자 추천, '추천 비중', 주문 버튼, 증권사 연동·자동 주문·실계좌 연동
- 상시 성과 추적·알림, 사용자 간 성과 랭킹, 일·주·월간 우승 전략
- 숙련 퀀트용 자유 코드 입력·전용 연구 화면, 전략 공유 커뮤니티
- 진단 화면 안의 결제 단계, 포인트·상품 선택, 가격·무료 범위·유료 제공량 결정
- QuantConnect 비교와 동등 기능 구현, 고객군별 재방문·전환율 측정, 결제 실험
- 현재 경제를 하나의 좋고 나쁜 점수로 평가하는 화면
- 마할라노비스·PCA·RRF를 기본 검색 모델에 넣는 것
- 전략별 가격 특징 중심의 다변량 유사 시장 검색(사용자 기능으로서). 단순 가격 추세·변동성 검색은 내부 비교 기준으로만 유지한다
- 법률 검토와 실제 제품 출시 여부·시점
- 분산 Worker·Spark·별도 빠른 탐색 엔진의 도입 확정(실측 후 별도 판단)
- 상장 전 합성 ETF 이력, 미래 자료로 결측을 채우는 처리, 임의 보간
- 거시 통계의 당시 발표·수정값(빈티지) 확보와 당시 재현 분석, 거시 검색을 매매 신호로 쓴 실시간 전략 검증 주장

## Spec 작성 규칙

- 사용자 스토리는 Jira Story 형식 `[대상]은 (목적)하기 위하여 (활동/작업/기능)할 수 있다`로 쓴다. 대상은 기획서 §3.2의 세 사용자(전략을 검증하려는 개인 / 거시경제·뉴스 관심 사용자 / 완전 입문자) 또는 서비스 운영자다.
- 기획 근거는 §·D·U 번호로 인용한다. 기획서가 "실행 전 결정 항목"으로 남긴 값은 확정하지 않고 PD 번호로 표시한다. PD 번호는 이 문서의 표와 같은 번호를 쓰고 소유 spec 하나에서 상태를 관리한다.
- 다른 spec의 규칙은 링크로 참조하고 다시 정하지 않는다. 같은 규칙이 두 spec에 필요하면 소유 spec을 정하고 다른 쪽은 "~를 따른다"로 쓴다.
- `Feature Branch` 항목은 spec 디렉터리 식별자다. 구현 Task의 Git 브랜치는 Jira Task마다 `{type}({position})/{JIRA_NUMBER}-{description}` 형식으로 따로 만든다.
- 각 spec의 `checklists/requirements.md`는 `/speckit-specify`가 만든 품질 체크리스트다. 항목이 미완료면 `/speckit-clarify` 또는 `/speckit-plan` 전에 spec을 고친다.

## 다음 단계

- `.specify/feature.json`의 `feature_directory`는 한 번에 spec 하나를 가리킨다. `/speckit-clarify`·`/speckit-plan`·`/speckit-tasks`를 실행하기 전에 대상 spec 디렉터리로 바꾼다.
- plan은 spec 우선순위 순서(001 → 005 → 014·006·007 → 008~011 → 012·013)를 기본으로 하되, 팀 배치에 따라 병렬로 진행할 수 있다. plan의 Constitution Check는 constitution을 기준으로 판정한다.
- PD 항목이 확정되면 소유 spec의 표를 갱신하고 이 문서의 상태 열도 같은 값으로 고친다.
