# Feature Specification: 전략 저장 및 공유

**Feature Branch**: `009-strategy-save-sharing`

**Created**: 2026-09-03

**Status**: Draft

**Input**: User description: "F9. 전략 저장 및 공유 — Quantum Jump에서 사용자가 관심 있는 전략과 설정을 사용자 자산으로 저장하고 목록에서 다시 찾아 백테스트에 재사용하거나, 명시적으로 허용한 범위에서 다른 사용자와 공유할 수 있는 기능을 정의한다. 저장 시 전략과 파라미터 등 재사용 정보를 식별하고 소유자와 접근 범위를 구분하며, 다른 사용자는 원본을 임의로 수정할 수 없어야 한다. 사용자 작성 전략 코드 실행, 전략 추천, 랭킹, 커뮤니티 게시판 및 구체적인 권한·DB 구현 방식은 제외한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 전략과 설정을 사용자 자산으로 저장 (Priority: P1)

여러 전략을 실험한 사용자가 다시 검토할 가치가 있는 전략과 설정에 이름과 설명을 붙여 자신의 저장
전략으로 보관한다. 저장 내용에는 전략과 정확한 버전, 전체 파라미터, 백테스트 대상·기간·초기 자산 등
재사용에 필요한 조건이 포함된다. 저장 직후 접근 범위는 비공개이며 소유자는 자신으로 명확히 표시된다.

**Why this priority**: 설정을 정확히 보존하는 것이 목록, 재사용과 공유의 전제다. 전략 버전이나 파라미터가
빠지면 같은 설정을 다시 구성할 수 없어 저장 기능의 가치가 사라진다.

**Independent Test**: 유효한 F2 조건과 완료 결과에서 각각 전략을 저장하고, 저장된 전략 버전·전체
파라미터·대상·기간·초기 자산·조건이 원본과 같은지 확인한다. 저장 직후 다른 사용자에게 보이지 않으며,
비밀값이나 사용자 작성 실행 코드가 포함되지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 유효한 백테스트 조건(F2), **When** 사용자가 이름과 선택적 설명을 입력해 저장하면, **Then**
   저장 전략 식별자가 제공되고 전략 버전, 전체 파라미터와 조건, 소유자, 비공개 접근 범위가 보존된다.
2. **Given** 완료된 백테스트·비교·탐색·검증 또는 추천의 전략 후보, **When** 사용자가 해당 설정을 저장하면,
   **Then** 화면에 실제 표시된 전략 버전과 전체 설정이 저장되고 출처 기록을 추적할 수 있다.
3. **Given** 필수 파라미터가 없거나 지원 전략을 식별할 수 없는 설정, **When** 사용자가 저장하려 하면,
   **Then** 누락되거나 잘못된 항목이 표시되고 불완전한 저장 전략은 생성되지 않는다.
4. **Given** 저장 전 확인 화면, **When** 사용자가 접근 범위를 확인하면, **Then** 기본값이 비공개임과 공유는
   저장 후 별도의 명시적 동작이라는 점이 표시된다.
5. **Given** 같은 저장 요청이 재전달된 상황, **When** 시스템이 요청을 처리하면, **Then** 중복 저장 전략이나
   중복 리비전을 만들지 않고 원래 저장 결과를 제공한다.

### User Story 2 - 저장 목록 조회와 백테스트 재사용 (Priority: P2)

사용자는 자신이 소유한 저장 전략 목록을 열어 이름, 전략 버전, 주요 파라미터, 저장·수정 시점과 공유
상태를 확인하고 원하는 항목을 찾는다. 항목을 재사용하면 저장된 설정이 새 백테스트 조건 초안(F2)에
복사된다. 사용자는 원본을 바꾸지 않은 채 초안을 그대로 사용하거나 수정한 뒤 검증하고 백테스트를 별도로
실행한다.

**Why this priority**: 저장한 설정을 쉽게 찾고 정확히 다시 사용하는 것이 반복 실험 비용을 줄이는 직접적인
사용자 가치다.

**Independent Test**: 저장 전략이 100개인 계정에서 이름·전략·수정 시점으로 원하는 항목을 찾고 재사용한다.
F2 초안에 모든 조건이 정확히 복사되는지, 초안을 수정해도 저장 원본이 바뀌지 않는지, 재사용만으로
백테스트가 자동 시작되지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 사용자가 소유한 저장 전략들, **When** 목록을 열면, **Then** 각 항목의 이름, 전략과 버전,
   주요 파라미터, 최신 리비전, 저장·수정 시점 및 현재 공유 상태를 확인할 수 있다.
2. **Given** 여러 저장 전략, **When** 사용자가 이름 또는 전략으로 찾거나 저장·수정 시점으로 정렬하면,
   **Then** 조건에 맞는 항목을 구분해 확인할 수 있다.
3. **Given** 사용 가능한 전략 버전을 가리키는 저장 전략, **When** 사용자가 다시 백테스트에 사용하면,
   **Then** 최신 저장 리비전의 전체 설정이 새 F2 조건 초안에 정확히 복사되고 저장 원본은 변경되지 않는다.
4. **Given** 재사용한 조건 초안, **When** 사용자가 파라미터나 기간을 수정하면, **Then** 수정 사실과 출처
   저장 전략이 표시되고 원본 리비전은 그대로 유지된다.
5. **Given** 더 이상 실행할 수 없는 전략 버전을 가리키는 저장 전략, **When** 사용자가 재사용하려 하면,
   **Then** 조회는 가능하지만 그대로 실행할 수 없는 이유가 안내되고 최신 버전으로 자동 변경되지 않는다.
6. **Given** 저장 전략에서 만든 조건 초안, **When** 사용자가 재사용 동작만 완료하면, **Then** 백테스트는
   시작되지 않고 F2 검증과 별도 실행 확인이 필요하다.

### User Story 3 - 지정 사용자에게 읽기 전용 공유 (Priority: P3)

소유자는 저장 전략의 특정 리비전을 등록된 다른 사용자에게 공유한다. 공유 전에 상대방에게 보일 전략,
파라미터, 백테스트 조건, 이름과 설명을 미리 확인하고 대상을 명시적으로 선택한다. 공유 후에는 대상별
접근 상태를 확인하거나 철회할 수 있으며, 소유자가 새 리비전을 만들어도 기존 공유본은 자동으로 바뀌지
않는다.

**Why this priority**: 공유는 사용자 자산의 노출 범위를 넓히므로 비공개 기본값, 구체적인 대상 지정과
공유 내용 확인이 선행되어야 한다. 리비전을 고정하면 상대방이 본 설정이 나중에 조용히 달라지는 일을 막는다.

**Independent Test**: 비공개 저장 전략을 사용자 A에게만 공유해 A는 지정 리비전을 볼 수 있고 사용자 B는
존재 여부도 알 수 없는지 확인한다. 소유자가 설정을 수정해 새 리비전을 만들어도 A의 공유본은 그대로이며,
소유자가 새 리비전 공유를 명시적으로 선택해야 바뀌는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 비공개 저장 전략의 소유자, **When** 공유할 리비전과 등록된 사용자 한 명 이상을 선택하고
   공개될 내용을 확인한 뒤 공유하면, **Then** 선택한 사용자에게만 해당 리비전의 읽기 권한이 부여된다.
2. **Given** 공유 확인 전 상태, **When** 소유자가 대상이나 공개 내용을 확인하지 않고 화면을 벗어나면,
   **Then** 접근 범위는 비공개로 유지되고 공유 권한이 생성되지 않는다.
3. **Given** 특정 리비전이 공유된 저장 전략, **When** 소유자가 설정을 수정해 새 리비전을 만들면, **Then**
   기존 수신자는 원래 공유 리비전을 계속 보고 새 리비전은 소유자가 다시 명시적으로 공유하기 전까지
   볼 수 없다.
4. **Given** 활성 공유들, **When** 소유자가 공유 관리를 열면, **Then** 리비전별 수신자, 공유 시점과 현재
   활성·철회 상태를 확인하고 특정 수신자의 접근을 철회할 수 있다.
5. **Given** 소유자가 공유를 철회한 경우, **When** 수신자가 원본 공유 항목을 다시 열면, **Then** 더 이상
   접근할 수 없고 다른 비공개 리비전이나 원본 존재 여부에 관한 추가 정보는 노출되지 않는다.

### User Story 4 - 공유된 설정 확인과 독립적으로 활용 (Priority: P4)

수신자는 “나에게 공유됨” 목록에서 공유자, 전략 버전, 전체 파라미터와 주요 백테스트 조건을 확인한다.
공유 원본은 읽기 전용이며 수신자는 이를 직접 수정하거나 다른 사람에게 재공유할 수 없다. 활용하려면
새 F2 조건 초안으로 복사하거나 자신의 비공개 저장 전략으로 사본을 만들며, 사본은 출처를 남기되 원본과
독립적인 사용자 자산이 된다.

**Why this priority**: 수신자가 조건을 충분히 검토하고 재사용할 수 있게 하면서 원소유자의 자산과 접근
결정을 침해하지 않아야 안전한 공유가 완성된다.

**Independent Test**: 공유 수신자로 원본 수정·재공유가 거부되는지, 표시된 주요 조건이 공유 리비전과
일치하는지 확인한다. 개인 사본과 F2 초안을 각각 만든 뒤 이를 수정해도 공유 원본이 바뀌지 않는지,
공유 철회 후 원본 접근은 사라지지만 이미 만든 사본의 처리 정책이 사전 고지와 일치하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 활성 공유를 받은 사용자, **When** “나에게 공유됨” 목록과 상세를 열면, **Then** 공유자,
   공유 시점, 공유 리비전, 전략 이름·버전, 전체 파라미터, 대상·기간·초기 자산과 기타 저장 조건을 확인할
   수 있다.
2. **Given** 공유 원본을 보는 수신자, **When** 이름·설명·전략·파라미터·조건 또는 공유 대상을 바꾸려 하면,
   **Then** 원본은 읽기 전용으로 유지되고 변경이 거부된다.
3. **Given** 공유 원본, **When** 수신자가 다시 백테스트에 사용하면, **Then** 공유 리비전의 설정이 새 F2
   조건 초안에 복사되고 원본은 변경되지 않으며 백테스트는 자동 시작되지 않는다.
4. **Given** 공유 원본, **When** 수신자가 자신의 저장 전략으로 복사하면, **Then** 자신이 소유하는 비공개
   사본이 생성되고 출처 공유 리비전이 기록되며 이후 수정은 원본에 영향을 주지 않는다.
5. **Given** 수신자가 공유 원본을 직접 재공유하려는 경우, **When** 공유를 시도하면, **Then** 재공유는
   거부된다. 수신자가 만든 독립 사본은 자신의 자산으로서 별도 공유 정책에 따라 공유할 수 있다.

### Edge Cases

- 같은 이름의 저장 전략이 여러 개여도 고유 식별자와 전략 버전·주요 파라미터로 구분한다. 이름 중복을
  이유로 기존 자산을 덮어쓰지 않는다.
- 저장하려는 출처가 진행 중이거나 실패한 실행이어도 F2 검증을 통과한 완전한 설정을 식별할 수 있으면
  저장할 수 있다. 결과 성과는 이 기능의 저장·공유 대상에 포함하지 않는다.
- 전략 정의가 개정되거나 삭제되어도 기존 저장 리비전은 당시 전략 버전과 설정을 그대로 보여준다. 실행할
  수 없는 버전은 자동 변환하지 않고 사유와 사용 가능한 대안을 별도 초안에서 선택할 수 있게 한다.
- 소유자가 오래된 화면을 기준으로 동시에 수정하면 최신 리비전을 조용히 덮어쓰지 않는다. 기준 리비전이
  달라졌음을 알리고 최신 내용을 확인한 뒤 새 리비전을 만들게 한다.
- 공유 대상이 존재하지 않거나 비활성 사용자이면 공유를 생성하지 않고 해당 대상을 특정해 안내한다.
- 소유자가 자기 자신을 공유 대상에 넣거나 같은 사용자를 중복 선택하면 중복 권한을 만들지 않는다.
- 공유 중 전략 설정에 포함될 수 없는 비밀값이나 공유 범위 밖 정보가 발견되면 공유를 차단하고 해당 항목을
  제거한 유효한 설정으로 다시 저장하도록 안내한다.
- 소유자의 원본에 연결된 백테스트 결과, 개인 메모 또는 다른 비공개 자산은 별도로 공유하지 않는 한
  수신자에게 노출하지 않는다.
- 공유 철회는 이후 원본 접근과 새 복사를 막지만 수신자가 철회 전에 만든 독립 사본을 삭제하지 않는다.
  소유자는 공유 확정 전에 이 정책을 확인한다.
- 공유를 철회하는 순간 수신자가 상세를 보고 있으면 다음 접근 확인부터 내용이 제공되지 않는다.
- 수신자가 독립 사본을 만든 뒤 원본 공유 리비전이 갱신·철회되어도 사본은 자동 변경되지 않는다.
- 권한이 없는 사용자가 저장 전략 식별자를 추측해 조회하면 자산 존재 여부, 소유자 또는 설정을 노출하지
  않고 접근을 거부한다.
- 저장·공유 요청의 재전달이나 재시도로 중복 자산, 리비전 또는 접근 권한을 만들지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 사용자는 Quantum Jump가 제공하는 전략과 유효한 설정을 자신의 저장 전략으로 만들 수 있어야
  한다. 사용자 작성 전략 코드 또는 실행 가능한 임의 코드는 저장·실행 대상으로 받아서는 안 된다.
- **FR-002**: 사용자는 F2의 유효한 조건 초안이나 F1·F4·F5·F6·F8 기록에서 완전한 전략 설정을 선택해
  저장할 수 있어야 한다. 출처 기록을 사용하는 경우 저장 전략에서 그 출처를 식별할 수 있어야 한다.
- **FR-003**: 저장 리비전은 전략 식별자와 버전, 전체 파라미터 이름·값, 대상 종목, 시작일·종료일, 초기
  자산 및 F2가 정의한 재사용 가능 조건 전체를 포함해야 한다.
- **FR-004**: 저장 전략은 고유 식별자, 사용자 지정 이름과 선택적 설명, 소유자, 생성·수정 시점, 최신
  리비전 및 접근 범위를 가져야 한다.
- **FR-005**: 새 저장 전략의 접근 범위는 항상 비공개여야 한다. 저장 동작만으로 다른 사용자에게 공개되어서는
  안 되며, 공유는 소유자의 별도 명시적 확인을 거쳐야 한다.
- **FR-006**: 저장 전략의 설정을 변경하면 기존 내용을 덮어쓰지 않고 새 리비전을 생성해야 한다. 각
  리비전은 번호, 생성 시점, 생성한 소유자와 바로 이전 리비전을 식별할 수 있어야 한다.
- **FR-007**: 최신 리비전이 아닌 내용을 기준으로 동시에 변경하려는 경우 시스템은 최신 리비전을 조용히
  덮어쓰지 않고 충돌 사실을 알린 뒤 사용자가 최신 내용을 확인하게 해야 한다.
- **FR-008**: 같은 저장 또는 수정 요청의 재전달·재시도는 중복 저장 전략이나 중복 리비전을 만들지 않아야
  한다.
- **FR-009**: 사용자는 자신이 소유한 저장 전략 목록에서 이름, 전략과 버전, 주요 파라미터, 최신 리비전,
  생성·수정 시점과 공유 상태를 확인할 수 있어야 한다.
- **FR-010**: 사용자는 소유 목록을 이름 또는 전략으로 찾고 생성·수정 시점으로 정렬할 수 있어야 한다.
- **FR-011**: 사용자는 저장 전략의 어느 리비전이든 전략 버전, 전체 파라미터와 조건, 이름·설명, 출처와
  생성 시점을 상세 조회할 수 있어야 한다.
- **FR-012**: 사용자가 저장 전략을 재사용하면 선택한 리비전의 전체 설정을 새 F2 조건 초안에 정확히
  복사해야 한다. 이 동작은 저장 원본을 수정하거나 백테스트를 자동 실행해서는 안 된다.
- **FR-013**: 재사용한 초안에는 출처 저장 전략과 리비전을 표시해야 한다. 사용자가 설정을 수정하면 원본과
  달라졌음을 표시하되 원본 리비전은 변경하지 않아야 한다.
- **FR-014**: 재사용 초안은 백테스트 실행 전에 현재 F2 검증을 통과해야 한다. 저장된 전략 버전이나 조건을
  더 이상 사용할 수 있지 않으면 이유를 제공하고 다른 버전으로 자동 변경해서는 안 된다.
- **FR-015**: 저장 전략의 소유자만 이름·설명·설정을 수정해 새 리비전을 만들거나 공유 대상을 추가·변경·
  철회할 수 있어야 한다.
- **FR-016**: 이 기능의 공유 범위는 소유자가 지정한 등록 사용자에 대한 읽기 권한으로 한정한다. 공개·익명
  링크, 전체 사용자 공개 및 검색 가능한 게시물 형태의 공유는 제공하지 않는다.
- **FR-017**: 공유 전 시스템은 선택 리비전, 수신자와 수신자에게 공개될 이름·설명·전략 버전·전체
  파라미터·조건을 소유자에게 보여주고 명시적인 확인을 받아야 한다.
- **FR-018**: 공유 권한은 저장 전략의 특정 리비전을 가리켜야 한다. 소유자가 새 리비전을 만들어도 기존
  공유 권한이 새 리비전으로 자동 이동해서는 안 되며 새 리비전은 별도 확인을 거쳐 공유해야 한다.
- **FR-019**: 소유자는 공유 리비전별 수신자, 공유 시점, 활성·철회 상태를 확인하고 개별 수신자의 접근을
  철회할 수 있어야 한다.
- **FR-020**: 공유 철회 후 수신자는 원본 공유 리비전을 조회하거나 새 조건 초안·개인 사본을 만들 수 없어야
  한다. 철회 전에 만든 독립 사본은 삭제하지 않으며 이 정책을 공유 확인 전에 소유자에게 고지해야 한다.
- **FR-021**: 수신자는 “나에게 공유됨” 목록에서 공유자, 공유 시점, 공유 리비전, 전략과 버전, 주요
  파라미터 및 조건을 확인할 수 있어야 한다. 소유 목록과 공유받은 목록은 명확히 구분되어야 한다.
- **FR-022**: 수신자는 활성 공유 리비전의 이름·설명·전략 버전·전체 파라미터와 조건을 읽을 수 있어야
  하지만, 원본 내용이나 공유 대상을 수정할 수 없어야 한다.
- **FR-023**: 수신자는 공유 리비전을 새 F2 조건 초안으로 복사하거나 자신이 소유하는 새 비공개 저장
  전략으로 복사할 수 있어야 한다. 복사본은 출처 공유 리비전을 기록하고 원본과 독립적으로 변경되어야 한다.
- **FR-024**: 수신자는 공유 원본을 다른 사용자에게 재공유할 수 없어야 한다. 수신자가 만든 독립 사본은
  자신의 소유 자산으로서 이 명세의 공유 절차에 따라 별도로 공유할 수 있다.
- **FR-025**: 공유 대상에는 저장 전략에 포함된 설정만 공개해야 한다. 연결된 백테스트 결과, 개인 메모,
  출처 기록의 비공개 내용과 소유자의 다른 자산은 별도의 공유 없이 노출해서는 안 된다.
- **FR-026**: 저장하거나 공유하는 설정에는 접속 정보, 비밀키 또는 실행에 불필요한 민감 정보를 포함해서는
  안 된다. 금지 정보가 발견되면 저장 또는 공유를 거부하고 문제 항목을 알려야 한다.
- **FR-027**: 권한이 없는 사용자의 조회·수정·복사·공유 요청은 거부되어야 하며 저장 전략의 존재 여부,
  소유자 또는 설정을 노출해서는 안 된다.
- **FR-028**: 같은 공유 요청의 재전달·재시도는 중복 공유 권한을 만들지 않아야 한다. 모든 공유와 철회는
  대상 리비전, 수행한 소유자, 수신자, 시점과 결과를 기록하고 소유자가 확인할 수 있어야 한다.
- **FR-029**: 이 기능은 전략 설정의 저장, 리비전 조회, F2 조건 초안 재사용, 지정 사용자 읽기 공유와
  독립 사본 생성까지만 제공한다. 사용자 작성 전략 코드 실행, 전략 추천, 랭킹 계산, 공개 커뮤니티 게시판,
  실제 투자 자문, 자동 주문 및 구체적인 권한·저장 기술 선택은 포함하지 않는다.

### Key Entities *(include if feature involves data)*

- **저장 전략(Saved Strategy)**: 사용자가 소유하는 전략 설정 자산. 고유 식별자, 이름·설명, 소유자,
  생성·수정 시점, 최신 리비전과 공유 상태를 가진다.
- **저장 전략 리비전(Saved Strategy Revision)**: 특정 시점의 불변 설정. 리비전 번호, 전략 식별자와 버전,
  전체 파라미터, 대상·기간·초기 자산과 기타 F2 조건, 생성 시점, 이전 리비전과 출처 기록을 가진다.
- **공유 권한(Share Grant)**: 소유자가 등록 사용자에게 특정 리비전을 읽도록 부여한 접근 기록. 소유자,
  수신자, 대상 리비전, 공유·철회 시점과 활성 상태를 가진다.
- **재사용 조건 초안(Reusable Condition Draft)**: 소유 또는 공유 리비전에서 복사된 새 F2 조건. 출처
  저장 전략·리비전, 복사된 설정, 사용자 수정 여부와 현재 검증 상태를 가진다.
- **저장 전략 사본(Saved Strategy Copy)**: 공유 수신자가 자신의 자산으로 복사한 새 비공개 저장 전략.
  출처 공유 리비전을 기록하지만 원본과 독립된 소유자와 리비전 생명주기를 가진다.
- **자산 접근 기록(Asset Access Record)**: 공유와 철회의 추적 정보. 대상 리비전, 수행 소유자, 수신자,
  시점, 동작과 결과를 가지며 소유자가 공유 내역을 확인하는 근거가 된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 저장된 리비전의 100%에서 전략 식별자·버전, 전체 파라미터, 대상, 기간, 초기 자산과 F2의
  재사용 가능 조건을 식별할 수 있다.
- **SC-002**: 저장 또는 공유 리비전을 F2 조건 초안으로 재사용했을 때 복사된 설정이 원본과 불일치한 사례가
  0건이며, 재사용 동작만으로 백테스트가 시작된 사례가 0건이다.
- **SC-003**: 새 저장 전략이 소유자의 명시적 공유 없이 다른 사용자에게 노출된 사례가 0건이다.
- **SC-004**: 권한이 없는 사용자가 저장 전략의 존재·소유자·설정을 확인하거나 수정·복사·공유하는 데
  성공한 사례가 0건이다.
- **SC-005**: 공유 수신자가 원본 리비전 또는 공유 대상을 수정하는 데 성공한 사례가 0건이다.
- **SC-006**: 공유 및 철회 동작의 100%에서 대상 리비전, 소유자, 수신자, 시점과 결과를 추적할 수 있다.
- **SC-007**: 공유 철회 후 수신자의 다음 접근 요청부터 원본 내용이 제공된 사례가 0건이다.
- **SC-008**: 저장 전략 500개와 공유받은 전략 500개를 가진 사용자의 목록 조회 중 95%는 3초 이내에
  구분된 목록과 주요 정보를 제공한다.
- **SC-009**: 사용성 검증에서 대상 사용자의 90% 이상이 3분 이내에 현재 설정을 저장하고 목록에서 찾아
  새 F2 조건 초안으로 재사용할 수 있다.
- **SC-010**: 사용성 검증에서 소유자와 수신자의 85% 이상이 공유 전후에 누가 어느 리비전을 볼 수 있는지,
  수신자가 수정할 수 없는 항목과 철회가 기존 사본에 미치는 영향을 추가 도움 없이 정확히 설명할 수 있다.

## Assumptions

- 대상 사용자는 인증된 Quantum Jump 사용자이며, 공유 수신자도 등록된 사용자로 한정한다.
- “전략 설정”은 Quantum Jump가 제공하는 전략의 특정 버전과 F2가 정의한 파라미터·백테스트 조건이다.
  사용자가 작성한 전략 소스 코드, 스크립트 또는 실행 파일은 저장·공유 대상이 아니다.
- 이름과 설명은 사용자가 자산을 구분하기 위한 정보다. 이름 중복은 허용하며 고유 식별자와 리비전으로
  자산을 구분한다.
- 저장 전략은 기본 비공개이고 지정 사용자에게만 읽기 공유할 수 있다. 공개 링크, 익명 접근, 전체 공개,
  검색·댓글·좋아요·구독 같은 커뮤니티 기능은 후속 기능으로 분리한다.
- 공유는 특정 리비전의 스냅샷에 고정된다. 소유자가 새 리비전을 수신자에게 보이려면 새 공유 확인을 해야
  하며, 수신자의 개인 사본에는 자동으로 변경이 전파되지 않는다.
- 공유 수신자는 원본을 재공유할 수 없지만 자신의 독립 사본을 새 자산으로 공유할 수 있다. 사본에는 직접
  출처 리비전을 남기되 원소유자의 비공개 기록이나 백테스트 결과는 노출하지 않는다.
- 공유 철회는 원본에 대한 이후 접근만 제거하고 이미 생성된 독립 사본은 회수하지 않는다. 회수 가능한
  공유나 사본 삭제가 필요하면 별도 정책과 기능으로 정의한다.
- 저장 전략과 리비전의 영구 삭제, 휴지통, 보존 기간 및 계정 탈퇴 시 처리는 이번 범위에 포함하지 않는다.
  이 기능에서 생성된 자산은 적용되는 사용자 데이터 보존 정책에 따라 보존된다고 가정한다.
- 전략 버전이 더 이상 실행 가능하지 않아도 저장 리비전은 조회할 수 있다. 버전 변환은 사용자가 새 F2
  초안에서 명시적으로 수행하며 시스템은 설정을 자동 이행하지 않는다.
- 저장·공유하는 것은 전략 설정뿐이다. 연결된 성과지표, 자산 시계열, 거래 내역 또는 추천 순위는 해당
  기능의 별도 공유 정책이 정의되기 전까지 공유하지 않는다.
- 저장·권한 데이터의 물리적 저장 방식, 접근 검사 구현과 외부 식별 체계는 계획 단계에서 결정한다.

## Constitution Alignment

- **원칙 I·II (백테스트 실행 경계와 추적성)**: FR-012~FR-014는 재사용을 새 F2 조건 초안 생성으로 한정하고
  백테스트를 자동 실행하지 않는다. 이후 실행은 F1의 독립 실행·추적 정책을 따른다.
- **원칙 III (실측 후 기술 도입)**: FR-029와 Assumptions는 저장소·권한 기술이나 배포 구조를 요구하지
  않는다. 목록 규모와 응답 목표를 측정해 현재 요구를 만족하는 가장 단순한 구조를 계획한다.
- **원칙 IV (파트 경계 계약)**: 저장 리비전, 공유 권한과 재사용 조건 초안은 이를 생산·소비하는 파트가
  공유하는 계약이며, 구체적 필드와 전달 형식은 계획 단계에서 문서화하고 호환성을 함께 관리한다.
- **원칙 V (결과 신뢰성)**: FR-003·FR-006·FR-012~FR-014가 전략 버전과 전체 설정을 보존해 재사용 결과의
  재현 기반을 제공한다. 실제 백테스트 결과를 공유하지 않으므로 공통 지표 비교에는 변경을 주지 않는다.
- **보안·데이터 제약**: FR-005와 FR-015~FR-028이 비공개 기본값, 소유자 권한, 명시적 공유, 읽기 전용
  접근과 비밀정보 차단을 요구한다.
- 원칙에서 벗어나는 요구사항은 없다.
