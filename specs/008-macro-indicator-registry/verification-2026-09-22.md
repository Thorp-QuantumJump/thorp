지표마다 세 달을 골라 **원천 응답에서 다시 계산한 값**과 파이프라인 값을 견줬다. 허용 오차는
0이다(PD-12 확정 전까지 정확 일치).

- 검증: `data/tests/test_macro_value_crosscheck.py`
- 표본: 2026-09-17 실조회 응답 (`data/tests/fixtures/macro/`)
- 대조 방식: 변환 모듈을 쓰지 않고 시험 파일 안에서 다시 계산한다. 같은 모듈로 다시 계산하면
  그 모듈이 틀렸을 때 둘이 똑같이 틀린다

| 항목 | 결과 |

| 여섯 변환 유형이 모두 표본에 든다 | 확인 |
| 주택가격: 이어 붙인 이음매를 넘는 전월 대비 | 확인 (표 셋을 `housing.link()`로 이은 계열에서 대조) |
| 실업률: 원천 계절조정값을 그대로 둔다 | 확인 |
| 결측 직후 달이 가까운 달로 물러나지 않는다 | 확인 |
| 수출·수입 | 확인 (관세청 2025·2026 표본 21개월을 이어 2026-01·05·09 의 전년동월 대비를 대조) |

`SAMPLE_TOO_SHORT`는 비어 있고, 시험이 그 사실을 고정한다 — 표본 한계로 건너뛴 지표가 다시

## 4. 닫은 것과 열린 것

### 4.1 수출·수입의 원값 대조 — 2026-09-22 닫음

저장된 표본이 2026년 아홉 달뿐이라 전년동월이 없었다. 관세청 2025년 응답을 받아 표본에 넣고
두 해를 이어 읽게 했다. 원천이 조회 기간을 1년으로 제한하므로(FR-017a) 표본도 해마다 따로
두고 시험이 잇는다.

2026-01·05·09 의 전년동월 대비가 원천 숫자로 다시 계산한 값과 정확히 일치했다(오차 0).

### 4.2 증분 수집 보존·과거 개정 — 2026-09-22 확인, 결함을 찾아 고쳤다

이 셋은 정기 수집을 여러 달 기다려야 하는 일이 아니다. 기다려야 하는 것은 **실제 원천이 언제
개정하는가**(재조회 구간 `N`, T073에서 미확인으로 닫음)이고, **우리 파이프라인이 개정을 만났을
때 제대로 하는가**는 통제된 시나리오로 지금 확인할 수 있다. 처음에 둘을 섞어 판단했다.

확인하면서 **실제 결함이 나왔다.**

> 정기 수집은 최근 `N`개월만 받는데 발행은 계열 시작월부터 모든 달을 요구했다. 그래서
> **정기 수집이 한 번도 발행에 성공할 수 없었다** — FR-017의 증분 모델이 통째로 동작하지
> 않았고, 성공적인 정기 발행을 시험한 적이 없어 드러나지 않았다.

고친 뒤 셋 다 확인했다.

| 시나리오 | 확인 |
|---|---|
| 증분 수집 보존 | `test_macro_publish_postgres.py::test_정기_수집이_예전_달을_지우지_않는다` — 받지 않은 달을 앞 버전에서 이어받는다 |
| 과거 개정 | `test_macro_publish_postgres.py::test_과거_개정이_새_버전을_만들고_앞_버전은_그대로다` — 개정값이 새 버전에 반영되고 앞 버전은 불변 |
| 값 규칙 변경 시 이어받지 않음 | `test_macro_publish_atomic.py::test_value_rule_change_requires_the_whole_range` — 옛 규칙 값이 새 버전에 섞이지 않는다 |

`N` 밖 개정의 **탐지**(원천 공지·메타데이터로 과거 개정을 알아채는 것)는 여전히 열려 있다.
008은 그것을 자동으로 알 방법이 없고, 알게 됐을 때 그 범위를 다시 받는 경로는 위 셋으로 동작이
확인됐다.
