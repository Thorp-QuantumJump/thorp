## 1. 무엇을 만드는가

```text
현재: KRX data/ → PostgreSQL → Backend/Worker
      009 카드용 최신값 11개 ── 별도 경로
      008 월별 17개 ── 미구현

목표: ECOS·KOSIS·관세청·OECD
        → data/ raw → 월별 processed Parquet → macro_* PostgreSQL
        → 17개 전체 불변 스냅샷 + 원자적 current 포인터
        ├→ 008 Backend 단일 조회 → 009의 기존 화면 API 2개
        └→ 010 data/ MacroIndicatorSource → 검색 사전 계산
```

기존 ETF `dataset_version`이나 009의 `market_flow_field_summary`를 거시자료 저장소로 재사용하지 않는다. 계산 등록표 버전, 화면 표시 버전, 자료 버전을 분리한다. 원값과 변환값, 원천 개정 이력, 발표일·수신 시각을 보존한다. Backend는 검색 계산과 원천 수집을 맡지 않는다.

### 1.5 기능 흐름과 상태

```text
① PD-11 계열 검증 ── 어느 원천·항목·조건을 실제로 쓸 수 있는가?
  ↓
② 최초 전 구간 / 이후 새 발표분+최근 N개월 수집 ── 개정·한도를 어떻게 다루는가?
  ↓
③ 원본 보존·월별 변환 ── 대상월과 발표/수신 시각, 결측을 구별했는가?
  ↓
④ 17개 유효 변환값 검증 ── 지표마다 1건 이상 있는가?
  ↓
⑤ 전 구간 스냅샷·T_g/T_all·manifest 봉인 ── 한 자료 버전으로 재현되는가?
  ↓
⑥ DB current 포인터 원자적 교체 ── 이전/새 자료가 섞이지 않는가?
  ↓
⑦ 008 조회 / 009 화면 / 010 계산 ── 각각 같은 고정 버전을 읽는가?
```

```text
COLLECTING → NORMALIZING → VALIDATING → PUBLISHING → PUBLISHED
     └────────────── 각 단계 실패/보류 ──────────────→ FAILED / HELD
```

| 사건 | 처리 |
|---|---|
| 17개 처리 성공, 각 지표의 유효 월별 변환값 ≥1건 | 새 완결 스냅샷을 발행한다. |
| 원천 실패·한도 도달·일부 성공 | 성공 raw와 실패 상태는 남기되 새 공개 버전은 만들지 않는다. 이전 완결 버전을 유지한다. |
| 한 지표에 원값만 있고 유효 변환값 0건 | `HELD`로 발행을 보류한다. |
| 각 지표에는 값이 있지만 전체 공통월 없음 | 발행은 허용하고 `T_all=null`로 둔다. 종합 검색만 계산 불가다. |
| 첫 완결 버전 없음 | 17개 등록 정보와 무자료/실패 상태를 제공하고 값·기준월·자료 버전은 비운다. 운영 fixture 자동 대체는 금지한다. |
| 한 지표의 과거 값 개정 | 전체 17개로 새 불변 자료 버전을 발행하고 이전 결과의 참조 버전은 보존한다. |

## 2. 다음 Task 지도

`tasks.md`가 없어 번호·개수·선행 관계·MVP 경계는 아직 확정되지 않았다. [plan.md의 Delivery Slices](plan.md)는 분할 입력일 뿐 Jira 티켓 목록이 아니다.

```text
실자료 검증·등록표
       ↓
수집·정규화·개정 → 저장·원자적 발행 → 008 단일 조회 → 009·010 연동
```

Claude가 이어서 할 일은 다음 순서가 적절하다.

1. [기본 체크리스트](checklists/requirements.md)와 새 [자료·소비 계약 점검표](checklists/macro-data.md), [원천·이용 조건 점검표](checklists/source-compliance.md)를 읽는다. 새 두 목록은 각각 34개·20개 모두 미체크이며, 구현 완료 표시가 아닌 **요구사항 문장 품질 질문**이다. 검토 없이 일괄 체크하지 않는다.
2. 누락·충돌로 확인된 항목만 소유 문서에 반영한다. 특히 이용 조건과 009/010 계약은 해당 spec/계약의 소유 경계를 지킨다. 미확인 실자료 값을 추측해서 채우지 않는다.
3. 사용자가 작업 분할을 요청하면 `/speckit-tasks`로 `tasks.md`를 작성한다. 각 task의 파일·검증·의존성을 명시하고, 독립 검증/롤백 가능한 **작업 묶음** 후보를 구분한다. 이후 `/speckit-analyze`로 spec·plan·tasks 정합성을 확인한다.
4. Jira Task와 구현 브랜치는 작업 묶음 확정 후, 실제 착수할 묶음에 대해서만 만든다. 1 Jira Task = 1 Branch = 1 MR이다. 사용자가 선택한 현재 문서 브랜치를 임의로 바꾸지 않는다.

## 5. 검증 시나리오와 현재 증거

[quickstart.md](quickstart.md)의 계약·자료 검증 표는 첫 완결 전, 정상 발행, raw만 존재, 공통월 없음, 부분 실패, 과거 개정, 증분 보존, `N` 밖 개정, 월별 변환 계보, 세 버전의 독립 변경, 동시 조회/발행, 파일/DB 경계, 009/010 연동을 다룬다. 구현 후 `data/`는 `ruff check src scripts tests`와 `pytest`, Backend는 `spotlessApply build` 및 Docker를 요구하는 DB 통합 테스트로 검증한다. skipped 시험은 통과로 세지 않는다.

가장 준비 비용이 큰 검증은 `PD-11`의 **17/17 실제 API 응답과 계열별 이용 조건 확인**이다. 이 문서 작성 시에는 수집기·API 구현, 실제 원천 조회, 계약 통합 테스트, 성능 측정이 수행되지 않았다. 문서 존재나 체크리스트 항목 수를 검증 완료로 보고하지 않는다.
