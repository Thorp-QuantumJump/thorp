## 범위 요약

사용자가 이메일 소유 확인을 거쳐 계정을 만들거나 카카오·구글·네이버 계정으로 가입·로그인하고, 로그인 상태를 시작·확인·복원·종료하며, 로그인해야 하는 '내 기록'에 안전하게 접근하는 기능이다. 소셜 계정의 이메일이나 소셜 가입에 입력한 휴대폰 번호가 이미 가입된 계정과 같으면 기존 계정 소유를 확인한 뒤에만 연결하고, 처음 가입하는 소셜 사용자에게는 추가 정보를 받는다. 로그인하지 않은 사용자는 공개 기능을 그대로 이용할 수 있고, '내 기록'과 011의 보호 동작에 접근할 때 로그인 안내를 받는다. 인증이 끝나면 원래 목적지로 돌아간다. 입력 오류·요청 실패·처리 중·로그인 만료를 사용자가 이해할 수 있는 상태로 처리하며, 서버에 없는 기능은 구현된 것으로 가정하지 않는다.

## Clarifications

### Session 2026-09-10

- Q: 사용자는 어떤 계정 정보로 로그인해야 하나요? → A: 이메일과 비밀번호로 로그인한다.
- Q: 회원가입을 완료한 사용자는 다음으로 어디로 이동해야 하나요? → A: 로그인 화면으로 이동하고 가입한 이메일을 미리 입력한다.
- Q: 로그인 화면에 사용자가 선택하는 ‘로그인 상태 유지’ 옵션을 제공해야 하나요? → A: 별도 옵션 없이 서버가 정한 유효기간을 따른다.
- Q: ‘내 기록’을 이용하던 중 로그인 상태가 만료되어 재로그인한 사용자는 어디로 돌아가야 하나요? → A: 만료 전에 이용하던 ‘내 기록’ 위치로 복귀한다.
- Q: 로그아웃 요청 중 네트워크 오류가 발생하면 화면을 어떤 상태로 처리해야 하나요? → A: 보호 정보를 숨기고 ‘로그아웃 미확인’ 상태에서 재시도를 제공한다.

### Session 2026-10-01 (소셜 로그인 추가)

- 소셜 로그인을 범위 밖에서 범위 안으로 옮긴다. 기존 이메일·비밀번호 가입·로그인은 그대로 유지한다.
- Q: 어떤 소셜 계정을 지원하나요? → A: 카카오·구글·네이버 세 곳을 모두 지원한다.
- Q: 소셜 계정의 이메일이 이미 가입된 계정과 같으면 어떻게 하나요? → A: 자동으로 합치지 않는다. 사용자가 연결을 확인하고 기존 계정 소유를 증명해야 연결한다.
- Q: 처음 가입하는 소셜 사용자에게 추가 정보를 받나요? → A: 받는다. 이메일 가입과 같은 계정 정보 기준을 맞추기 위해 닉네임과 국내 휴대폰 번호를 받는다. **(2026-10-02 결정으로 휴대폰 번호는 받지 않는다. 아래 결정 참고)**
- 결정(2026-10-02, 사용자 결정): **가입(이메일·소셜)에서 휴대폰 번호를 받지 않는다.** 번호를 쓰는 기능(문자 발송·번호로 계정 찾기·본인 확인)이 없고, 인증하지 않은 번호를 유일 값으로 받으면 남의 번호로 먼저 가입해 진짜 주인의 가입을 막거나 엉뚱한 계정 연결 안내를 띄울 수 있다. 화면은 번호를 묻지 않고, 계정의 휴대폰 번호는 비어 있을 수 있다. **번호를 다루는 서버 규칙(형식 검사·중복 검사·번호가 겹칠 때의 연결 확인)은 지우지 않는다** — 요청에 번호가 실려 오면 지금처럼 동작하고, 없으면 건너뛴다. 번호와 문자 인증을 함께 도입할 때 화면 입력만 다시 붙인다. 이 결정으로 아래 휴대폰 번호 관련 시나리오(US6-5의 번호 중복, US7 시나리오 4)는 번호가 실려 온 요청에만 해당한다.
- Q: 소셜 제공자에게서 이메일을 받지 못하면 어떻게 하나요? → A: 가입·로그인을 거절하고, 이메일 제공 동의가 필요하다는 안내 화면을 띄운다. 화면에는 다시 동의하기, 이메일로 가입하기, 로그인 화면으로 돌아가기를 둔다.

### Session 2026-10-01 (소셜 로그인 clarify)

- 결정(2026-10-01, 사용자 요청): 휴대폰 번호가 겹쳐 연결 확인으로 온 경우에는 그 기존 계정의 가린 이메일과 연결된 소셜 제공자를 보여주지 않는다. 요청한 사람은 그 번호의 주인임이 확인되지 않았으므로, 남의 번호를 넣는 것만으로 그 계정의 이메일 일부·도메인·연결 제공자를 알아낼 수 있으면 안 된다. 확인 방법은 언제나 "기존 비밀번호"와 "가입할 때 쓴 이메일로 받는 인증번호" 두 가지만 내놓는다(비밀번호가 없는 계정이어도 같다 — 그 사실도 드러내지 않는다). 이메일이 겹친 경우는 요청한 사람이 그 이메일을 확인했으므로 지금처럼 보여준다.

- Q: 제공자가 이메일 확인 여부를 알려주지 않거나 확인되지 않았다고 알리면 그 이메일을 어떻게 다루나요? → A: 거절하지 않고, Thorp가 그 주소로 기존 6자리 인증번호를 보내 확인한 뒤 가입 또는 계정 연결로 진행한다. 거절 화면은 이메일 자체를 받지 못한 경우에만 띄운다.
- 결정(2026-10-02, 사용자 확인): **네이버 이메일은 확인된 이메일로 본다.** 네이버 응답에는 확인 여부 필드가 없지만, 받는 값은 사용자가 고른 연락처 이메일이고 그것은 네이버 메일이거나 네이버가 등록할 때 인증 메일로 확인한 외부 주소뿐이다(사용자가 외부 연락처 이메일 등록 시 인증 메일 확인 절차를 직접 확인). 그래서 네이버 첫 가입에서 Thorp 인증번호를 다시 받지 않는다. 위 인증번호 경로는 확인 여부를 빼고 주는 카카오 응답 등에 그대로 남는다.
- Q: 같은 이메일의 기존 계정에 연결할 때 기존 계정 소유를 어떻게 확인하나요? → A: 기존 계정으로 로그인(비밀번호 또는 이미 연결된 소셜 계정)하거나, 기존 계정 이메일로 보낸 6자리 인증번호를 확인하는 것 중 하나로 확인한다.
- Q: 소셜 신규 가입자가 입력한 휴대폰 번호가 이메일이 다른 기존 계정에서 쓰이고 있으면 어떻게 하나요? → A: 가입을 거절만 하지 않고 "이 번호로 가입된 계정이 있다"고 안내한 뒤 연결 확인 화면으로 보낸다. 기존 계정 소유를 확인하면 연결하고, 확인하지 못하면 가입도 연결도 하지 않는다.
- Q: 이메일이나 번호가 같은 기존 계정에 같은 제공자의 다른 소셜 계정이 이미 연결돼 있으면 어떻게 하나요? → A: 연결 확인 화면을 띄우지 않고 "이 계정은 이미 다른 {제공자} 계정과 연결돼 있다"고 안내한다. 연결된 그 소셜 계정이나 다른 로그인 방법으로 로그인하도록 안내하고, 아무것도 만들거나 연결하지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 새 사용자가 계정을 만든다 (Priority: P1)

새 사용자는 자신의 이메일로 받은 인증번호를 확인한 뒤 필수 정보를 입력해 계정을 만들고, 성공 여부 또는 고쳐야 할 항목을 확인할 수 있다.

**Why this priority**: 계정이 없으면 로그인과 사용자별 내 기록 이용을 시작할 수 없다. 기존 서버가 제공하는 가입 기능을 실제 사용자 흐름으로 연결하는 출발점이다.

**Independent Test**: 가입되지 않은 이메일로 인증번호를 받아 제한 시간 안에 확인한 뒤 유효한 정보로 가입을 완료한다. 잘못되거나 만료된 인증번호, 미인증 이메일, 잘못된 입력·중복 이메일·중복 전화번호도 각각 시험한다.

**Acceptance Scenarios**:

1. **Given** 가입되지 않은 이메일을 입력한 사용자, **When** 인증번호 발송을 요청하면, **Then** 시스템은 요청 처리 상태와 발송 결과를 알려주고 인증번호 입력 단계로 진행할 수 있게 한다.
2. **Given** 유효시간 안에 올바른 인증번호를 입력한 사용자, **When** 인증번호 확인을 요청하면, **Then** 시스템은 이메일 소유 확인 완료를 표시하고 회원가입을 계속할 수 있게 한다.
3. **Given** 잘못되거나 만료된 인증번호를 입력한 사용자, **When** 인증번호 확인을 요청하면, **Then** 시스템은 계정 생성을 허용하지 않고 오류 원인과 재입력 또는 재발송 방법을 알려준다.
4. **Given** 이메일 소유 확인과 유효한 정보 입력을 완료한 사용자, **When** 회원가입을 제출하면, **Then** 시스템은 한 번의 가입 요청만 처리하고 로그인 화면으로 이동해 가입한 이메일만 미리 입력하며 비밀번호는 전달하지 않는다.
5. **Given** 필수 항목이 비었거나 허용 형식·길이를 벗어난 사용자, **When** 회원가입을 제출하려 하면, **Then** 시스템은 잘못된 항목과 수정 방법을 표시하고 요청을 시작하지 않는다.
6. **Given** 이미 사용 중인 이메일 또는 전화번호를 입력한 사용자, **When** 인증 또는 회원가입을 요청하면, **Then** 시스템은 해당 정보를 사용할 수 없음을 알리고 중복 계정을 만들지 않는다.
7. **Given** 인증번호 발송·확인 또는 회원가입 요청을 처리 중인 사용자, **When** 같은 제출 동작을 반복하면, **Then** 시스템은 동일 요청을 중복으로 시작하지 않는다.

### User Story 2 - 기존 사용자가 로그인하고 상태를 복원한다 (Priority: P1)

기존 사용자는 이메일과 비밀번호로 로그인하고, 페이지를 새로 열거나 새로고침해도 유효한 로그인 상태라면 사용자로 인식된다.

**Why this priority**: 로그인과 상태 복원이 없으면 내 기록을 사용자별로 제공하거나 보호할 수 없다.

**Independent Test**: 유효한 계정으로 로그인한 뒤 공개 화면을 이동하고 새로고침해 로그인 표시가 유지되는지 확인한다. 잘못된 계정 정보와 네트워크 실패도 별도로 확인한다.

**Acceptance Scenarios**:

1. **Given** 유효한 계정을 가진 사용자, **When** 올바른 이메일과 비밀번호를 제출하면, **Then** 시스템은 로그인 완료를 알리고 사용자에게 허용된 기능을 사용할 수 있게 한다.
2. **Given** 올바르지 않은 로그인 정보를 입력한 사용자, **When** 로그인을 제출하면, **Then** 시스템은 로그인하지 않은 상태를 유지하고 다시 시도할 수 있는 안내를 보여준다.
3. **Given** 로그인 요청을 처리 중인 사용자, **When** 제출 동작을 반복하면, **Then** 시스템은 동일 로그인 요청을 중복으로 시작하지 않는다.
4. **Given** 유효한 로그인 상태의 사용자, **When** 페이지를 새로 열거나 새로고침하면, **Then** 시스템은 상태 확인이 끝난 뒤 같은 사용자를 로그인 상태로 복원한다.
5. **Given** 로그인 상태 확인이 진행 중인 사용자, **When** 화면이 표시되면, **Then** 시스템은 확인 완료 전까지 로그인 여부를 단정하거나 보호된 정보를 잠시 노출하지 않는다.

### User Story 3 - 로그인 후 원래 내 기록으로 돌아간다 (Priority: P1)

로그인하지 않은 사용자가 '내 기록'을 선택하면 로그인 안내를 받고, 로그인에 성공한 뒤 다시 '내 기록'으로 돌아간다.

**Why this priority**: 사용자의 원래 목적을 보존하면서 사용자별 기록을 보호해야 한다. [006 내 기록](../006-my-records/spec.md)의 식별 조건을 충족하는 연결 기능이다.

**Independent Test**: 로그아웃 상태에서 '내 기록'에 접근해 로그인 화면으로 이동하는지 확인하고, 로그인 완료 후 별도의 탐색 없이 원래 '내 기록'으로 복귀하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인하지 않은 사용자, **When** '내 기록'에 접근하면, **Then** 시스템은 보호된 내용을 표시하지 않고 로그인이 필요하다는 안내와 로그인 진입을 제공한다.
2. **Given** '내 기록'에서 로그인 화면으로 이동한 사용자, **When** 로그인에 성공하면, **Then** 시스템은 원래 접근하려던 '내 기록'으로 돌아간다.
3. **Given** 로그인하지 않은 사용자, **When** 전략 진단·시장 흐름·배우기를 이용하면, **Then** 시스템은 가입이나 로그인을 강제하지 않는다.
4. **Given** 외부 또는 유효하지 않은 복귀 위치가 전달된 사용자, **When** 로그인에 성공하면, **Then** 시스템은 안전한 기본 화면으로 이동하고 외부 위치로 보내지 않는다.

---

### User Story 4 - 사용자가 로그아웃한다 (Priority: P2)

로그인한 사용자는 어느 사용자 화면에서든 로그아웃하고, 이후 사용자 전용 정보에 접근할 수 없는 상태가 되었음을 확인할 수 있다.

**Why this priority**: 공용 기기나 사용 종료 상황에서 사용자별 기록을 계속 노출하지 않도록 로그인 상태를 명시적으로 끝낼 수 있어야 한다.

**Independent Test**: 로그인 상태에서 로그아웃한 뒤 공개 기능은 계속 사용할 수 있고, '내 기록' 재접근 시 로그인 안내가 나타나는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자, **When** 로그아웃을 선택하면, **Then** 시스템은 로그인 상태를 종료하고 완료 상태를 명확히 표시한다.
2. **Given** 로그아웃을 완료한 사용자, **When** '내 기록'에 다시 접근하면, **Then** 시스템은 이전 사용자 정보나 기록을 표시하지 않고 로그인 안내를 제공한다.
3. **Given** 로그아웃을 완료한 사용자, **When** 공개 기능으로 이동하면, **Then** 시스템은 로그인 없이 정상 이용을 허용한다.
4. **Given** 로그아웃 요청 중 네트워크 오류가 발생한 사용자, **When** 서버의 로그아웃 완료를 확인할 수 없으면, **Then** 시스템은 보호 정보를 즉시 숨기고 로그아웃 완료로 표시하지 않으며 상태 확인 또는 재시도를 제공한다.

---

### User Story 5 - 만료와 일시적인 실패에서 안전하게 이어간다 (Priority: P2)

사용자는 로그인 만료와 네트워크 오류를 일반 오류 화면이 아닌 이해 가능한 상태로 보고, 입력을 다시 준비하지 않고 적절한 다음 행동을 선택할 수 있다.

**Why this priority**: 인증 상태가 불확실할 때 보호된 정보를 노출하거나 성공한 것처럼 표시하면 안 되며, 일시적인 연결 실패가 전체 공개 기능 이용을 막아서도 안 된다.

**Independent Test**: 로그인 상태를 만료시키거나 각 인증 요청의 연결을 실패시켜 보호 정보가 숨겨지고 재로그인·재시도 안내가 나타나는지, 공개 화면은 계속 이용 가능한지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인 상태가 만료된 사용자, **When** 보호된 기능을 이용하려 하면, **Then** 시스템은 보호 정보를 숨기고 로그인 만료와 재로그인 필요를 알린다.
2. **Given** 회원가입 또는 로그인 중 네트워크 오류가 발생한 사용자, **When** 실패 응답을 받으면, **Then** 시스템은 완료로 표시하지 않고 안전하게 재시도할 수 있게 한다.
3. **Given** 로그인 상태 확인이 실패한 사용자, **When** 공개 기능을 이용하면, **Then** 시스템은 공개 기능을 막지 않으며 로그인 상태를 확인되지 않은 것으로 처리한다.
4. **Given** '내 기록' 이용 중 로그인 상태가 만료되어 로그인 화면으로 이동한 사용자, **When** 재로그인에 성공하면, **Then** 시스템은 만료 전에 이용하던 유효한 서비스 내부 위치로 돌아간다.

---

### User Story 6 - 소셜 계정으로 가입하고 로그인한다 (Priority: P2)

사용자는 로그인·회원가입 화면에서 카카오·구글·네이버 중 하나를 골라 그 계정으로 로그인한다. 처음이면 닉네임만 확인해 가입을 마치고, 이미 연결된 계정이면 바로 로그인된다.

**Why this priority**: 비밀번호를 새로 만들고 이메일 인증번호를 확인하는 부담 없이 가입과 재방문을 할 수 있게 한다. 이메일 가입·로그인(US1·US2)이 먼저 동작해야 같은 계정 기준과 세션 흐름을 재사용할 수 있다.

**Independent Test**: 제공자별로 처음 쓰는 소셜 계정으로 가입을 마친 뒤 로그아웃하고 같은 소셜 계정으로 다시 로그인해 같은 사용자로 인식되는지 확인한다. 제공자 화면에서 취소, 이메일 제공 거부, 추가 정보 입력 중 이탈과 만료, 중복 전화번호도 각각 시험한다.

**Acceptance Scenarios**:

1. **Given** 로그인·회원가입 화면의 사용자, **When** 카카오·구글·네이버 중 하나를 선택하면, **Then** 시스템은 그 제공자의 로그인·동의 화면으로 보낸다.
2. **Given** 이미 Thorp 계정과 연결된 소셜 계정으로 제공자 로그인을 마친 사용자, **When** 서비스로 돌아오면, **Then** 시스템은 추가 입력 없이 연결된 계정으로 로그인하고 원래 가려던 서비스 내부 위치로 보낸다.
3. **Given** 어떤 Thorp 계정과도 연결되지 않았고 확인된 이메일도 기존 계정과 겹치지 않는 소셜 계정의 사용자, **When** 서비스로 돌아오면, **Then** 시스템은 제공자에게 받은 이메일을 고칠 수 없게 보여주고 닉네임을 입력받는 추가 정보 화면을 띄운다. 제공자 닉네임이 기준에 맞으면 미리 채운다.
4. **Given** 추가 정보를 유효하게 입력한 사용자, **When** 가입을 제출하면, **Then** 시스템은 계정 하나를 만들고 그 소셜 계정을 연결한 뒤 로그인 상태로 원래 가려던 위치로 보낸다. 비밀번호와 이메일 인증번호는 요구하지 않는다.
5. **Given** 추가 정보 화면에서 형식에 맞지 않는 값을 입력한 사용자, **When** 제출하면, **Then** 시스템은 계정을 만들지 않고 해당 항목과 수정 방법을 표시한다. 휴대폰 번호가 이미 다른 계정에서 쓰이고 있으면 계정을 만들지 않고 US7의 연결 확인 화면으로 보낸다.
6. **Given** 추가 정보를 입력하지 않고 떠났거나 입력 대기 시간이 지난 사용자, **When** 다시 제출하거나 돌아오면, **Then** 시스템은 계정을 만들지 않고 소셜 로그인을 처음부터 다시 시작하도록 안내한다.
7. **Given** 제공자가 이메일을 주지 않은 사용자, **When** 서비스로 돌아오면, **Then** 시스템은 계정을 만들거나 로그인하지 않고 이메일 제공 동의가 필요하다는 거절 화면을 띄운다. 이 화면에서 이메일 제공에 다시 동의하는 소셜 로그인, 이메일로 가입하기, 로그인 화면으로 돌아가기를 고를 수 있다.
8. **Given** 제공자가 이메일은 줬지만 확인 여부를 알려주지 않았거나 확인되지 않았다고 알린 사용자, **When** 서비스로 돌아오면, **Then** 시스템은 그 이메일을 고칠 수 없게 보여주고 FR-004와 같은 6자리 인증번호를 그 주소로 보낸다. 3분 안에 번호를 확인하면 기존 계정과 겹치는지에 따라 추가 정보 화면(시나리오 3) 또는 연결 확인 화면(US7)으로 이어지고, 확인 전에는 계정을 만들거나 연결하거나 로그인하지 않는다.
9. **Given** 제공자 화면에서 로그인이나 동의를 취소한 사용자, **When** 서비스로 돌아오면, **Then** 시스템은 오류 화면 대신 로그인 화면으로 돌려보내고 로그인이 취소됐다고 알린다.

---

### User Story 7 - 같은 이메일이나 휴대폰 번호의 기존 계정에 소셜 계정을 연결한다 (Priority: P2)

이메일로 가입했거나 다른 소셜 계정으로 가입한 사용자가 같은 이메일의 소셜 계정으로 로그인하거나 소셜 가입에서 같은 휴대폰 번호를 입력하면, 기존 계정이 있다는 안내를 받고 그 계정의 소유를 확인한 뒤 소셜 계정을 연결한다.

**Why this priority**: 같은 사람이 계정 두 개를 갖게 되면 내 기록이 나뉜다. 반대로 확인 없이 합치면 다른 사람이 같은 이메일을 내세워 기존 계정에 들어올 수 있으므로, 연결은 기존 계정 소유 확인을 거쳐야 한다.

**Independent Test**: 이메일로 가입한 계정과 같은 이메일의 소셜 계정으로 로그인해 연결 확인 화면이 뜨는지 확인한다. 기존 계정 비밀번호로 확인하면 연결되고 이후 소셜 로그인만으로 같은 계정에 들어가는지, 취소하거나 확인에 실패하면 연결도 새 계정도 생기지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 확인된 이메일이 기존 Thorp 계정과 같고 그 소셜 계정은 아직 연결되지 않은 사용자, **When** 서비스로 돌아오면, **Then** 시스템은 로그인하거나 새 계정을 만들지 않고 "이미 가입된 계정이 있다"는 연결 확인 화면을 띄운다. 화면에는 일부를 가린 기존 계정 이메일과 소유 확인 방법(그 계정의 로그인 방법인 이메일·비밀번호 또는 이미 연결된 소셜 제공자, 그리고 기존 계정 이메일로 받는 인증번호)을 보여준다. 이 이메일은 요청한 사람이 확인한 자기 이메일과 같은 주소다.
2. **Given** 연결 확인 화면의 사용자, **When** 연결을 선택하고 기존 계정으로 로그인하거나 기존 계정 이메일로 받은 6자리 인증번호를 3분 안에 확인하면, **Then** 시스템은 소셜 계정을 기존 계정에 연결하고 기존 계정으로 로그인한 뒤 원래 가려던 위치로 보낸다.
3. **Given** 연결 확인 화면의 사용자, **When** 연결을 취소하면, **Then** 시스템은 아무것도 연결하거나 만들지 않고 로그인 화면으로 돌려보낸다.
4. **Given** 이메일은 기존 계정과 겹치지 않았지만 추가 정보 화면에서 입력한 휴대폰 번호가 다른 기존 계정에서 쓰이는 사용자, **When** 가입을 제출하면, **Then** 시스템은 계정을 만들지 않고 "이 번호로 가입된 계정이 있다"는 연결 확인 화면을 띄운다. 이 화면은 기존 계정의 이메일·연결된 소셜 제공자를 보여주지 않고 기존 비밀번호와 가입할 때 쓴 이메일로 받는 인증번호만 내놓는다. 소유 확인 결과 처리는 시나리오 1·2·3·5와 같고, 인증번호는 그 기존 계정의 이메일로 보낸다. 연결을 마치면 Thorp 계정의 이메일·닉네임·휴대폰 번호는 기존 값을 유지하고, 추가 정보 화면에 입력한 닉네임은 버린다. 연결을 취소한 사용자는 다른 번호로 가입을 계속할 수 있다.
5. **Given** 기존 계정 소유 확인에서 비밀번호나 인증번호가 틀렸거나, 인증번호가 만료됐거나, 다른 계정으로 확인한 사용자, **When** 확인 결과를 받으면, **Then** 시스템은 소셜 계정을 연결하지 않고 다시 시도하거나 취소할 수 있게 한다. 다른 계정으로 확인했다면 그 계정에 연결하지 않는다.
6. **Given** 제공자가 확인 여부를 알려주지 않아 이미 FR-022의 인증번호로 기존 계정과 같은 이메일을 확인한 사용자(시나리오 1의 경우), **When** 연결 확인 화면에서 연결을 선택하면, **Then** 시스템은 그 인증번호 확인을 기존 계정 소유 확인으로 인정하고 인증번호를 다시 요구하지 않는다.
7. **Given** 소셜 계정을 연결한 사용자, **When** 이후 그 소셜 계정으로 로그인하면, **Then** 시스템은 연결 확인 없이 기존 계정으로 로그인하고, 기존 로그인 방법도 계속 쓸 수 있다.
8. **Given** 이메일이나 휴대폰 번호로 찾은 기존 계정에 같은 제공자의 다른 소셜 계정이 이미 연결된 사용자, **When** 서비스로 돌아오거나 가입을 제출하면, **Then** 시스템은 연결 확인 화면을 띄우지 않고 "이 계정은 이미 다른 {제공자} 계정과 연결돼 있다"고 안내하며, 연결된 그 소셜 계정이나 기존 계정의 다른 로그인 방법으로 로그인하는 길을 제공한다. 계정을 만들거나 연결하거나 로그인하지 않는다.

### Edge Cases

- 이메일은 FE와 BE 모두 앞뒤 공백을 제거하고 소문자로 변환한 동일한 정규형으로 검증·인증·중복 조회·로그인·저장한다. 전화번호는 하이픈·공백 없는 국내 휴대폰 숫자 형식만 허용하며 FE와 BE가 같은 정규식을 사용한다. 현재 Backend에는 이메일 정규화가 없으므로 구현 완료가 아니라 필요한 BE 변경으로 취급한다.
- 회원가입 요청이 성공했으나 사용자의 화면 전환 전에 응답이 지연되거나 다시 전달돼도 계정을 두 번 만들지 않는다.
- 로그인 도중 사용자가 다른 화면으로 이동하거나 요청을 다시 시작해도 늦게 도착한 이전 결과가 최신 로그인 상태를 덮어쓰지 않는다.
- 로그아웃 요청 결과를 확인하지 못한 동안에는 이전 사용자의 보호 정보를 다시 노출하지 않고, 상태를 재확인하기 전까지 보호 기능 접근을 허용하지 않는다.
- 여러 탭에서 로그인 또는 로그아웃 상태가 달라질 수 있으므로 앱 최초 진입, 숨겨졌던 탭이 다시 활성화된 시점, '내 기록' 진입 직전에 현재 사용자를 다시 확인한다. 재확인 중에는 보호 정보를 표시하지 않되 공개 기능은 막지 않는다.
- 로그인 만료 직전에 '내 기록'을 열었으면 보호된 내용이 계속 남아 있지 않도록 만료 상태로 전환한다.
- 사용자가 로그인 화면과 회원가입 화면 사이를 이동해도 이전 화면의 비밀번호를 다른 화면에 자동으로 노출하지 않는다.
- 이미 로그인한 사용자가 로그인 또는 회원가입 화면에 직접 접근하면 인증 입력 화면을 표시하지 않고 안전한 기본 화면 `/home`으로 이동한다.
- 로그아웃 시작 또는 인증 만료 뒤 브라우저의 뒤로가기·앞으로가기·페이지 캐시 복원으로 보호 화면이 다시 나타나더라도 현재 사용자 확인 전에는 이전 사용자의 정보와 기록을 표시하지 않는다.
- 서버가 사용자에게 보여줄 수 없는 내부 오류를 반환하면 내부 세부정보 대신 재시도 가능한 일반 안내를 표시한다.
- 소셜 계정은 제공자가 준 사용자 고유 식별자로 구분한다. 제공자 쪽에서 이메일을 바꿔도 이미 연결된 Thorp 계정과의 연결은 유지하고, Thorp 계정의 이메일을 자동으로 바꾸지 않는다.
- 제공자에게서 돌아온 요청이 서비스가 시작한 로그인과 맞지 않거나(위조·재사용·만료), 제공자가 오류를 돌려주면 로그인하지 않고 처음부터 다시 시도하라는 일반 안내를 표시한다. 사용자가 직접 취소한 경우는 오류가 아닌 취소로 안내한다.
- 이미 다른 Thorp 계정에 연결된 소셜 계정은 다른 계정에 다시 연결하지 않는다.
- 한 Thorp 계정에는 제공자마다 소셜 계정을 하나만 연결한다. 이메일이나 휴대폰 번호로 찾은 기존 계정에 같은 제공자의 다른 소셜 계정이 이미 연결돼 있으면 소유 확인을 요구하기 전에 그 사실과 로그인 방법을 안내하고 연결하지 않는다(US7 시나리오 8).
- 소셜로만 가입해 비밀번호가 없는 계정으로 이메일·비밀번호 로그인을 시도하면 일반 로그인 실패와 같은 안내를 준다. 계정 존재 여부나 가입 방법을 로그인 실패 안내로 드러내지 않고, 로그인 화면의 소셜 로그인 버튼으로 다른 방법을 고를 수 있게 한다.
- 이메일 가입 시 이메일이 소셜로만 가입한 계정과 같으면 기존 중복 이메일 규칙(FR-003)대로 사용할 수 없다고 안내한다.
- 소셜 가입 추가 정보 입력이나 연결 확인을 기다리는 동안 제공자 정보는 서버에만 두고 URL·FE 영구 저장소에 남기지 않는다. 대기 상태는 10분 뒤 만료되고 한 번 쓰면 다시 쓸 수 없다.
- 소셜 로그인으로 제공자 화면을 다녀오는 동안에도 원래 가려던 서비스 내부 위치를 보존하고, 외부·유효하지 않은 위치는 FR-011과 같이 `/home`으로 대체한다.
- 이미 로그인한 사용자가 소셜 로그인을 시작하는 경우는 로그인·회원가입 화면 직접 접근과 같이 `/home`으로 보낸다. 로그인한 상태에서 소셜 계정을 추가로 연결하는 기능은 이번 범위가 아니다.
- 탈퇴했거나 이용이 막힌 계정에 연결된 소셜 계정으로 로그인하면 로그인하지 않고 이메일 로그인과 같은 일반 실패 안내를 준다. 계정 상태를 따로 드러내지 않는다.
- 이메일이나 휴대폰 번호가 겹친 기존 계정이 탈퇴했거나 이용이 막힌 상태면 연결 확인을 권하지 않는다. 가입도 연결도 하지 않고 같은 일반 실패 안내를 준다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 서비스는 사용자가 이메일·비밀번호·닉네임을 입력해 계정을 만들 수 있게 한다. 휴대폰 번호는 묻지 않는다(2026-10-02 결정). 요청에 번호가 실려 오면 아래 형식으로 검사하고 중복이면 거절한다. 이메일은 앞뒤 공백을 제거하고 소문자로 변환한 뒤 검증·인증·중복 조회·로그인·저장에 동일하게 사용한다. 현재 확인된 나머지 입력 기준은 유효한 이메일, 8~25자의 비밀번호, 2~20자의 닉네임, `^01[016789]\d{7,8}$`에 맞는 하이픈·공백 없는 국내 휴대폰 번호다. 정규형의 최종 판정과 저장은 Backend가 맡고 FE는 같은 규칙으로 사전 안내한다.
- **FR-002**: 서비스는 필수 입력 누락과 형식·길이 위반을 제출 전에 항목 가까이에 표시하고, 서버 판정과 다른 임의 기준으로 유효한 요청을 차단하지 않는다.
- **FR-003**: 서비스는 이미 가입된 이메일·전화번호, 이메일 인증 요청 없음·잘못된 번호·만료·미완료, 그 밖의 입력 거절 사유를 안정된 오류 코드로 구분해 안내하며 중복 계정을 성공으로 표시하지 않는다. 기존 Backend가 이 사유를 모두 `INVALID_INPUT`으로 반환하는 상태는 요구사항 충족으로 간주하지 않고 공통 계약을 보완해야 한다.
- **FR-004**: 서비스는 회원가입에 이메일 소유 확인 단계를 포함한다. 사용자는 가입되지 않은 이메일로 6자리 인증번호 발송을 요청하고 3분 안에 번호를 확인해야 회원가입을 완료할 수 있다. 재발송하면 앞서 발급된 번호는 더 이상 사용할 수 없으며, 발송 실패·요청 없음·잘못된 번호·만료·미확인 상태를 각각 다음 행동이 드러나는 안내로 처리한다.
- **FR-005**: 회원가입 성공 시 서비스는 로그인 화면으로 이동해 가입한 이메일만 미리 입력한다. 생성된 사용자의 식별자·이메일·닉네임·상태처럼 비민감한 결과만 표시 또는 후속 흐름에 사용하고, 비밀번호를 화면 간 전달값·응답 표시·완료 상태에 노출하지 않는다.
- **FR-006**: 서비스는 이메일 인증번호 발송·확인, 회원가입, 로그인, 로그아웃 요청을 처리하는 동안 같은 동작의 추가 제출을 막는다. 각 요청은 현재 처리 중인 요청 식별자 또는 취소 상태를 기준으로 최신 요청의 결과만 반영하며, 성공·실패·네트워크 오류 중 하나가 확인되기 전에 완료로 표시하지 않는다.
- **FR-007**: 서비스는 기존 사용자가 이메일과 비밀번호로 로그인하고 성공 또는 실패 여부를 알 수 있게 한다. 로그인 실패는 로그인 상태로 전환하지 않고 재시도를 허용한다.
- **FR-008**: 서비스는 별도의 '로그인 상태 유지' 선택지를 제공하지 않고 서버가 정한 유효기간을 따른다. 유효한 로그인 상태는 새로고침과 페이지 재진입 후 확인·복원하며, 앱 최초 진입·숨겨졌던 탭의 재활성화·'내 기록' 진입 직전에 현재 사용자를 확인한다. 확인 중에는 로그인 여부를 단정하거나 사용자 전용 정보를 노출하지 않고 공개 기능은 계속 이용할 수 있게 한다.
- **FR-009**: 서비스는 로그인한 사용자가 로그아웃할 수 있게 한다. 요청을 시작하면 이전 사용자의 표시 정보와 보호된 내용을 즉시 숨기며, 서버에서 완료를 확인한 경우에만 로그아웃 완료로 표시한다. 완료를 확인하지 못하면 '로그아웃 미확인' 상태로 보호 기능 접근을 차단하고 상태 확인 또는 재시도를 제공한다.
- **FR-010**: 서비스는 로그인하지 않은 사용자가 전략 진단·시장 흐름·배우기를 이용할 수 있게 하며, 이 기본 기능 진입에 회원가입이나 로그인을 요구하지 않는다. 예외는 011의 계산 생성·현금 시작·전체 기간 재계산·재시도·개인 검색 기록 저장 및 시장 흐름의 「이 기간으로 전략 비교」 진입이다. 경제환경 검색·사례 열람과 유효한 공개 주소의 기존 결과 조회는 공개한다.
- **FR-011**: 서비스는 로그인하지 않은 사용자의 '내 기록' 및 FR-010의 011 보호 동작 접근을 제한하고 로그인 필요 안내를 제공한다. 로그인 성공 후에는 사용자가 원래 접근하려던 서비스 내부 위치로 돌아가며, 유효하지 않거나 외부인 복귀 위치는 안전한 기본 화면으로 대체한다.
- **FR-012**: 서비스는 로그인 상태가 만료되면 보호된 정보를 숨기고 재로그인을 안내한다. 재로그인 성공 후에는 만료 전에 이용하던 유효한 '내 기록' 내부 위치로 돌아가며, 유효하지 않거나 외부인 위치는 안전한 기본 화면으로 대체한다. 만료 또는 상태 확인 실패를 로그인 성공이나 빈 기록으로 표시하지 않는다.
- **FR-013**: 서비스는 인증 요청 실패 시 공통 계약의 안정된 오류 코드와 사용자에게 공개 가능한 메시지를 사용한다. 가입·이메일 인증의 사유별 오류, 잘못된 로그인 정보, 로그인 필요, CSRF 오류, 예상하지 못한 서버 오류를 구분하되 내부 구현 정보나 민감한 값을 노출하지 않는다. 응답 없는 네트워크 실패는 FE가 별도의 연결 오류로 처리한다.
- **FR-014**: 로그인·로그아웃·현재 사용자 확인에 필요한 서버 기능이 현재 존재하지 않거나 확인되지 않았다면 이를 구현 완료로 가정하지 않고 계획 단계의 서버 의존성으로 기록한다. 이 spec 작성 과정에서는 서버 코드를 생성하거나 수정하지 않는다.
- **FR-015**: 로그인과 회원가입 화면은 서로 이동할 수 있으며, 이동·실패·재시도 과정에서 비밀번호를 URL·나 화면 간 전달값으로 노출하지 않는다.
- **FR-016**: 이메일 인증·회원가입·로그인·로그아웃·상태 확인의 처리 중·성공·실패·만료·로그아웃 미확인 상태는 화면을 보지 않는 사용자도 알 수 있도록 상태 알림 영역으로 전달한다. 입력 오류는 해당 입력과 연결하고 제출 실패 시 첫 번째 잘못된 입력으로 초점을 이동하며, 화면 전환 뒤에는 새 화면의 제목부터 흐름을 이어갈 수 있게 한다. 모든 입력과 주요 동작은 키보드만으로 완료할 수 있어야 한다.
- **FR-017**: 인증 상태나 요청 상태가 바뀌어도 전략 진단·시장 흐름·배우기의 사용 중인 입력을 이유 없이 초기화하지 않는다.
- **FR-018**: 로그인 성공 시 서비스는 로그인 전 세션 식별자를 그대로 재사용하지 않고 새 식별자로 교체한다. 비밀번호·인증번호·세션 식별자·전체 쿠키 또는 인증 헤더는 URL, 사용자 응답, FE 영구 저장소 및 인증 실패 로그에 기록하지 않는다.
- **FR-019**: 이미 로그인한 사용자가 로그인·회원가입 화면에 접근하면 `/home`으로 이동한다. 로그아웃 시작·로그인 만료·상태 확인 실패 후에는 현재 사용자 확인이 완료되기 전까지 브라우저 방문 기록이나 페이지 캐시에서 복원된 보호 정보를 표시하지 않는다.
- **FR-020**: 서비스는 로그인·회원가입 화면에서 카카오·구글·네이버 소셜 로그인을 제공한다. 소셜 로그인은 기존 이메일·비밀번호 가입·로그인을 대체하지 않으며, 성공하면 이메일 로그인과 같은 로그인 상태·만료·로그아웃·보호 경로 규칙(FR-008~FR-012, FR-018)을 따른다.
- **FR-021**: 서비스는 소셜 계정을 제공자와 제공자의 사용자 고유 식별자로 구분해 Thorp 계정에 연결한다. 이미 연결된 소셜 계정은 연결된 계정으로 로그인하고, 다른 계정에 다시 연결하지 않는다. 한 계정에는 제공자마다 하나의 소셜 계정만 연결한다. 이메일·휴대폰 번호로 찾은 기존 계정에 같은 제공자의 다른 소셜 계정이 이미 연결돼 있으면 FR-024의 연결 확인을 시작하지 않고, 이미 연결돼 있다는 사실과 로그인 방법만 안내한다.
- **FR-022**: 서비스는 확인된 이메일이 있을 때만 소셜 가입·연결을 진행한다. 제공자가 확인했다고 알린 이메일은 확인된 것으로 본다. 제공자가 확인 여부를 알려주지 않거나 확인되지 않았다고 알린 이메일은 FR-004와 같은 6자리 인증번호(3분 유효, 재발송 시 이전 번호 무효)를 그 주소로 보내 확인한 뒤에만 진행한다. 제공자가 이메일을 주지 않은 경우에는 계정을 만들거나 로그인하지 않고 거절 화면을 띄운다. 거절 화면은 이메일이 필요한 이유와 제공자 이름을 알리고, 이메일 제공에 다시 동의하는 소셜 로그인·이메일로 가입하기·로그인 화면으로 돌아가기를 제공한다. 제공자가 준 이메일은 FR-001과 같은 정규형으로 바꿔 쓴다.
- **FR-023**: 처음 가입하는 소셜 사용자는 추가 정보 화면에서 FR-001과 같은 기준의 닉네임을 입력해야 가입을 마친다. 휴대폰 번호는 묻지 않고, 아래 번호 규칙은 요청에 번호가 실려 온 경우에만 적용한다(2026-10-02 결정). 이메일은 제공자가 준 값을 고칠 수 없게 보여주고, 비밀번호와 이메일 인증번호는 요구하지 않는다. 제공자 닉네임이 기준에 맞으면 미리 채운다. 입력 오류는 FR-002와 같이 안내하고, 휴대폰 번호가 이미 다른 계정에서 쓰이면 계정을 만들지 않고 그 계정에 대한 FR-024 연결 확인으로 보낸다. 연결을 취소하면 다른 번호로 가입을 계속할 수 있게 한다. 가입 제출에는 FR-006의 중복 제출 방지를 적용한다.
- **FR-024**: 연결되지 않은 소셜 계정의 확인된 이메일이 기존 계정과 같거나, 소셜 신규 가입자가 입력한 휴대폰 번호가 기존 계정과 같으면 서비스는 자동으로 로그인하거나 연결하거나 새 계정을 만들지 않는다. 휴대폰 번호로 찾은 기존 계정이면 인증번호는 그 계정의 이메일로 보내고, FR-022에서 제공자 이메일을 확인한 것은 소유 확인으로 인정하지 않는다. 연결 확인 화면에서 사용자가 연결을 선택하고 다음 중 하나로 기존 계정 소유를 확인했을 때만 연결하고 기존 계정으로 로그인한다. (1) 기존 계정으로 로그인한다(이메일·비밀번호 또는 이미 연결된 소셜 계정). (2) 기존 계정 이메일로 보낸 FR-004와 같은 6자리 인증번호를 3분 안에 확인한다. 같은 대기 상태에서 FR-022의 인증번호로 이미 그 이메일을 확인했다면 (2)를 마친 것으로 본다. 확인 실패·만료·취소·다른 계정으로의 확인은 연결하지 않는다. 비밀번호가 없거나 잊은 사용자도 (2)로 연결할 수 있다. 이메일이 겹친 경우 확인 화면의 기존 이메일은 일부를 가려 보여준다. **휴대폰 번호가 겹친 경우에는 기존 계정의 이메일(가린 것 포함)·연결된 소셜 제공자·비밀번호 유무를 보여주지 않고**, 확인 방법으로 기존 비밀번호와 "가입할 때 쓴 이메일로 받는 인증번호"만 내놓는다. 인증번호는 서버가 그 계정 이메일로 보내므로 주소를 몰라도 주인은 확인할 수 있다.
- **FR-025**: 소셜 가입 추가 정보 입력과 연결 확인을 기다리는 상태는 서버에만 보관하고, 10분 뒤 만료되며 한 번만 쓸 수 있다. 만료되거나 이미 쓴 상태로 제출하면 계정을 만들거나 연결하지 않고 소셜 로그인을 다시 시작하도록 안내한다. 제공자에게 받은 접근 토큰은 URL·사용자 응답·FE 영구 저장소·로그에 남기지 않는다. 인가 코드는 제공자가 서버 콜백 주소로 돌려보낼 때만 주소에 실리며, 서버는 처리 뒤 코드가 없는 서비스 주소로 이동시키고 코드를 로그에 남기지 않는다.
- **FR-026**: 서비스는 제공자에게서 돌아온 요청이 서비스가 시작한 로그인 요청과 맞는지 확인하고, 맞지 않으면 로그인하지 않는다. 제공자 화면에서의 사용자 취소는 로그인 화면의 취소 안내로, 제공자 오류·요청 불일치는 재시도 가능한 일반 안내로 구분해 처리한다. 소셜 로그인 경로에서도 원래 가려던 서비스 내부 위치를 FR-011과 같은 규칙으로 보존·검증한다.

### Key Entities

- **사용자 계정**: 사용자별 기록 접근의 주체다. 현재 회원가입 결과에서 식별자·이메일·닉네임·계정 상태를 확인할 수 있으며, 전화번호와 비밀번호는 완료 화면에 노출하지 않는다.
- **회원가입 입력**: 이메일·비밀번호·닉네임과 유효성 상태를 포함한다. 휴대폰 번호는 선택이며 화면에서 묻지 않는다. 비밀번호는 계정 결과로 보존하거나 표시하지 않는다.
- **로그인 입력**: 가입된 이메일과 비밀번호로 구성하며, 로그인 성공 여부를 확인하는 동안 민감한 값을 화면 간 전달값이나 주소에 노출하지 않는다.
- **인증 상태**: 확인 중·로그인됨·로그인되지 않음·만료·확인 실패·로그아웃 미확인을 구분하며, 로그인된 경우 현재 사용자와 연결된다. 로그아웃 미확인 중에는 보호 정보를 노출하지 않는다.
- **복귀 위치**: 보호 기능에 접근하기 전 사용자가 원래 가려던 서비스 내부 위치다. 로그인 성공 뒤 한 번 사용하고 외부 위치로 이동시키지 않는다.
- **소셜 계정 연결**: Thorp 계정과 카카오·구글·네이버 계정의 연결이다. 제공자·제공자 사용자 고유 식별자·연결 시점을 가지며, 한 계정은 제공자마다 하나만 가진다. 소셜로만 가입한 계정은 비밀번호가 없다.
- **소셜 가입 대기 상태**: 제공자 로그인은 끝났지만 추가 정보 입력이나 기존 계정 연결 확인을 기다리는 서버 측 상태다. 제공자·제공자 사용자 식별자·확인된 이메일·제공자 닉네임과 만료 시각을 가지며, 10분 뒤 만료되고 한 번 쓰면 사라진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 유효한 가입 정보를 미리 준비한 사용자는 인증 메일을 확인해 인증번호 입력을 시작한 시점부터 회원가입 성공 응답까지 3분 이내에 흐름을 완료할 수 있다. 발송 요청 성공부터 메일을 실제로 확인하기까지의 외부 메일 전달 시간은 측정에서 제외한다.
- **SC-002**: 필수 입력 누락·형식 위반·중복 이메일·중복 전화번호·인증 요청 없음·잘못된 인증번호·만료·미확인 표본의 100%에서 계정이 생성되지 않고, 안내에 실패 원인과 사용자가 선택할 수 있는 다음 행동(입력 수정·재입력·재발송·재시도 중 해당 항목)이 함께 표시된다.
- **SC-003**: 인증번호 발송·확인, 회원가입, 로그인, 로그아웃 각각에 대해 처리 중 1초 안에 같은 제출 동작을 5회 연속 수행한 시험에서 서버 요청은 종류별 한 건만 시작되고 늦은 이전 응답이 최신 상태를 덮어쓴 사례는 0건이다.
- **SC-004**: 로그인하지 않은 사용자의 '내 기록' 접근 시험 100%에서 보호된 기록이 노출되지 않고, 로그인 성공 후 원래 '내 기록'으로 복귀한다.
- **SC-005**: 로그인하지 않은 사용자가 전략 진단·시장 흐름·배우기를 이용하는 기본 기능 시험 100%에서 인증이 강제되지 않는다. 011 예외 동작은 실행되지 않고 로그인 안내와 같은 사례 복귀가 제공되며, 익명 검색·기존 공개 결과 조회는 계속 가능하다.
- **SC-006**: 유효한 로그인 상태의 새로고침·재진입 표본 100%에서 상태 확인 후 같은 사용자로 복원되고, 확인 중 보호 정보가 먼저 노출된 사례가 0건이다.
- **SC-007**: 로그아웃 또는 로그인 만료 후 보호 기능에 접근한 시험 100%에서 이전 사용자 정보가 노출되지 않고 로그인 안내가 표시된다.
- **SC-008**: 잘못된 입력·인증 실패·네트워크 오류 표본의 100%가 전체 서비스 오류 화면으로 끝나지 않고 해당 흐름 안에서 수정 또는 재시도 가능한 상태로 처리된다.
- **SC-009**: 키보드만 사용하는 검증에서 회원가입·로그인·로그아웃과 오류 확인을 모두 완료할 수 있고, 주요 상태 변경 중 보조 기술에 전달되지 않는 상태가 0건이다.
- **SC-010**: 로그인 성공 표본 100%에서 로그인 전후 세션 식별자가 다르고, 비밀번호·인증번호·세션 식별자가 URL·사용자 응답·FE 영구 저장소·인증 실패 로그에 나타난 사례가 0건이며, CSRF 토큰이 없거나 일치하지 않는 상태 변경 요청은 상태 변경 없이 403 공통 오류로 끝난다.
- **SC-011**: 로그인된 사용자의 인증 화면 직접 접근과 로그아웃·만료 후 브라우저 방문 기록 및 페이지 캐시 복원 표본 100%에서 인증 입력 또는 이전 보호 정보가 노출되지 않는다.
- **SC-012**: 카카오·구글·네이버 각각에서 신규 가입·재로그인·연결 확인 후 로그인·이메일 미제공 거절·사용자 취소 표본의 100%가 해당 화면으로 끝나고, 같은 소셜 계정으로 다시 로그인했을 때 다른 계정이 만들어진 사례가 0건이다.
- **SC-013**: 기존 계정과 같은 이메일의 소셜 로그인 표본과 기존 계정과 같은 휴대폰 번호의 소셜 가입 표본 100%에서 기존 계정 소유 확인 없이 로그인·연결·새 계정 생성이 일어난 사례가 0건이고, 확인을 마친 표본 100%에서 이후 소셜 로그인만으로 같은 계정에 들어간다.
- **SC-014**: 이메일 미제공 표본의 100%에서 계정이 생성되거나 로그인되지 않고 거절 화면의 세 가지 다음 행동이 모두 표시된다. 확인 여부를 알 수 없거나 미확인인 이메일 표본의 100%에서 Thorp 인증번호 확인 전에 계정 생성·연결·로그인이 일어난 사례가 0건이고, 확인 후에는 가입 또는 연결 확인으로 이어진다.
- **SC-015**: 소셜 로그인 표본 100%에서 콜백 처리가 끝난 뒤의 서비스 주소·FE 영구 저장소·사용자 응답·로그에 제공자 접근 토큰·인가 코드가 남은 사례가 0건이고, 만료되거나 이미 쓴 가입 대기 상태로 계정이 만들어진 사례가 0건이며, 서비스가 시작하지 않은 콜백 요청으로 로그인된 사례가 0건이다.

## Assumptions

- 전략 진단·시장 흐름·배우기는 사용자 식별 없이 이용하고, '내 기록' 저장·재조회만 식별된 사용자 단위로 제공한다.
- 현재 서버에는 회원가입과 이메일 인증번호 발급·확인 기능이 존재한다. 회원가입은 이메일·비밀번호·닉네임·국내 휴대폰 번호를 받고 이메일 소유 확인 완료를 전제로 한다.
- 현재 저장소에서 로그인·로그아웃·현재 사용자 조회 기능은 확인되지 않았다. 이 기능들은 plan에서 기존 구현 여부를 다시 검증하고, 없으면 서버 담당 작업으로 분리한다.
- 인증·인가 방식과 로그인 상태의 구체적인 유효기간은 constitution에서 합의되지 않은 영역이다. 사용자는 유지 기간을 따로 선택하지 않으며 서버가 정한 유효기간을 따른다. 구체적인 구현 선택과 기간은 plan에서 서버 계약 의존성으로 확인한다.
- 카카오·구글은 이메일과 그 이메일의 확인 여부를 함께 알려준다. 네이버는 확인 여부 필드가 없지만 연락처 이메일을 네이버가 이미 확인하므로 확인된 것으로 본다(2026-10-02 결정). 확인 여부를 알 수 없거나 미확인인 이메일은 Thorp 인증번호로 확인한다(FR-022). 제공자별로 이 정보를 어떻게 받는지는 plan에서 확인한다.
- 소셜 가입자의 닉네임·휴대폰 번호 기준과 중복 규칙은 이메일 가입과 같다. 소셜로만 가입한 계정에 나중에 비밀번호를 만드는 기능은 이번 범위가 아니다.
- 사용자는 최신 상태의 일반적인 데스크톱 브라우저를 우선 사용하며, 기존 반응형 기준에 따라 360px 이상 모바일에서도 같은 인증 흐름을 완료할 수 있어야 한다.

## Dependencies

- 기존 회원가입 기능과 그 입력·거절 규칙을 재사용한다. 기존 동작을 바꾸어야 한다면 별도 서버 작업과 계약 합의가 필요하다.
- 로그인·로그아웃·현재 사용자 확인을 실제로 제공할 서버 기능과 FE/BE 공통 계약이 필요하다.
- '내 기록' 화면 또는 진입점은 인증 상태를 확인하고 원래 목적지를 복원할 수 있어야 한다.
- 반복 로그인과 인증번호 발송의 서버측 남용 방지 수치·잠금 정책은 현재 Backend와 팀 정책에서 확인되지 않았다. 임의의 횟수를 확정하지 않으며 운영 배포 전 별도 보안 Task에서 정책·오류 계약·관측 기준을 합의해야 한다. 2026-10-01에 소셜 연결 확인과 이메일 인증번호에는 계정 탈취·메일 폭탄을 막는 임시 상한(번호 대조 5회, 이메일 가입 재발송 간격 30초부터 두 배씩 최대 10분, 소셜 경로 발송 대기 상태당 5통, 같은 기존 계정을 향한 연결 확인 한 시간 10회·발송 5통)을 먼저 넣었다. 이 값은 그 보안 Task가 확정할 때까지의 임시값이며, 이메일·비밀번호 로그인 반복 시도의 제한은 여전히 그 Task의 몫이다.
- 카카오·구글·네이버 개발자 콘솔의 앱 등록, 개발·운영별 리다이렉트 주소, 클라이언트 자격 증명이 필요하다. 자격 증명은 서버에서만 관리한다. 카카오는 이메일을 필수 동의 항목으로 받으려면 비즈 앱 전환이 필요할 수 있고, 전환 전에는 이메일이 선택 동의라 거절 화면(FR-022)이 더 자주 뜰 수 있다.
- 비밀번호가 없는 계정과 소셜 계정 연결을 담는 DB 변경이 필요하다. 현재 `users`의 `password_hash`·`phone_number`가 NOT NULL이므로 plan에서 스키마와 기존 데이터 호환을 정한다.

## Out of Scope

- 비밀번호 찾기·재설정
- 카카오·구글·네이버 외의 소셜 로그인
- 로그인한 상태에서 소셜 계정을 추가로 연결하거나 연결을 해제하는 계정 관리 화면
- 소셜로만 가입한 계정에 비밀번호를 추가하는 기능
- 제공자 쪽 연결 끊기·탈퇴 알림을 받아 Thorp 계정에 반영하는 기능
- 제공자 프로필 사진·닉네임 변경의 자동 동기화
- 이메일 인증번호 방식 외 추가 본인확인 절차
- 회원 탈퇴
- 사용자 역할별 권한 관리와 관리자 계정
- 인증과 무관한 '내 기록' 조회·저장·비교 기능 자체 ([006](../006-my-records/spec.md))
- 서버 인증 기능의 구현 코드와 구체적인 통신 경로·메서드·응답 형식
- 반복 로그인·인증번호 요청의 운영 제한 횟수와 계정 잠금 정책(별도 보안 Task에서 확정)
